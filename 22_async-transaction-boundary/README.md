# 第22問：会員登録とその後続処理（クーポン付与・ウェルカムメール・集計）

**📅 出題日**: 2026年8月29日

## 📋 レビュー課題

会員登録APIから呼ばれるサービスクラスです。1回の登録で次の4つを行っています。

1. 会員レコードを保存する
2. 新規登録特典のクーポンを付与する（クーポン発行＋会員側のフラグ更新）
3. ウェルカムメールを送る（時間がかかるので非同期にしたつもり）
4. その日の登録件数を集計テーブルに加算する（裏で実行）

メンバーからは「ローカルで登録ボタンを押すと会員も作られるし、メールも届くし、クーポンも付いています。非同期化したのでレスポンスも速いはずです」と報告が来ています。

対象: [`bad/MemberRegistrationService.java`](bad/MemberRegistrationService.java)

「どこが問題か、どう直すべきか」をレビューしてみてください。

> ヒント代わりの問い：
> - このコードで、ウェルカムメールは**本当に非同期で**送られているでしょうか？
> - クーポン付与の途中（`couponRepository.save` の直後）で例外が起きたら、DBには最終的に何が残りますか？
> - 登録が1秒に100件来るサービスに育ったら、このサーバーには何が起き始めるでしょう？

---

## ❌ NGポイント (bad/ 配下)

1. **`@Async` の自己呼び出しで非同期が効かない（今回の核心①）**: `sendWelcomeMail` は `@Async` 付きだが、同じクラスの `register()` から `this.sendWelcomeMail(...)` として呼ばれている。Springは本体の周りに「プロキシ（代理人）」を1枚かぶせて非同期化を差し込むが、**同一クラス内の呼び出しはプロキシを素通り**するため無効化される。結果、メール送信は**同期実行**され、レスポンスは全く速くなっていない（報告と実態が食い違う）。

2. **`@Transactional` の自己呼び出しでトランザクションが効かない（今回の核心②）**: `grantSignUpCoupon` も同様に `register()` から自己呼び出しされており、`@Transactional` が効いていない。しかも `register()` 自体にトランザクションがない。→ `couponRepository.save`（クーポン発行）は成功したのに、その直後の会員フラグ更新で例外が起きると、**クーポンだけ発行されフラグは立っていない**ちぐはぐな状態がDBに残る（部分コミット）。会員保存とも別トランザクションなので、後続失敗時も会員だけ残る。

3. **取り消せない副作用（メール）をコミット確定前に実行している**: 仮に `@Async` が効いたとしても、メールは「登録が最終的に成功したか」を待たずに送られうる。登録がロールバックされても**「登録ありがとう」メールだけ飛ぶ**事故が起きる。取り消せない外部作用は、必ず**コミット確定後**に行うべき。

4. **`@Async` が効いた場合の"コミット前レコード読み取り"レース**: 非同期メール処理は別スレッドで `findById` するが、呼び出し元トランザクションが**まだコミットしていない**タイミングだと会員が見つからず `NoSuchElementException`（`.get()`）になりうる。非同期とトランザクション境界がかみ合っていない。

5. **`new Thread(...).start()` による無制限なスレッド生成**: 集計更新のたびにOSスレッドを新規生成・使い捨てしている。プール（固定チーム）もキュー（順番待ちの列）も上限もない。1秒100件なら毎秒100本のスレッドが生まれ、負荷が続けば**スレッド枯渇・メモリ枯渇でサーバごと停止**する。背圧（流入制御）もかからない。

6. **`@Async void` ＋ `e.printStackTrace()` で例外がどこにも伝わらない**: 非同期メソッドの戻り値が `void` だと、中で起きた例外は呼び出し元に伝播しない。さらに `printStackTrace()` は標準エラーに吐くだけで、ログ基盤にも監視にも乗らない＝**握りつぶし**。失敗に誰も気づけない。

7. **`Optional.get()` で存在チェックなし**: `findById(memberId).get()` は該当なしの場合に即例外。`orElseThrow` で「いない場合」を明示的に扱うべき。

8. **マジック値の直書き**: `"ACTIVE"`（状態）、`"WELCOME1000"`（クーポンコード）、`1000`（金額）がソースに直書き。状態は enum、特典内容は定数/設定として名前を付けて外に出すべき（表記ゆれ・変更漏れの温床）。

9. **入力バリデーション欠如**: メールの形式・必須・重複チェックがない。形式チェックはコントローラ層（Bean Validation）、重複などの業務チェックはサービス層で行う。

## ⭕️ 改善案 (good/ 配下)

1. **トランザクション境界を入口に置く**: `register()` 自身に `@Transactional` を付け、「会員保存＋クーポン付与＋集計」を1つの原子的単位に束ねる。外部（Controller）から呼ばれるのでプロキシを通り、確実に効く。→ 途中失敗なら全部ロールバックし、部分コミットが起きない。
2. **クーポン付与は同一トランザクション内の private メソッドに**: 別トランザクションにする必要がないので、`register()` の中で呼ぶ private メソッドにして同じトランザクションに含める（自己呼び出しの罠を回避）。
3. **メール送信はイベント＋コミット後・別Beanで非同期化**: `register()` は `ApplicationEventPublisher` で「登録された」イベントを発行するだけ。別Bean `WelcomeMailListener` が `@Async @TransactionalEventListener(AFTER_COMMIT)` で受け、**コミット確定後にだけ非同期送信**する。別Beanなのでプロキシを通り `@Async` が本当に効き、ロールバック時は送らない、レースも起きない。
4. **専用スレッドプールを用意（`AsyncConfig`）**: `@EnableAsync` ＋ 上限つき `ThreadPoolTaskExecutor`（コア/最大人数・キュー長・`CallerRunsPolicy` による背圧）。`new Thread` の無制限生成をやめ、負荷が急増してもサーバを守る。
5. **例外は握りつぶさずロガーへ**: リスナー内で受け止め、`log.error(..., e)` で原因ごと記録。メール失敗は確定済みの登録を巻き戻す理由にならないため、ここでは記録に留める（監視・再送の判断材料になる）。
6. **`orElseThrow` / enum / 設定外部化 / バリデーション**: `.get()` を `orElseThrow` に、状態は `MemberStatus` enum に、特典内容は定数（実務では設定）に、重複チェックはサービス層で実施。

## 💬 レビューコメント例文

> 実装おつかれさまです、動作確認まで丁寧で助かります。2点だけ設計の根っこに関わるところを一緒に見たいです。
>
> ① `@Async` と `@Transactional` は、**同じクラス内から呼ぶと効かない**仕様があります（Springがプロキシ経由で機能を差し込むため、自己呼び出しだと素通りしてしまう）。今回メールは実は同期実行、クーポン付与のトランザクションも効いていない状態です。メールは「登録イベントを発行→別BeANが AFTER_COMMIT で非同期送信」に、トランザクション境界は `register()` 自体に付ける形にすると、意図どおりに動いてデータのちぐはぐも防げます。
>
> ② 集計の `new Thread().start()` は、負荷が上がるとスレッドが青天井に増えてサーバが落ちる危険があります。`@Async` ＋上限つきスレッドプールに載せ替えて「固定チーム＋順番待ちの列」で捌く形にしましょう。
>
> このあたりは動いて見えるだけに気づきにくい"隠れ負債"なので、今のうちに直しておけると強いです。ペアで直しながら仕組みを共有しましょう。
