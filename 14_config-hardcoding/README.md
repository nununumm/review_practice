# 第14問：日次売上レポートを出力するサービス（設定値の扱い）

**📅 出題日**: 2026年8月1日

## 📋 レビュー課題

毎日の売上を集計する `DailySalesReportService` です。
毎晩1回、バッチ（自動実行の仕組み）から `generateDailyReport()` が呼ばれ、

1. その日の注文を集計し、
2. 消費税込みの金額をレポートファイルに書き出し、
3. 売上が大きい日は経理部長にメールで速報を送る、

という処理をします。

ローカルで動かすと、ちゃんとレポートファイルができてメールも飛び、一見きちんと動いています。

対象: `bad/DailySalesReportService.java`

このコードを本番に出す前提で、「どこが問題か・どう直すべきか」をレビューしてみてください。
今回は特に **「コードの中に“決め打ちで書かれた値”は、本番運用でどう困るか」** という観点で見てみましょう。
（もちろん、それ以外に気づいた点も遠慮なく指摘してください。過去の問題で扱った観点も潜んでいます。）

---

## ❌ NGポイント (bad/ 配下)

### 【今回の主観点：ハードコーディング＝“決め打ち”】

1. **環境依存の値をコードに直書き（最重要）**: 出力先パス `C:\reports\`（42行目）と送信先メール `keiri-bucho@example.com`（51行目）がコードに埋め込まれている。
   - `C:\reports\` は開発者のWindows PC専用。**本番のLinuxサーバーには存在せず、その場でクラッシュ**する。
   - メール先は経理部長の**異動で変わる**。変えるたびに「コード修正 → 再ビルド → 再デプロイ」が必要になり、たった1文字の変更に大掛かりな作業が発生する。
   - 環境（開発／検証／本番）ごとに値を変えられないため、同じビルドをどこでも動かす、が成立しない。

2. **マジックナンバー**: `* 1.1`（税率／37行目）と `> 1000000`（通知の基準額／49行目）が“謎の数字”のまま散らばっている。コードを読んでも「この1.1は何？」が分からず、税率変更や基準額変更のたびに人間が数字を探して直すことになる（＝直し漏れ・誤修正の温床）。

### 【復習：過去問で扱った観点】

3. **テスト容易性の欠如（第8・12問の復習）**: 「今日」を `LocalDate.now()` でメソッド内から直接取得している（28行目）。これだと**特定の日付のレポートを自動テストで検証できない**（テストを動かした“実際の今日”に依存してしまう）。時刻という「外の世界」に固く結びついている。

4. **例外の握りつぶし（第3・5問の復習）**: ファイル書き込みの `catch` が `e.printStackTrace()` だけ（45〜47行目）。
   - `printStackTrace()` は標準エラー出力に垂れ流すだけで**ログ基盤に乗らない**＝本番では誰の目にも届かない（第7・11問のログ設計にも通じる）。
   - 失敗しても処理は**そのまま先へ進み**、`if` を通ってメールが飛びうる。**「ファイルは壊れているのに売上速報だけ届く」という“嘘の正常”**が起きる。

5. **リソースリーク**: `FileWriter` を try-with-resources ではなく手動 `close()` で閉じている（43〜44行目）。途中の `writer.write(...)` で例外が出ると `close()` 行に到達できず、**ファイルハンドルが閉じられないまま漏れる**。

6. **集計をアプリ側の for 文で回している（パフォーマンス）**: 全注文を取得してから Java の for で合計している（31〜34行目）。件数が増えるほど大量のオブジェクトをメモリに積み、遅くなる。集計は DB（SUM/COUNT）に任せるべき。

## ⭕️ 改善案 (good/ 配下)

1. **環境依存値・業務ルール値を `application.properties` へ外部化**し、`@Value("${...}")` で注入する。値の変更が「設定ファイル1行の修正」で済み、再ビルド不要になる。環境ごとの差し替えも可能に。
2. **`Clock`（時計）をコンストラクタで注入**し、`LocalDate.now(clock)` で今日を取得。本番は本物の時計、テストは「止めた時計」を渡して**特定日を再現テスト**できるようにする。
3. **try-with-resources** でファイルを開き、閉じ忘れ（リソースリーク）を防ぐ。
4. **例外を握りつぶさない**：`logger.error(...)` でログ基盤に残したうえで**投げ直して中断**。ファイル出力が成功したときだけ通知する。
5. **集計は DB の SUM/COUNT に委譲**（`@Query` + プロジェクション `DailySalesSummary`）。返すのは数字だけにしてメモリ負荷を下げる。
