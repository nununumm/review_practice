# 第21問：外部倉庫システム（WMS）への在庫問い合わせ

**📅 出題日**: 2026年8月29日

## 📋 レビュー課題

注文された各商品について、外部の倉庫システム（WMS）のREST APIを HTTP で呼び出し、「その商品が必要数だけ在庫として引き当てられるか」を問い合わせるサービスです。

画面の「在庫確認」ボタンから呼ばれ、注文に含まれる全商品ぶんの在庫状況をまとめて返します。ローカルのテスト環境では、商品数が数個のときは問題なく動いています。

対象: [`bad/WarehouseStockService.java`](bad/WarehouseStockService.java)

「どこが問題か、どう直すべきか」をレビューしてみてください。

> ヒント代わりの問い：もし WMS 側が一時的に重くなって、1回の応答に30秒かかるようになったら、このボタンを押したユーザーとサーバーには何が起きるでしょう？また、注文に商品が50個入っていたら？

---

## ❌ NGポイント (bad/ 配下)

1. **タイムアウト未設定 → スレッド枯渇（今回の主役／信頼性）**
   `new RestTemplate()` はタイムアウトを設定していない。WMSが遅くなると、応答が返るまで担当スレッドがブロックされ続ける。Webサーバー（Tomcat）のスレッド数には上限（デフォルト約200）があり、リクエストごとに1本を占有する。WMS遅延が重なると全スレッドが待ちで埋まり、**在庫確認と無関係なページまで含めてアプリ全体が応答不能**になる（＝カスケード障害）。「速く諦める」ために接続/読み取りタイムアウトを必ず設定する。

2. **1商品=1リクエストの逐次呼び出し（外部API版N+1／パフォーマンス）**
   `for` ループ内で商品ごとに同期HTTP呼び出しをしている。50商品なら50往復を順番に待つ（1回0.5秒でも計25秒）。第2問・第13問のN+1と同じ構造。**まず相手にバルク（一括）APIがないか確認し、あれば1回にまとめる**。無ければ並列化（同時実行数を制限して）を検討する。

3. **例外の握りつぶし＋continueで失敗を黙殺（例外処理）**
   `catch (Exception e) { continue; }` で、失敗した商品は `results` に入らず**黙って消える**。呼び出し元は「在庫あり/なし/確認失敗」を区別できず、**在庫が無い（確認できていない）のに注文を通す**業務事故につながる。原因も記録されずデバッグ不能。

4. **`getForObject` の戻り値 null 未チェック → NPE（例外処理）**
   `getForObject` は例外を出さずとも `null` を返し得る。直後に `response.getAvailableQuantity()` を呼ぶと NullPointerException。しかもその NPE は同じ `catch` に拾われて 3. の黙殺に合流する。null は「想定外の例外」ではなく「想定内の分岐」として先に処理すべき。

5. **URLの文字列連結（セキュリティ／堅牢性）**
   `WMS_URL + "?code=" + item.getProductCode()` は、商品コードに `&` や空白・日本語など特殊文字が入るとURLが壊れる／意図しないパラメータ注入になり得る。クエリを手組みせず、`UriComponentsBuilder` でエンコードするか、値を本文(body)に載せて送る。

6. **RestTemplate を new 直書き（テスト容易性・DI）**
   メソッド内で `new RestTemplate()` すると、テスト時に偽物（モック）へ差し替えられず「WMSが遅い/落ちた」ケースを検証できない。第8問・第12問と同じ「new直書きはテスト不能」。外部依存はコンストラクタで注入する。

7. **URLのハードコード（設定の外部化）**
   エンドポイントを定数で直書きすると、開発/検証/本番で切り替えられない。`@Value` + `application.yml` で外部化する（第14問と同系）。

## ⭕️ 改善案 (good/ 配下)

1. **タイムアウト済み RestTemplate を Bean 化**（[`RestTemplateConfig.java`](good/RestTemplateConfig.java)）
   `RestTemplateBuilder` で接続/読み取りタイムアウトを設定した `RestTemplate` をアプリに1個だけ用意し、各サービスへDIする。設定が一箇所に集約され、待ち過ぎを防げる。

2. **一括問い合わせに集約**（[`WarehouseStockService.java`](good/WarehouseStockService.java)）
   全商品を1つのリクエストにまとめ、1回のHTTPで済ませる（N+1解消）。値は本文(JSON)に載せるため、URL文字列連結のエスケープ問題も同時に解消。

3. **状態を区別して返す**（[`StockStatus.java`](good/StockStatus.java) / [`StockResult.java`](good/StockResult.java)）
   `AVAILABLE`（引当可）/`SHORTAGE`（在庫不足＝確実な情報）/`CHECK_FAILED`（確認できなかった＝情報無し）をenumで区別。第16問の「状態はenumで」の実践。**1件も取りこぼさない**。

4. **例外を握りつぶさず伝える**（[`StockCheckException.java`](good/StockCheckException.java)）
   HTTP失敗は原因例外(cause)ごと専用例外に包んで上位へ。Controller側で 503 を返すなど適切に対処でき、原因も追える。

5. **null応答を明示的に処理**
   `postForObject` の戻り値が null / entries が null のケースを「確認できなかった異常」として先に分岐。予期せぬNPEを想定内の扱いに変える。

6. **依存とURLをすべて外部化**
   `RestTemplate` はコンストラクタ注入、URLは `@Value("${wms.stock-bulk-url}")` で設定ファイルから注入。テスト可能かつ環境切替可能に。

> 📌 補足（バルクか並列か）: 一括APIは相手(WMS)が対応している必要がある。DBと違い外部APIは他社の持ち物なので、こちらの都合でまとめられない場合がある。その際は「同時実行数を絞った並列呼び出し（`CompletableFuture` など）」で逐次待ちを解消する。優先順位は **①バルクAPI確認 → ②無ければ並列化**。さらに堅牢にするなら **リトライ**（一時的失敗の再試行）や **サーキットブレーカー**（連続失敗時に一定時間呼び出しを止めて相手と自分を守る仕組み）も検討する。

## 💬 レビューコメント例文

> WarehouseStockService、機能としては動いていますが、外部連携ならではのリスクがいくつか隠れているので一緒に潰しましょう。
>
> まず最優先で **RestTemplate のタイムアウト**をお願いします。いまタイムアウト未設定なので、WMSが重くなると応答待ちでリクエスト処理スレッドが埋まり、最悪アプリ全体が巻き添えで応答不能（カスケード障害）になり得ます。`RestTemplateConfig` でタイムアウト済みの Bean を用意して、コンストラクタで受け取る形にしましょう。ついでに `new RestTemplate()` を卒業できるので、テストでモックに差し替えられるようになります。
>
> 次に、ループ内で商品ごとに1回ずつ叩いている点です。50商品だと50往復を順番に待つことになるので、まず WMS に一括問い合わせのAPIがないか確認してもらえますか？あれば1回にまとめられます（DBのN+1をまとめるのと同じ発想です）。
>
> 最後に例外処理まわり。`catch (Exception e) { continue; }` だと、確認に失敗した商品が結果から黙って消えてしまい、呼び出し元が「在庫あり」と誤解しかねません。「在庫不足」と「確認できなかった」を別の状態として返し、HTTP失敗は握りつぶさず上位へ伝える形にしたいです。`getForObject` は null を返すこともあるので、そこも先にチェックしておくと安心です。
>
> どれも「外部は遅くなる・落ちる・変な値を返す」前提に立つと自然に出てくる対策です。ここを押さえられると外部連携のコードがぐっと堅くなりますよ。
