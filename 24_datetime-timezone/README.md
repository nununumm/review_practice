# 第24問：サブスクリプションの月次請求バッチ

**📅 出題日**: 2026年9月6日

## 📋 レビュー課題

月額制サービス（サブスクリプション）の請求を担当するサービスです。

- `billDueSubscriptions()`: 毎日0時に動く日次バッチ。請求日を迎えた契約に対して請求書（Invoice）を作り、次回請求日を進めて、利用者にメールで知らせる。無料お試し期間（7日）の間は請求しない。
- `reserveCancel()`: 管理画面から「解約予定日」（例: `"2026-10-01"`）を文字列で受け取って契約に登録する。

なお、`reserveCancel()` は Web の管理画面から呼ばれるため、日次バッチと**同時に動くことがあります**。

対象: `bad/SubscriptionBillingService.java`

「どこが問題か、どう直すべきか」をレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

### 【日付・時刻】このお題の主役

1. **`static final SimpleDateFormat` を複数スレッドで共有している**
   `SimpleDateFormat` は内部に「計算途中のメモ帳」を持つ**可変・非スレッドセーフ**なクラス。日次バッチと管理画面（`reserveCancel`）が同時に触ると、`ParseException` / `NumberFormatException` で落ちるか、**もっと怖いことに「別の契約の日付」が静かに混ざる**。`static` はそれを「アプリ全体で1個」にしてしまう決定打。

2. **「次回請求日 = 30日後」は月次課金ではない**
   1月1日 → 1月31日 → 3月2日…と、月をまたぐたびに請求日が前へズレる。1年で5日以上ズレ、**「今月2回請求された」**というクレームになる。月額サービスの請求日は「翌月の同日」であるべき。

3. **タイムゾーンをどこにも指定していない**
   `new Date()` も `SimpleDateFormat` も `@Scheduled(cron)` も、**JVMが動くサーバーのデフォルトTZ**に黙って従う。本番が海外リージョン／Docker（UTC）だと、日本時間10月1日朝の請求が `2026-09-30` として記録され、**9月分の請求が2回・10月分が0回**という会計事故になる。しかも開発機（JST）では再現しない。

4. **「請求日」に時刻成分が入っている**
   `new Date(today.getTime() + 30日)` は「日付＋バッチが動いたその瞬間の時刻」を保存する。そのため `before(today)` の判定が**実行時刻に左右され**、当日請求されなかったり翌日に二重で走ったりする。業務上「請求日」に時刻は不要 ＝ `LocalDate` を使うべき。

5. **無料お試し期間をミリ秒の割り算で判定している**
   `(today.getTime() - startDate.getTime()) / (1000*60*60*24)` は `startDate` の時刻成分によって**丸1日ぶれる**。「7日間」という業務ルールをミリ秒計算で表現するのは、読み手にも意図が伝わらない。

### 【トランザクション・信頼性】

6. **`@Transactional` が無い＋冪等性がない**
   請求書を `save()` した直後に落ちると、`nextBillingDate` が進まないまま請求書だけ残る → **翌日もう一度請求される（二重請求）**。バッチは「障害で再実行されるもの」なので、同じ請求日の請求書があればスキップする作り（＝冪等性）が必須。

7. **取り消せない副作用（メール送信）をDB確定前に実行している**
   `save()` を呼んだ時点ではまだコミットされていない。後続で失敗して巻き戻ると、**請求していないのに請求メールだけ届く**。

8. **`catch (Exception e) { e.printStackTrace(); }` で握りつぶし**
   失敗した契約が黙って飛ばされ、**誰も気づかないまま請求漏れが積み上がる**。`printStackTrace` は標準エラー出力に垂れ流すだけで、ログ基盤に載らず検索も追跡もできない。

9. **`reserveCancel()` が失敗しても成功として返る**
   `ParseException` を握りつぶした後、そのまま `save()` に進む。画面には「登録しました」と出るのに解約日は入っていない。`findById().get()` も存在チェック無し。

### 【設計・性能】

10. **`findAll()` で全契約をメモリに載せている**
    100万契約なら100万件を取ってきて99万件を捨てる。絞り込みは**SQL（WHERE句）でやる**のが鉄則。Java側の `filter` / Stream API では DB 負荷は 1ミリも減らない。

11. **解約予定日が請求条件に入っていない**
    解約を予約しても請求が止まらない。

12. **マジックナンバー（7日・30日）と、請求日の文字列保存**
    設定として外に出すべき値がコードに直書き。また `billedAt` を文字列で持つと、並び替え・範囲検索ができず書式ゆれの温床になる。

## ⭕️ 改善案 (good/ 配下)

1. **`java.time` へ全面移行**：`Date`/`SimpleDateFormat` を捨て、日付は `LocalDate`、書式は不変（＝スレッドセーフ）な `DateTimeFormatter` を使う。**「日付」と「瞬間」を型で区別する**（請求日＝`LocalDate`、送信日時＝`Instant`）。
2. **`Clock` をDIで注入**：`LocalDate.now(clock)` にすることで、タイムゾーン明示とテスト容易性が同時に解決する。テストでは `Clock.fixed(...)` で「1月31日」に時間を固定できる。
3. **タイムゾーンを設定として明示**：`@ConfigurationProperties` で `Asia/Tokyo` を外部化し、`@Scheduled(cron = "...", zone = "Asia/Tokyo")` も明示。
4. **請求日は `anchorDay` 基準で月加算**：`plusMonths(1)` ＋ `Math.min(anchorDay, 月の日数)` で、1/31 → 2/28 → **3/31** と正しく戻す。
5. **役割を2クラスに分割**：`SubscriptionBillingBatch`（対象を集めて回す）と `SubscriptionBiller`（1契約＝1トランザクション）。全件を1トランザクションで囲まないことで、1件の失敗が全体を巻き戻さない。同時に、Spring のプロキシ問題（自己呼び出しで `@Transactional` が効かない）も回避できる。
6. **冪等性の担保**：`existsBySubscriptionIdAndBillingDate` で二重請求を防ぐ（DB側にもユニーク制約を張って二重に守る）。
7. **メールは `@TransactionalEventListener(AFTER_COMMIT)`**：DB確定後にだけ送る。
8. **例外はログに文脈付きで残す**：`log.error("... subscriptionId={}", id, e)` で「どの契約が」「なぜ」失敗したかを追える形にする。
9. **入力検証を `reserveCancel` に**：null・形式・過去日をチェックし、失敗は例外として呼び出し側に伝える。`Optional` は `orElseThrow` で。
10. **必要な行だけSQLで取る**：`findIdsDueForBilling`（請求日到来 × ACTIVE × 未解約）を500件ずつ処理。

## 💬 レビューコメント例文

> `SubscriptionBillingService` 拝見しました。処理の流れ自体はきれいなので、日付まわりだけ相談させてください🙏
>
> 1. **`static final SimpleDateFormat SDF`**：`SimpleDateFormat` は内部に状態を持つ非スレッドセーフなクラスで、日次バッチと管理画面の `reserveCancel()` が同時に呼ぶと落ちるか、最悪「別の契約の日付」が混ざります。`java.time` の `DateTimeFormatter` は不変なので、そのまま `static` で共有できます。ここを機に `Date` → `LocalDate` に寄せてしまいませんか？
> 2. **`+ 30日` の次回請求日**：1/1 → 1/31 → 3/2 と月をまたぐたび請求日が前倒しになって、1年で5日ほどズレます。「今月2回引き落とされた」というお問い合わせに直結するので、`plusMonths(1)` ベースにしたいです。1/31契約の人の扱い（2月は28日）だけ仕様を決めさせてください。
> 3. **タイムゾーン**：本番はUTCリージョンなので、いまのままだと請求日が1日前にズレて記録されます。開発機（JST）では再現しないタイプの事故なので、`Clock` をBean化して `Asia/Tokyo` を明示しませんか。ついでに `new Date()` が消えてテストも書けるようになります。
> 4. **`@Transactional` と再実行**：請求書を保存した直後に落ちると `nextBillingDate` が進まず、翌日また請求されてしまいます。1契約＝1トランザクションにして、同じ請求日の請求書があればスキップする形にしたいです。
> 5. **メール送信**：`save()` の直後だとまだコミット前なので、巻き戻ったときに「請求していないのにメールだけ届く」ことがあります。`@TransactionalEventListener(AFTER_COMMIT)` に移しましょう。
>
> あと `findAll()` は契約数が増えると厳しいので、WHERE句で「請求日が来ていて未解約のもの」だけ取る形にお願いします。解約予定日が請求条件に入っていない点も、いまのうちに直しておきたいです。
