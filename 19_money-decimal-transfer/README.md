# 第19問：口座間の送金サービス

**📅 出題日**: 2026年8月11日

## 📋 レビュー課題

ネットバンキングの「振込」機能です。`transfer(fromId, toId, amount)` を呼ぶと、
送金元(`fromId`)の口座から送金先(`toId`)の口座へ `amount` 円を移し、
さらに送金額の 0.5% を手数料として送金元から引きます。

処理は「①送金元から出金 → ②手数料を引く → ③送金先へ入金」の順に進み、
成功したら `true`、失敗したら `false` を返します。一見、ちゃんと動きます。

対象:
- `bad/TransferService.java`
- `bad/Account.java`
- `bad/AccountRepository.java`

「どこが問題か、どう直すべきか」をレビューしてみてください。

> 💡 ヒント無しで挑戦してみてください。すぐ気づく問題から、じっくり考えないと見えない問題まで、
> **複数**潜んでいます。「1万円を送金したら本当にピッタリ1万円動くか？」「途中で例外が起きたら？」
> 「同じ口座に同時に2件の送金が来たら？」——そんな視点で眺めてみると見えてきます。
> （ヒントが欲しくなったら「ヒントちょうだい」と言ってください）

## ❌ NGポイント (bad/ 配下)

1. **【致命的・主テーマ】お金を `double` で計算している**
   `balance` も `amount` も `double`。`double` は「だいたいの数」しか表せず、`0.1 + 0.2` が `0.30000000000000004` になるように**端数がズレる**。手数料 `amount * 0.005` を繰り返し引くと、1円未満のズレが積み重なり、大量取引で会計が合わなくなる。**お金に浮動小数点型（double/float）は厳禁**。

2. **【致命的】`@Transactional` が無く、部分反映が起きる**
   「①出金→②手数料→③入金」を別々に `save()` している。②の直後・③の前で例外が飛ぶと、**送金元だけ減って送金先が増えない**（お金が消える）。一連の操作は1つのトランザクションにまとめ、失敗時は全部ロールバックすべき。

3. **【致命的】lost update（更新の喪失）— 同時送金で残高が壊れる**
   「残高を読む→計算→書き戻す」を Java 側でやっており、同じ口座に同時アクセスが来ると、後の save が前の save を上書きして出金が消える。悲観ロック(`SELECT ... FOR UPDATE`)／楽観ロック(`@Version`)／DBでの原子的UPDATEのいずれかで守る必要がある。

4. **バリデーション欠如**
   金額がマイナス・ゼロでも通る（マイナス送金は「引くつもりが増える」事故）。自分自身への送金も弾いていない。**残高不足チェックも無い**ため残高がマイナスになれる（＝無限に引き出せる）。

5. **`Optional.get()` で存在チェックなし**
   口座が存在しないと `NoSuchElementException` で落ちる。`orElseThrow` で意味のある例外に変換すべき。

6. **例外の握りつぶし＋ `boolean` 返し**
   `catch (Exception e) { e.printStackTrace(); return false; }` は、失敗の**原因情報を捨てて** `false` だけ返す。呼び出し側は「なぜ失敗したか」が分からず、しかもDBが中途半端な状態のまま。意味のある例外を投げて、トランザクションにロールバックさせるべき。

7. **マジックナンバー / `System.out.println`**
   手数料率 `0.005` が直書き。ログも `println` で出力レベル・出力先を制御できない。

## ⭕️ 改善案 (good/ 配下)

1. **残高は `long`（円）で保持**。`double` を排除し、端数ズレを根絶。`int` ではなく `long` で桁あふれも防ぐ。
2. **手数料の丸めを明示**。`BigDecimal` で `amount × 0.005` を計算し、`RoundingMode.FLOOR`（切り捨て）と**明示的に**指定してから `long`（円）に戻す。「なんとなく丸まる」を排除。
3. **`@Transactional` で一連の操作を束ねる**。途中失敗で自動ロールバック。エンティティのダーティチェックに任せ、`save()` の連打も廃止（＝「まとめて保存」の勘が正解）。
4. **悲観ロックで lost update を防止**。`findByIdForUpdate`(`PESSIMISTIC_WRITE`) で口座を押さえてから読み書き。**デッドロック回避のためロック取得順をID昇順で固定**。
5. **バリデーションを追加**。金額>0、送金元≠送金先、残高≥（送金額＋手数料）をチェック。残高チェックはロック中に行うので他者に抜かれない。
6. **意味のある例外を投げる**。`AccountNotFoundException` / `InsufficientBalanceException` / `InvalidTransferException` を用意。これらは `RuntimeException` 系にして `@Transactional` の自動ロールバック対象にする（checked例外は既定でロールバックされない点に注意）。戻り値は `boolean` をやめる。
7. **手数料率を定数化**（さらに設定ファイル外出しが望ましい）／**SLF4Jロガー**を使用。

### 💡 発展：ロックの選択肢
- **悲観ロック**（good/ で採用）: 確実だが待ちが発生。お金が絶対消えてはいけない送金向き。
- **楽観ロック**（`@Version`）: 衝突が稀な前提で速いが、衝突時のリトライ処理が要る。
- **DBでの原子的UPDATE**: `UPDATE account SET balance = balance - :total WHERE id = :id AND balance >= :total` の1文で「残高チェック＋出金」を割り込み不能にする最も軽量な手。ユーザーの「一行で引く」案がこれに相当。

## 💬 レビューコメント例文

> 送金ロジック、`@Transactional` を付けて出金と入金を1トランザクションにまとめましょう。今のままだと②手数料の後・③入金の前で例外が出たとき、送金元だけ減ってお金が消えてしまいます。あと残高を `double` で持っているのが要注意で、`double` は端数がズレるためお金には使えません（`0.1+0.2` が `0.3` にならない例が有名です）。残高は `long`（円）にして、手数料の 0.5% だけ `BigDecimal` + `RoundingMode` で丸めを明示するとキレイです。もう一点、同じ口座に同時送金が来たときの lost update 対策として、`SELECT ... FOR UPDATE`（悲観ロック）で口座を押さえてから残高チェック→更新に入ると安全です。最後に、失敗時は `false` を返すのではなく `InsufficientBalanceException` のような意味のある例外を投げると、原因も追えるしトランザクションのロールバックも効きます。バリデーション（金額>0・自己送金禁止・残高不足）も忘れずに👍
