# 第13問：ブログ記事一覧を著者名つきで返すサービス（パフォーマンス）

**📅 出題日**: 2026年7月19日

## 📋 レビュー課題

ブログの記事一覧を返す `ArticleService` です。
画面には「記事タイトル」と「その記事を書いた著者の名前」を並べて表示したいので、
記事を全部取ってきて、1件ずつ著者名を付けて返しています。

ローカルの開発DB（記事が数件だけ）で動かすと、一覧はちゃんと著者名つきで返ってきて、
一見きちんと動いています。

対象: `bad/ArticleService.java`

このコードを、記事が何万件もある本番DBに出す前提で、
「どこが問題か・どう直すべきか」をレビューしてみてください。
今回は特に **「データが増えたときに耐えられるか（パフォーマンス）」** の観点で見てみましょう。

---

## ❌ NGポイント (bad/ 配下)

1. **N+1問題（最重要・パフォーマンス）**: `findAll()` で記事を1回取得したあと、for ループの中で `userRepository.findById(...)` を毎回呼んでいる。記事がN件あると **1（記事の取得）+ N（著者の取得）回** のDBアクセスが発生する。記事1万件なら 10,001回。ローカル（数件）では気づけないが、本番では応答が激遅になりDBを圧迫する。これが「N+1問題」。
2. **全件取得（ページングなし）**: `findAll()` は全記事をメモリに載せる。件数が増えるとメモリ枯渇・レスポンス肥大を招く。一覧は「1ページ分ずつ」取得すべき。
3. **フィールドインジェクション（テスト容易性）**: `@Autowired` をフィールドに直接付けている。テスト時にモック（偽物）を差し込みにくく、`final` にもできない。コンストラクタインジェクションにすべき。
4. **`Optional#get()` の無防備な呼び出し（例外処理）**: `userRepository.findById(...).get()` は、著者が見つからないと `NoSuchElementException` を投げる。データ不整合時にどう振る舞うかが設計されていない。
5. **Entity をそのまま扱う設計**: 表示に必要なのは3項目だけなのに Entity を引き回している。表示用DTOに必要な項目だけ詰めるのが筋（第4問の復習）。

## ⭕️ 改善案 (good/ 配下)

1. **JOIN + DTOプロジェクションで1クエリ化**: `SELECT new ...ArticleDto(a.id, a.title, u.name) FROM Article a, User u WHERE a.authorId = u.id` のように、記事と著者をDB側で結合し、結果を直接DTOに詰める。DBアクセスは**1回**に激減（N+1の解消）。
2. **`Pageable` でページング**: サービス／リポジトリが `Pageable` を受け取り、`Page<ArticleDto>` を返す。全件ではなく1ページ分だけ取得。
3. **コンストラクタインジェクション**: `@Autowired` を排し、コンストラクタで依存を受け取り `final` 化。テストではモックを `new` で渡せる。
4. **DTOは不変（setterなし）**: コンストラクタで組み立て、生成後は書き換えられない安全な入れ物にする。

> 💡 別解（B案）: 記事を取得 → 著者IDをまとめて `findAllById(ids)` で一括取得 → `Map<著者ID, User>` に入れてループ内はマップ参照、という方法でもN+1を解消できる（DBアクセス2回）。「マップを使う」というレビュー時の直感はこちらで活きる。今回は最もシンプルなA案（JOIN 1クエリ）を模範解答とした。

## 💬 レビューコメント例文

> ロジック自体はきれいに書けていて、やりたいことはすぐ理解できました 👍
> 一点だけ、本番のデータ量を想定して相談させてください。いまループの中で `userRepository.findById()` を著者ごとに呼んでいますが、これは記事がN件だとDBへの問い合わせが「1 + N回」に膨らみます（いわゆるN+1問題）。ローカルだと数件なので気づきにくいのですが、本番で記事が数万件になると一覧表示がかなり重くなりそうです。
> 記事と著者をDB側でJOINして1クエリで取り、必要な3項目だけをDTOに詰める形にすると、アクセスが1回で済んでスッと速くなります。あわせて一覧はページング（20件ずつ等）にしておくと、件数が増えても安心です。
> ついでに、依存はコンストラクタで受け取る形にするとテストでモックが差し込みやすくなるので、そこも直せると◎です。一緒に直し方を見てみましょう！
