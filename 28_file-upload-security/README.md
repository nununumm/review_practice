# 第28問：プロフィール画像アップロードサービス

**📅 出題日**: 2026年9月20日

## 📋 レビュー課題

Webアプリの「プロフィール画像（アバター）アップロード」機能です。
ユーザーが送ってきた画像ファイルをサーバーのディスクに保存し、その保存先パスを
ユーザー情報（`User`）に紐づけて更新します。保存したパスを戻り値で返します。

一見すると「ファイルを受け取って保存してDBを更新するだけ」の素直なコードに見えますが、
外部（＝ユーザー）から送られてくるファイルを扱う処理には、実は複数の落とし穴が潜んでいます。

対象: `bad/AvatarService.java`
「どこが問題か、どう直すべきか」をレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

1. **パストラバーサル（最重要）**: `"/var/www/uploads/avatars/" + file.getOriginalFilename()` と、ユーザーが名付けたファイル名をそのまま保存パスに文字列連結している。ファイル名を `../../../etc/cron.d/evil` のようにすれば、保存フォルダの外の任意の場所にファイルを書き込める。設定ファイルやcronの上書きでサーバー乗っ取りに直結する。
2. **無制限アップロード（種類の検証なし）**: 拡張子・MIMEタイプ・中身（マジックバイト）を一切検証しない。「画像アップロード」のはずが `.jsp` や `.sh` などの実行可能ファイルもそのまま保存でき、リモートコード実行の温床になる。
3. **サイズ上限なし**: 巨大ファイルをそのまま受け入れ、ディスクを埋め尽くされる（DoS）。
4. **リソースリーク**: `InputStream in` を一度も `close()` していない。さらに `out.close()` は正常時にしか到達せず、コピー途中で例外が飛ぶと閉じられない。ファイルハンドルが漏れ続け、いずれファイルを開けなくなる。
5. **ファイルとDBの整合性なし**: ディスクへの保存とDB更新（`userRepository.save`）が別々の資源への操作なのに `@Transactional` もなく、順序・後始末の考慮もない。DB更新に失敗すると「DBにパスはあるのに実ファイルが無い」リンク切れが起きうる。
6. **同名衝突で上書き**: ユーザーのファイル名をそのまま使うため、別ユーザーが同名ファイルを送ると既存のアバターを上書きしてしまう。
7. **入力チェック欠如**: `file` の null / 空（0バイト）チェックがなく NPE や空ファイル保存を招く。
8. **設定のハードコーディング**: 保存先パスを直書き。環境（開発/本番、OS）が変わると動かない。
9. **存在チェックなし**: `userRepository.findById(userId).get()` はユーザーが存在しないと `NoSuchElementException`。
10. **例外の握りつぶし＋return null**: `catch (Exception e)` で全部握りつぶし `printStackTrace` → `null`。呼び出し側は成否も原因も分からない。
11. **内部パスの情報漏洩**: サーバー内部の絶対パス（`/var/www/...`）を戻り値としてクライアントに返している。

## ⭕️ 改善案 (good/ 配下)

1. **ファイル名は自前生成（UUID）**: ユーザー由来のファイル名を捨て、`UUID.randomUUID() + 拡張子` でサーバーが命名。`../` が入り込む余地をなくし、同名衝突も同時に解消。
2. **保存パスの正規化チェック（多層防御）**: 組み立てたパスを `normalize()` して `..` を解決し、`target.startsWith(baseDir)` で基準フォルダ内に収まっているか最終確認。
3. **検証は許可リスト方式**: サイズ上限・許可する Content-Type（JPEG/PNG）を明示的にチェック。禁止リストではなく「許可したものだけ通す」。
4. **try-with-resources**: `in`・`out` を `try(...)` 内で開き、成功でも例外でも確実に閉じる。手書きコピーループは `in.transferTo(out)` に置換。
5. **整合性は順序＋補償で守る**: 先にファイル保存 → 最後にDB更新（`@Transactional`）。DB更新失敗時は置いたファイルを削除して後始末。DBとファイルシステムは1トランザクションに一体化できない前提を踏まえ「傷を最小化」する。
6. **設定の外部化**: 保存先・上限・許可タイプを `@ConfigurationProperties` で `application.yml` から注入。
7. **存在チェックは orElseThrow**: `findById(...).orElseThrow(...)` で意味のある例外に。
8. **例外を投げる**: return null をやめ、専用の `InvalidFileException` を投げて呼び出し側（例外ハンドラ）が適切なHTTPステータスに変換できるようにする。ログは `printStackTrace` でなくロガーへ。
9. **返すのは公開用ファイル名のみ**: 内部の絶対パスは隠し、DBにもファイル名だけを保持する。

## 💬 レビューコメント例文

> アバターアップロード、機能としては動いていますね！ ただ「外部から来るファイルを扱う」処理なので、いくつか一緒に固めておきたい点があります。
>
> 一番大事なのが21行目で、送られてきた `getOriginalFilename()` をそのまま保存パスに連結している点です。ここはファイル名を `../` 付きで細工されると保存フォルダの外に書き込めてしまうので（パストラバーサル）、**ファイル名はUUIDでこちら側が付け直す**方式にしませんか。そうすると同名で他ユーザーのファイルを上書きする問題も一緒に消えて一石二鳥です。あわせて、保存前に**サイズ上限と画像タイプ（JPEG/PNGの許可リスト）**のチェックも入れたいです。画像のつもりでも実行ファイルが届く可能性があるので。
>
> あと2点だけ。`InputStream` が閉じられていない＆例外時に閉じ漏れるので **try-with-resources** に。それと、ファイル保存とDB更新は別々の資源なので、**先にファイル→最後にDB(@Transactional)**、DB失敗時はファイルを消す、の順にすると片方だけ成功する事故を防げます。
>
> どれも「動くけど本番でジワジワ効いてくる」タイプの話なので、ここで潰しておけると安心です。一緒に直していきましょう！
