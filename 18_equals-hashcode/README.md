# 第18問：発行済みクーポンの二重発行チェック

**📅 出題日**: 2026年8月11日

## 📋 レビュー課題

「同じクーポンコードは二度と発行しない」ためのサービスです。
発行したクーポンを `Set`（＝重複を許さない入れ物）に溜めておき、発行前に「もう持っているか？」をチェックして、二重発行を防いでいる…つもりのコードです。

たとえば `issue("SUMMER2026", 500)` を2回呼んだら、2回目は「すでに発行済みです」となって枚数は1枚のまま——というのが期待する動きです。

対象:
- `bad/CouponService.java`
- `bad/Coupon.java`

「どこが問題か、どう直すべきか」をレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

1. **【致命的】`equals()` / `hashCode()` 未実装で、重複チェックが常にすり抜ける**
   `Coupon` クラスに `equals()` / `hashCode()` を書いていないため、`HashSet` は `Object` クラスのデフォルト挙動（＝「メモリ上の同じ場所にある同一オブジェクトか」で比較）を使ってしまう。
   `new Coupon("SUMMER2026", 500)` を2回作ると、中身は同じでも**別々のアドレスに作られた別オブジェクト**なので、`contains()` は必ず `false`。結果、「発行済みチェック」は永遠に働かず、**同じクーポンが何度でも発行できてしまう**。コンパイルは通り例外も出ないので、静かに仕様が壊れる（最もタチが悪いバグ）。

2. **値オブジェクトなのに可変（setter を全公開）**
   `Coupon` は「クーポンの内容」を表す値。それなのに `setCode()` / `setDiscountAmount()` で後から書き換えられる。もし `HashSet` に入れた後で `code` を変えると、`hashCode()` が変わって**二度と取り出せない迷子オブジェクト**になる（HashSetの整合性が壊れる典型パターン）。値オブジェクトは不変(immutable)にするのが鉄則。

3. **`System.out.println` でログ出力**
   出力レベル・出力先・フォーマットを制御できず、本番運用に耐えない。SLF4J などのロガーを使うべき（第7問・第11問と同じ観点）。

4. **重複チェックが `contains()` → `add()` の二度手間**
   ハッシュ計算を2回走らせているうえ、意図も散らばる。`Set.add()` は「追加できたか」を戻り値で教えてくれるので1手で書ける。

## ⭕️ 改善案 (good/ 配下)

1. **`Coupon` に `equals()` / `hashCode()` を実装**（`code` と `discountAmount` で「同じ」を判定）。これで `HashSet` が「中身が同じ＝同じクーポン」と正しく判断できる。
2. **`Coupon` を不変にする**：`final class` ＋ フィールド `final` ＋ setter廃止。生成後は中身が変わらないので、Setの整合性が壊れない。
3. **`equals` と `hashCode` は必ずセットで実装**（equals/hashCodeの「契約」）。片方だけだとハッシュ系コレクションが壊れる。
4. **ロガー(SLF4J)を使用**。
5. **`Set.add()` の戻り値で重複判定**し、`contains`+`add` を1手にまとめる。

### 💡 もっと良くする（発展）
- **Java 16以降なら `record` が最適解**。`public record Coupon(String code, int discountAmount) {}` と書くだけで、不変・`equals`・`hashCode`・`toString` を**コンパイラが自動生成**してくれる。今回手書きした内容がまるごと1行になる。
- **「同一性」の定義は業務で決まる**。今回は「code+割引額が同じなら同じ」としたが、「クーポンコードこそが唯一の識別子」という業務なら、`equals` を `code` だけで判定する、あるいはそもそも `Set<String>`（コードの集合）や `Map<String, Coupon>`（コードをキー）で持つほうが素直。**何をもって"同じ"とするかを最初に決める**のが設計の勘所。

### 🏢 現場ではどうするか（ユーザー指摘：DB管理について）
今回の `good/` は equals/hashCode の学習に集中するため、あえてメモリ(`Set`)で管理している。だが**指摘のとおり、本番では発行済み情報はDBで永続化すべき**：
- メモリ管理だと**再起動で消える**／**サーバ複数台だと各台バラバラ**になり、重複チェックが破綻する。
- 実際は `coupons` テーブルに `code` を **UNIQUE制約**で持たせ、`existsByCode(code)` で判定、枚数は `count()` で取る、という形になる。
- ただし「DBのユニーク制約 + アプリ側の判定」でも、真の二重発行防止は最終的に**DBのUNIQUE制約（＝DBレベルの一意保証）**が守ってくれる点は覚えておくとよい（アプリ側チェックだけだと、同時アクセス時にすり抜けうる＝第10問の観点）。

## 💬 レビューコメント例文

> クーポンの二重発行チェック、`HashSet` で管理する方針いいと思います👍 一点だけ、`Coupon` に `equals()` / `hashCode()` が無いので、今のままだと `contains()` が中身ではなく“同じインスタンスか”で比較してしまい、`new` するたびに別物扱いになって重複チェックがすり抜けてしまいます（コンパイルは通るぶん気づきにくいやつです）。`code` と割引額で `equals`/`hashCode` を実装するか、Java 16+なら `record Coupon(...)` にすると不変性込みで一気に解決できます。あと `Coupon` は値オブジェクトなので setter は無くして不変にしておくと、Setに入れた後の事故も防げて安心です。ログは `System.out` ではなく SLF4J に寄せておきましょう。
