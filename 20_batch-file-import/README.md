# 第20問：商品マスタCSVの一括取り込み

**📅 出題日**: 2026年8月23日

## 📋 レビュー課題

運用担当者がアップロードした「商品マスタCSV」を読み込み、商品テーブルに一括登録するバッチ処理です。

- CSVは1行1商品で、`商品コード,商品名,価格,在庫数` の形式。
- 1日1回、深夜バッチから `importProducts(filePath)` が呼ばれます。
- ファイルを読み込み、1行ずつ `Product` にして保存し、「〇件の商品を登録しました」と返します。

一見すると素直に動きそうですが、**大量データを扱うバッチ処理**として、また**ファイルを触る処理**として、現場に出すには危ういところがいくつも潜んでいます。

対象: `bad/ProductImportService.java`

「どこが問題か、どう直すべきか」をレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

### 【主題・最重要】ファイルを閉じていない（リソースリーク）
`new BufferedReader(new FileReader(filePath))` で開いたファイルを、どこでも `close()` していない。ファイルを開くとOSは「ファイルハンドル」という**数に上限のある資源**を貸し出す。返さない（閉じない）と枠が埋まり続け、いつか **`Too many open files`** でシステム全体が止まる。しかも「昨日は動いていたのに突然」という追いにくい壊れ方をする。Windowsでは開いたままのファイルは**他プロセスが削除・移動できない（ロック）**ため、取り込み済みCSVの退避運用も失敗する。
さらに悪いことに、`parseInt` が例外を投げると `catch` に飛んで**閉じないままメソッドを抜ける**。エラー時こそ確実に閉じたいのに、真っ先に閉じ忘れる作りになっている。

### 全行をメモリに読み込んでいる（大容量でOOM）
`List<String> lines` にファイルの全行をいったん貯めてからループしている。数十万〜数百万行のCSVが来ると、この時点で**メモリを食いつぶして `OutOfMemoryError`** で落ちる。バッチは大量データを想定すべきで、「1行ずつ読んで1行ずつ処理する（ストリーミング）」のが基本。

### トランザクション境界がない（部分取込・再実行不能）
`@Transactional` が無く、ループ内で1件ずつ `save()` している。3000行の2500行目で例外が出ると、**1〜2499件はDBに残ったまま**、メソッドは「取り込みに失敗しました」を返す。＝**「失敗」と言っているのにDBは中途半端**。翌日もう一度流すと重複登録の恐れもあり、リカバリが困難。「全部成功か、全部なかったことにする（ロールバック）」を保証すべき。

### 1件ずつ save（バッチ化なし・性能）
`save()` を1行ごとに呼ぶと、1万件で**1万回のDB往復**が発生し非常に遅い。`saveAll` でまとめて登録し、往復回数を減らすべき（＋Hibernateの `hibernate.jdbc.batch_size` 設定でSQLレベルもまとめる）。

### 例外の握りつぶし＆フェーズの混同
`catch (Exception e) { e.printStackTrace(); return "..."; }` は、原因（スタックトレース）を標準出力に流すだけで**呼び出し側に何も伝えない**。「成功/失敗」「失敗なら何行目で何が」が消える。しかも `try` が**ファイル読み込みからDB登録まで丸ごと**囲っているため、**「ファイルが読めなかった」のか「DB登録でコケた」のか区別できない**。例外は握りつぶさず、フェーズごとに意味のある例外として投げて伝えるべき。

### バリデーション欠如／ヘッダ行スキップなし
- `cols[3]` まで無条件でアクセス → 列が足りない行で `ArrayIndexOutOfBoundsException`。
- `Integer.parseInt(cols[2])` → 数値でない値で `NumberFormatException`（しかも何行目か分からない）。
- 価格・在庫の**負数チェックなし**。
- **1行目（ヘッダ＝列名）をスキップしていない** → 列名がそのまま商品として登録される（`parseInt("価格")` で落ちる）。

### `split(",")` の素朴処理
値の中にカンマを含むCSV（例 `"1,000"`、住所など）が来ると列がずれて壊れる。本番はCSVライブラリ（OpenCSV / Apache Commons CSV）でクォート・エスケープを正しく扱うべき。

### 文字コード未指定（環境依存の文字化け）
`FileReader` は**プラットフォーム既定の文字コード**を使う。開発環境と本番環境で既定が違うと、日本語商品名が文字化けする。`UTF-8` のように明示すべき。

## ⭕️ 改善案 (good/ 配下)

1. **try-with-resources** で開いたファイルを正常時も例外時も自動close（`Files.newBufferedReader(path, UTF_8)`）。
2. **1行ずつ処理**し、`BATCH_SIZE`件ごとに `saveAll` → バッファを `clear`。メモリ一定・DB往復も削減。
3. **`@Transactional`** を付与。`CsvImportException`（RuntimeException）を投げれば途中登録分も自動ロールバック＝「全部か無か」。
4. **例外は投げて伝える**。返り値は `int`（登録件数）にし、失敗時は行番号つきで throw。ファイル読み込み失敗（`IOException`）とデータ不正（`CsvImportException`）を区別。
5. **ヘッダ行スキップ・列数/数値/負数チェック**を追加。マジックナンバーは定数化。
6. **文字コードをUTF-8で明示**。

### 発展（今回の good/ では踏み込まない設計論点）
- **冪等性（同じCSVを2回流しても壊れない）**：商品コードで検索し「無ければINSERT・有ればUPDATE」する upsert 設計にすると、再実行しても安全。マスタ更新バッチでは有力な選択肢（レビューで挙がった着眼点）。
- **超大容量ファイル**：`saveAll` を重ねると永続化コンテキスト（JPAが抱える管理対象）が膨らむため、チャンクごとに `flush()` + `clear()`、あるいはJDBCバッチ/ `COPY` などの検討も。

## 💬 レビューコメント例文

> CSV取り込みお疲れさまです！ロジックの流れは分かりやすいです。本番に出す前に、バッチ処理ならではの観点で何点か一緒に固めたいです。
>
> 1. **ファイルのclose**：`BufferedReader` が閉じられていないようです。特に途中で例外が出ると閉じ忘れてファイルハンドルが漏れ、繰り返すと `Too many open files` になりがちです。`try-with-resources` にすると成功／失敗どちらでも自動で閉じてくれるので安全です。
> 2. **途中失敗時のDB状態**：今は1件ずつ保存していて `@Transactional` が無いので、途中の行でコケると「一部だけ登録済み」で終わってしまいます。メソッドに `@Transactional` を付けて「全部成功 or 全部ロールバック」に揃えませんか？
> 3. **例外の扱い**：`printStackTrace` + 文字列returnだと、呼び出し側から見て失敗の原因や失敗行が分かりません。行番号を添えて例外として投げ直すと、運用でのリカバリがぐっと楽になります。
>
> あわせて、全行を `List` に貯めている点（大容量でメモリ懸念）、`save` の1件ずつ呼び出し（`saveAll` で往復削減）、ヘッダ行スキップと数値チェック、文字コード指定あたりも直せると安心です。どれも定番の型なので、この機会に一緒に押さえていきましょう💪
