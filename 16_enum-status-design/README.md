# 第16問：注文ステータスの管理

**📅 出題日**: 2026年8月2日

## 📋 レビュー課題

ECサイトの「注文（Order）」のステータスを管理するサービスです。注文は **新規受付 → 支払い済み → 発送済み → 配達完了** と進んでいき、途中でキャンセルされることもあります。

この `OrderStatusService` は、
- 支払い完了時にステータスを進める（`markAsPaid`）
- 発送時にステータスを進める（`ship`）
- 画面に出す日本語ラベルを返す（`getStatusLabel`）
- キャンセル可能かを判定する（`canCancel`）

という、注文まわりでよくある処理をまとめています。

対象: `bad/OrderStatusService.java` / `bad/Order.java`

一見ふつうに動きそうに見えますが、**このまま人数の多いチームで開発を続けると、地味だけど厄介なバグが必ず出てくる**書き方になっています。実際に `markAsPaid` の後に `ship` を呼ぶと、想定どおりに動かない箇所もあります。

「どこが問題か、どう直すべきか」をテックリード目線でレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

1. **`ship` の `==` による文字列比較（致命的バグ）**: `order.getStatus() == "PAID"` は「中身が同じか」ではなく「メモリ上の同じオブジェクトか」を比べる。文字列は `==` でたまたま true になることもあり、**テストでは通るのに本番で落ちる“気まぐれバグ”**になる。文字列の中身比較は必ず `.equals()`。

2. **`"PAYED"` という綴りミス（課題文のバグの正体）**: `markAsPaid` は `setStatus("PAYED")` としているのに、`ship` は `"PAID"` を待っている。**綴りが違うので永遠に一致せず、支払い後に発送できない**。文字列で状態を持つと、コンパイラがこの打ち間違いを検知できない。

3. **マジックストリングでの状態管理（根本原因）**: `"NEW"` `"PAID"` などを各所に直書きしているため、①表記ゆれ（PAID/PAYED/paid）、②タイプミス、③「取りうる状態の一覧」がコード上どこにも定義されていない、という問題が生まれる。状態が増減したときに直し漏れが起きやすい。

4. **`println` での“素通り”処理**: 進めない状態のとき `System.out.println` で表示するだけで処理を続けてしまう。出力先やレベルを制御できない上に、**呼び出し元が成功/失敗を判断できない**。支払い前の注文を発送してしまう事故に気づけない。

5. **判定ロジックの分散**: 表示ラベル（`getStatusLabel` の長い if-else）やキャンセル可否（`canCancel`）の判定が、状態そのものではなくサービス側に散らばっている。状態を1つ増やすたびに複数箇所を直す必要がある。

## ⭕️ 改善案 (good/ 配下)

1. **`String` → `enum OrderStatus` にする**: 取りうる状態を `NEW / PAID / SHIPPED / DELIVERED / CANCELLED` として型で固定。**存在しない状態はコンパイルエラーで書けなくなる**ので、綴りミス・表記ゆれが原理的に消える（NG 2・3を同時に解決）。

2. **比較は enum の `==` で行う**: enum の値はプログラム全体で1つだけ存在する“シングルトン”なので、`==` が正しく・null 安全に使える。**「文字列は `.equals()`／enum は `==`」**がセットの学び。enum 化した瞬間に NG 1 も消える。

3. **進めないときは例外を投げる**: `println` で素通りせず `IllegalOrderTransitionException` を投げて処理を止める。呼び出し元・上位ハンドラが確実に異常を検知できる。成功時の記録は SLF4J のロガー（`log.info`）で残す（NG 4 を解決）。

4. **表示ラベル・キャンセル可否を状態自身に持たせる**: `OrderStatus#getLabel()` / `OrderStatus#isCancellable()` にロジックを寄せ、サービスの if-else を排除。状態を増やしても enum 1箇所の修正で済む（NG 5 を解決）。

## 💬 レビューコメント例文

> ステータスまわり、丁寧に書けていて処理の流れは追いやすいです 🙆‍♂️ ひとつ、`ship` の `order.getStatus() == "PAID"` だけ相談させてください。Java の文字列比較は `==` だと中身ではなくメモリ上の同一性を見てしまうので、`.equals()` が安全です。あわせて `markAsPaid` 側が `"PAYED"` になっていて `ship` の `"PAID"` と綴りが食い違っており、支払い後に発送へ進めない状態になっていそうです。
>
> 根っこの話をすると、ステータスを文字列で持っているとこの手の打ち間違い・表記ゆれをコンパイラが弾けないのが痛いところです。思い切って `enum OrderStatus` にしてしまうと、存在しない状態はそもそも書けなくなり、比較も `==` で安全に書けます。表示ラベルやキャンセル可否も enum 側に持たせると、状態が増えたときの直し漏れも防げます。進めない状態のときは `println` ではなく例外にして、成功時はロガーに残す形にすると呼び出し元も異常に気づけて安心です。良ければ次のリファクタで一緒にやってみましょう 💪
