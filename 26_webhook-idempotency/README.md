# 第26問：決済Webhookの受信処理

**📅 出題日**: 2026年9月19日

## 📋 レビュー課題

決済プロバイダ（外部サービス）からの「入金完了」通知（Webhook）を受け取るエンドポイントです。
通知を受けると、対象の注文を支払い済みにし、購入額に応じてポイントを付与し、確認メールを送信します。
決済プロバイダは、成功レスポンス（2xx）を受け取るまで同じ通知を何度も再送する仕様です。

対象: `bad/PaymentWebhookController.java`
「どこが問題か、どう直すべきか」をレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

1. **署名(signature)を検証していない【セキュリティ・最重要】**: `X-Signature` を受け取っているのにログに出すだけで、本物か検証していない。公開URLは誰でも叩けるため、攻撃者が偽の `payment.succeeded` を直接POSTするだけで、1円も払っていない注文が `PAID` になりポイントも付く。
2. **冪等性がない＝重複処理し放題【本丸】**: プロバイダは 2xx を受け取るまで同じ通知を再送する仕様。なのに「処理済みか」の判定が一切なく、同じ通知が3回届けばポイント3回付与・メール3通送信になる。
3. **失敗しても "OK"(2xx) を返す**: `catch` で握りつぶし `return "OK"`。DBエラー等で処理に失敗しても成功扱いになり、プロバイダは再送を止める＝入金通知が永久に失われる。`e.printStackTrace()` もログ設計としてNG。
4. **`@Transactional` がない＝部分コミット**: 注文 save とポイント save が別々。ポイント更新でエラーが出ると「注文はPAID・ポイント未付与」の中途半端な状態が残る（第03問）。
5. **`findById(orderId).get()`**: 注文が無いと中身の分かりにくい `NoSuchElementException` が発生（第05問）。
6. **ログに機密情報・個人情報**: `signature`（秘密の印）と `email`（個人情報）を平文でログ出力（第07・11問）。
7. **状態が文字列("PAID")のマジック値**: タイプミスしてもコンパイルで気づけない。enum にすべき（第16問）。
8. **`Map<String,Object>` ＋ 手動キャスト**: `(int) payload.get("amount")` 等は型の保証がなく実行時に落ちる。型付きDTOにすべき（第04問）。
9. **`amount / 100` のマジックナンバー**: 100 の意味が不明。名前付き定数にして意図を明示する。
10. **`eventType.equals("payment.succeeded")`**: `eventType` が null だと NPE。定数を左に置く（`"payment.succeeded".equals(...)`）。

## ⭕️ 改善案 (good/ 配下)

1. **署名検証を"門番"にする**: `WebhookSignatureVerifier` で、本文の生バイト列＋秘密キーから HMAC-SHA256 を自分でも計算し、送られてきた署名と一致するか照合。不一致なら 401 で即拒否。秘密キーは設定/環境変数から注入（第14問）。生バイト列で受けてから検証→パースの順にする（パース後だと1バイトずれて検証失敗しうる）。
2. **冪等性を二重の安全網で保証**: ①処理済みイベントID(`ProcessedWebhookEvent`)を記録し、再送はスキップ。②`eventId` にDBの一意制約を張り、"同時"再送でも二重登録を物理的に阻止（第10問のCheck-Then-Act対策）。加えて `status==PAID` なら弾く状態ガードも併用。
3. **正しいHTTPステータスを返す**: 成功・重複は 200（再送不要）、本文不正やデータ不整合は 400（再送しても無駄）、想定外エラーは 500（プロバイダに再送＝自動リトライさせる）。失敗を 2xx で隠さない。
4. **`@Transactional` で一括更新**: 注文・ポイント・処理済み記録を「全部成功 or 全部取消」にまとめる。
5. **`orElseThrow` ＋ 専用例外**: `OrderNotFoundException` で原因を明確に。
6. **ログから秘密・PIIを排除**: 署名やメールは出さず、必要な識別子のみ。
7. **`OrderStatus` enum**: 取り得る状態をコンパイラが保証。
8. **型付きDTO `PaymentWebhookRequest`(record)**: Jacksonが安全に型変換。
9. **`YEN_PER_POINT` 定数**: 100 の意味を明示。
10. **責務分離**: Controllerは受け口(署名検証・変換・委譲・ステータス)、業務ロジックはServiceへ（第08問）。

> 補足（発展）: メール送信を `@Transactional` の中で行うと、「メールは送ったのにDBコミットで失敗」等の不整合が起こり得る。厳密にはトランザクションのコミット後に送る（`TransactionSynchronization` / イベント方式）のが理想。good/ ではまず「冪等性・トランザクション・署名検証」の背骨を優先している。
