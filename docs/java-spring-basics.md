## 🟦 A. Java言語そのものの話（Springがなくても通用する）

### A-1. スレッド（同時実行）
- **メソッド＝レシピ（1枚）、スレッド＝料理人（何人でも）。** 同じメソッドが複数スレッドから**同時に実行される**のが普通。
- スレッドは**1手ごとにOS（スケジューラ）に中断・交代させられる**ので、後から始めた処理が先に終わる「**追い越し**」が起きる。タイミングは毎回バラバラ。
- `a = a + 1` は「読む→+1→書く」の**3ステップ**。途中で追い越されると値がズレる。この“たまたま壊れる”状態を**競合状態（レースコンディション）**と呼ぶ。
- 「確認してから実行」（**Check-Then-Act**）は、確認と実行の**すきま**に割り込まれるので並行処理では危険。

### A-2. ローカル変数 vs フィールド（何が共有される？）
- **メソッド内のローカル変数・引数** → スレッドごとに別（安全）。
- **インスタンスのフィールド（クラス直下の変数）** → その1インスタンスを共有する全スレッドで共有（同時に触ると危険）。

### A-3. コンストラクタの仕様
- コンストラクタ＝**`new` の瞬間に1回だけ呼ばれる初期化メソッド**。同名で引数違いを複数持てる（**オーバーロード**）。
- **落とし穴**：コンストラクタを1個も書かなければ「引数なしコンストラクタ」がJavaに自動生成される。
  でも**引数ありを1個でも書くと自動生成は消える** → 引数なしが必要なら**手で書き足す**。

### A-4. アクセス修飾子（`public` / `protected` / `private`）
- 「**誰に使わせて、誰に使わせないか**」を決める設計の道具。
- 例：`protected Application()` は「フレームワーク（JPA）には使わせるが、業務コードには“正規のコンストラクタを使え”と促す」ちょうどいい制限。
  `public`だと不正なオブジェクトを作られ、`private`だと必要な相手も使えない。

### A-5. インターフェース
- **「こういうメソッドがあるよ」という約束（設計図）だけ**を書いたもの。単体では中身がなく動かない。
- 「実物ではなく**約束に依存**しておくと、中身を差し替えられる」——これがテスト容易性・柔軟性の土台。

## 🟩 B. Spring Boot / フレームワークの仕組みの話

### B-1. DI（依存性の注入）
- 必要な部品を**自分で `new` せず、外（Spring）から渡してもらう**仕組み。
- Springは起動時に `@Service` `@Repository` 等のクラスを**自分で作って倉庫（DIコンテナ）に保管**し、必要なところへ挿し込む。
- たとえ：料理人（Service）が自分で野菜を育てる（new）のではなく、仕入れ業者（Spring）が届けてくれる（DI）。

### B-2. `@Autowired` と注入の流派
- `@Autowired`＝「ここに部品を自動で挿し込んで」という印（auto + wired = 自動配線）。
- **コンストラクタ注入（推奨）**：`final`フィールド＋コンストラクタで受け取る。
  「必ず入っている・後から変わらない・テストで差し替えやすい」の3点で優秀。
- **コンストラクタが1個なら `@Autowired` は書かなくてよい**（Springが自動判断。Spring 4.3以降）。
- **フィールド注入（`@Autowired private ...`）は現場では基本避ける**
  （`final`にできない／中身nullのオブジェクトが作れる／テストしづらい）。

### B-3. `@Service` はシングルトン
- `@Service`（や大半のBean）は**アプリ全体で1インスタンスだけ**作られ、全リクエストで**使い回される**。
- だから**フィールドに可変な状態を持たせると、全スレッドで共有されて事故る**。
  サービスは**状態を持たない（ステートレス）**のが基本。← A-1 / A-2 と直結。

### B-4. Spring Data JPA の“空インターフェースが動く”仕組み
- `JpaRepository` を継承した**インターフェースを書くだけ**で、Springが起動時に**実装クラスを自動生成**して倉庫に入れる。
- だから中身を書いていないのに `save()` `count()` が動く。
  受け取っているのは「インターフェースの形」だが、正体は自動生成された実物。

### B-5. JPA / ORM とは
- **JPA（Java Persistence API）**＝JavaオブジェクトとリレーショナルDBの表を**自動で翻訳**して、
  SQLをほぼ書かずに永続化（＝データを消えないように保存）する**公式ルール（仕様）**。
- この「オブジェクト⇔表の対応づけ」を **ORM（Object-Relational Mapping）** と呼ぶ。
- 役割分担：**JPA＝ルール / Hibernate＝実際に動かす実装 / Spring Data JPA＝さらに楽にする層**。
- `@Entity` `@Table` `@Id` `@Column` は「クラス⇔表、フィールド⇔列」の**対応地図**。
- JPAは「**空のオブジェクトを作ってから値を後入れ**」する → だから**引数なしコンストラクタが必須**（A-3とつながる）。
- DBへの反映は**即時ではなく、トランザクションの区切りなど決まったタイミング**でまとめて同期される。

### B-6. DAO / Repository
- **DAO（Data Access Object）**＝「DBへのアクセス処理だけを担当する係」の設計パターン。
- Spring の **Repository は DAO の一種**。役割は「データの出入り口係」。
- セットで捉える：**Entity（表の1行の入れ物）＋ Repository/DAO（出し入れする係）**。

### B-7. `@Query` と `:名前` プレースホルダ／`@Param`（値の差し込み）
- `@Query("...")` ＝ リポジトリのメソッドに**自分で書いたSQL（正確にはJPQL）**を紐づけるアノテーション。命名規則（`findByXxx`）では書けない集計（SUM/COUNT）やJOINを書きたいときに使う。
- SQL文の中の **`:名前`（コロン付き）＝「あとで値を差し込む空欄（プレースホルダ）」の目印**。まだ具体値は入っていない。
- メソッド引数の **`@Param("名前")` ＝「この引数を、SQL中の `:名前` の空欄に入れてね」という宛名ラベル**。
  ```java
  @Query("... WHERE o.orderDate = :date")
  DailySalesSummary summarize(@Param("date") LocalDate date);
  //                          ↑ この引数が :date の空欄に入る
  ```
- **対応づけは「名前」であって「順番」ではない。** `:名前` と `@Param("名前")` の**名前が一致**していれば結びつく。だから引数の並び順は自由で、取り違えが起きにくい。
- **引数が複数でも同じ**。空欄と `@Param` を数だけ用意して、名前で対応させるだけ：
  ```java
  @Query("... WHERE o.orderDate = :date AND o.amount >= :minAmount")
  DailySalesSummary summarize(@Param("date") LocalDate date,
                              @Param("minAmount") long minAmount);
  ```
- **よくあるミス**：`:minAmount` なのに `@Param("minamount")` のような**大文字小文字・綴り違い**。名前が一致せず**起動時にエラー**になる（`:名前` と `@Param("名前")` は完全一致が条件）。
- **なぜ文字列連結でSQLを作らないのか**：`"... = '" + date + "'"` のような手組みは、悪意ある入力でSQLを乗っ取られる **SQLインジェクション**の穴になる。`:名前`＋`@Param` の差し込み（**バインド変数**）は、渡された値を「**ただのデータ**」として安全にはめ込むので、この攻撃を原理的に防げる。→ セキュリティ観点（第1・7問）にも直結。
