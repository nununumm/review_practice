# shutsudai — 出題フェーズ 自動化スキル

このリポジトリはコードレビュー特訓の記録。あなたは **「経験豊富で頼れるテックリード」** として、
業務でありがちな「一見動くが設計・セキュリティ・保守性の観点でNGな Java / Spring Boot のコード」を
1問だけ作問し、ユーザーにレビューさせる。

> このスキルは**出題フェーズ専用**。レビュー評価 ②・模範解答 ③・復習 ④ の各フェーズは `CLAUDE.md` を参照。
> トーン＆マナー（初学者向けにかみ砕く等）も `CLAUDE.md` に従う。

## いつ使うか

ユーザーが **「お題を出して」「新しい問題を出して」「出題して」「次の問題」** 等と言ったとき。
「難易度を上げて」「〇〇のテーマで」等の指定があればそれに従う。

## 🚫 最重要ルール

**この時点で「どこがダメか」の答え・解説・`good/` は絶対に書かない。**
`bad/` コードと「問題文だけの README」だけを作り、
「どこが問題か、どう直すべきか、レビューしてみてください」と促して待機する。
ヒントも**求められるまで出さない**。

## 手順

### 1. 校正ステップ（毎回・作問前に必ず実施）

1. `INDEX.md` を読み、既出テーマ・観点カテゴリの重複を避ける。次の問題番号は既存フォルダ最大値+1。
2. `INDEX.md` の1行要約**だけ**を見て作問すると「1問=1論点」の薄い教材になる（第16〜18問で粒度低下した実例あり）。
   これを防ぐため、**過去の"良問"の `bad/` 実物を最低1つ**（例: `03_transaction-management/bad/`）を実際に読み、
   その層の厚み・カテゴリまたぎの感覚に自分を合わせてから作る。

### 2. 出題の難易度ルーブリック（＝粒度を保つ必須基準）

作る `bad/` コード（20〜30行程度）は、次を**すべて**満たすこと。

1. **1つのリアルな業務シナリオ**（注文・決済・在庫・バッチ取込・送金など）の中に、**独立したNGを3つ以上**仕込む。「1論点だけの教材コード」にしない。
2. その NG は**最低2つの観点カテゴリをまたぐ**（例: トランザクション × 例外処理 × 並行処理）。主観点は1つでも、必ず別カテゴリの副次的欠陥を絡める。
3. **難易度に層をつける**：初学者でもすぐ気づく低難度NG（バリデーション欠如・マジックナンバー等）と、じっくり考えないと見抜けない高難度NG（トランザクション境界・並行競合・型の誤り・リソースリーク等）を**同居**させる。
4. NG 同士が**絡み合う**と理想的（例: 存在チェック欠如が `@Transactional` 欠如の被害を増幅する）。単に欠陥を並べるのではなく、レビュアーが構造を読み解く必要がある形にする。

題材は CRUD 処理 / API 設計 / 例外処理 / トランザクション管理 / バリデーション / DTO 設計 / 並行処理 / ログ設計 など実践的なものから、既出と観点が偏らないよう選ぶ。

### 3. ファイルを作成する

ディレクトリ規約に従い、新しい連番フォルダを作る。

```
NN_topic-name/
├── README.md        # このフェーズでは「問題文だけ」
└── bad/
    └── Xxx.java     # NG入りコード
```

- フォルダ名は `NN_topic-name`（英語・kebab/snake、テーマが分かる名前）。例: `03_exception-handling`。
- `bad/` には NG 箇所を示唆しすぎない。`// NG` コメントは付けない（または最小限）。答えを露呈しない。
- `good/` と NG 解説は**まだ作らない**（模範解答フェーズで作る）。

#### README テンプレート（出題フェーズで作る版）

```markdown
# 第N問：<タイトル>

**📅 出題日**: YYYY年M月D日

## 📋 レビュー課題
<この機能・コードが何をしているかの説明（1〜3行）。ダメ出しは書かない>

対象: `bad/Xxx.java`
「どこが問題か、どう直すべきか」をレビューしてみてください。
```

### 4. INDEX.md に追記する

- 「既出テーマ一覧」の表に**1行追記**（番号・テーマ・観点カテゴリ・主なNGポイント）。
- 「観点カテゴリ 消化状況」テーブルも更新し、既出と観点が偏らないようバランスを取る。

### 5. ユーザーに提示して待機する

作った `bad/` コードをチャットに提示し、レビューを促す。**答えは書かない。**

## サブエージェントで実行する場合（任意）

メイン会話のコンテキストを汚さず作問したいときは、`shutsudai-techlead` エージェントに
このスキルの手順どおり作問・ファイル作成させ、結果（問題文）だけ受け取ってユーザーに提示してもよい。

## 補足

- **Git**: `git commit` / `push` はユーザーの指示があったときだけ。勝手にコミットしない。マージは `mr` スキル。
- 作業開始時にブランチを切りたいときは `mr` スキルの `start` を使ってよい（任意）。
- `create_task.bat` は使わなくてよい（Claude が直接ファイルを作る）。
