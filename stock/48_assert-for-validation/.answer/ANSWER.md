## ❌ NGポイント (bad/ 配下)

1. **入力検証に `assert` を使っており、本番では検証が丸ごと無効化される（核心・重大／気づきにくい）**: `assert` は「開発中に、起こり得ないはずの前提が本当に成り立っているか」を確認するデバッグ用の仕掛けで、**Java の本番実行では標準で無効**（起動時に `-ea`／`-enableassertions` を付けない限り、その行はまるごと実行されない）。つまり本番環境では `assert amount > 0` などが**すべて素通り**し、マイナス送金・上限100万円超え・不正な口座番号のチェックが一切効かなくなる。開発環境（`-ea` 付き）では正しく弾けるので、「開発では動いたのに本番でだけ検証が消える」という最悪の事故になる。送金という金銭を扱う機能でこれは致命的。

2. **そもそも「外から来る入力」の検証に assert を使う設計が誤り（設計・例外）**: assert は「プログラム内部の不変条件（自分たちのコードが正しければ必ず成り立つこと）」の確認用であって、ユーザー入力や API 引数のような**信頼できない外部入力の検証には使ってはいけない**。外部入力は通常の `if` ＋例外で検証するのが原則。

3. **失敗時に `AssertionError` になり、呼び出し側が扱えない（例外設計／低〜中）**: 仮に `-ea` が付いていても、assert が失敗すると `AssertionError`（`Error` の一種）が飛ぶ。これは本来キャッチして処理すべきものではなく、入力エラーを表す例外としては不適切。呼び出し側は「入力が不正だった」として扱えない。

4. **上限額 `1000000` がマジックナンバー（低）**: 何の値か・なぜその値かがコードから読み取れない。名前付き定数か外部設定にすべき。

## ⭕️ 改善案 (good/ 配下)

1. **検証は `if` ＋例外で行う**: `if (amount <= 0) throw new IllegalArgumentException(...)` のように、本番でも必ず実行される通常のコードで検証する。assert は使わない。

2. **不正入力は `IllegalArgumentException` など意味のある例外で知らせる**: 呼び出し側（例：`@ControllerAdvice`）が入力エラーとして受け止め、適切な HTTP ステータスに変換できる。

3. **マジックナンバーを名前付き定数にする**: `MAX_AMOUNT` / `ACCOUNT_NUMBER_LENGTH` として意味を明示する（必要なら外部設定へ）。

4. **形式検証を一段厚くする**: 「10桁」だけでなく「数字のみか」も確認する。

## 💬 レビューコメント例文

> 「開発環境ではちゃんとエラーになるのに、本番だと大丈夫か不安」——この不安、実は大正解です。ここには本番でだけ検証が消える罠があります。入力チェックに `assert` を使っていますよね。assert は開発中のデバッグ専用で、本番の Java は起動時に `-ea` を付けない限り assert の行を**まるごと無視**するんです。つまり本番では、マイナス送金も上限超えも不正な口座番号も、チェックが全部素通りします。送金機能でこれはかなり危険です。

> assert は「自分たちのコードが正しければ絶対に成り立つはずの内部前提」を確認するための道具で、ユーザー入力のような外から来る値の検証には使ってはいけない、と覚えておいてください。外部入力は必ず `if` ＋例外で検証します。`if (amount <= 0) throw new IllegalArgumentException(...)` のように書けば本番でも確実に効きますし、`IllegalArgumentException` にしておけば上位のハンドラで入力エラーとして拾えます。ついでに上限の `1000000` は名前付き定数にして、口座番号も「10桁かつ数字のみ」まで見ておくと堅くなりますよ。
