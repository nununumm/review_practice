## ❌ NGポイント (bad/ 配下)

1. **`size` を無検証で受け入れている（メモリ枯渇の危険）**:
   `@RequestParam int size` をそのまま使っており、上限がありません。悪意でなくても
   `?size=1000000` のようなリクエストが来ると、その件数を一気に扱おうとします。
   「1ページに100万件」を平気で受け付けるAPIは、リクエスト1本でサーバのメモリを食いつぶし、
   最悪 OOM（＝OutOfMemoryError。メモリが足りずアプリが落ちること）でサービス全体が止まります。
   これは外部から簡単に狙える弱点（DoS＝サービス妨害）になります。

2. **`page` / `size` の負数・0 を検証していない**:
   `page=-1` や `size=0` がそのまま計算に流れます。`offset = page * size` が負になると
   `all.subList(負, ...)` で `IndexOutOfBoundsException`（＝範囲外アクセスの例外）になり、
   500エラー（＝サーバ内部エラー）を返します。ユーザーの打ち間違い1つでAPIが落ちる状態です。

3. **DBのページングを使わず、全件ロードしてアプリ側で切り出している**:
   `findAll()` は「テーブルの全行」をメモリに載せます。そのあと `subList(...)` で
   欲しいページだけ切り出しても、“いったん全部読む”という一番重い部分は変わりません。
   商品が10件のうちは動きますが、10万件・100万件になると1ページ見るだけで全件読み込みが走り、
   遅い・重い・落ちる、の三重苦になります（＝スケールしない）。
   ページングの目的は「必要な分だけ取る」ことなのに、それが実現できていません。

4. **総件数を `findAll().size()` で数えている**:
   件数を知りたいだけなのに、また全行をメモリに読み込んでから数えています。
   DBには `SELECT COUNT(*)`（＝件数だけ返す軽い問い合わせ）があるのに、それを使っていません。
   しかも `getProducts` と `countProducts` で `findAll()` を2回呼んでおり、全件ロードを二度走らせています。

5. **`offset = page * size` が int 同士の掛け算でオーバーフローする**:
   Java の `int` は約21億（2,147,483,647）が上限です。`page` と `size` が大きいと
   掛け算の結果がこの上限を超え、桁あふれして**負の数に化けます**。
   本来は範囲外エラーで弾きたい入力が、負のoffsetになって別の異常動作を引き起こす、
   という「気づきにくいのに影響が大きい」バグです。

6. **デフォルト値・最大件数の上限がない**:
   `page` / `size` が必須パラメータで、しかも上限も初期値もありません。
   「未指定なら20件」「多くても100件まで」といったガードレールがないため、
   呼ぶ側の作法に完全に依存し、事故が起きやすい設計になっています。

## ⭕️ 改善案 (good/ 配下)

1. **入力を安全な範囲に補正する**:
   `page` は負なら0に、`size` は1未満ならデフォルト（20）に、上限（100）を超えたら100に
   “クランプ（＝上限・下限で頭打ちにする）”します。これでNG1・NG2・NG6を一括で潰せます。

2. **Spring Data の `Pageable` / `PageRequest` でDBに委譲する**:
   `PageRequest.of(page, size, Sort.by("id"))` を作って `findAll(pageable)` に渡すと、
   Spring Data がDBに `LIMIT / OFFSET` を付けて“そのページ分だけ”取ってきます。
   全件ロード＋`subList` は不要になり、スケールします（NG3を解消）。

3. **総件数はDBの `count()` を使う（`Page` が自動でやる）**:
   `findAll(pageable)` の戻り値 `Page<Product>` は、中身のリストに加えて
   `getTotalElements()`（総件数＝COUNT結果）や `getTotalPages()` も持っています。
   自前で全件を数える必要がなくなります（NG4を解消）。

4. **offset の計算はフレームワークに任せ、桁あふれを避ける**:
   自分で `page * size` を計算しないので、int オーバーフローの心配が消えます（NG5を解消）。
   仮に自前計算が必要でも `(long) page * size` のように long で計算します。

5. **レスポンス専用DTOに詰め替えて返す**:
   エンティティを直接返さず `PageResponse` に詰め替え、APIの形とDBの構造を切り離します。

6. **（発展）深いページには keyset ページング**:
   OFFSET が巨大になるとDBの「読み飛ばし」が遅くなります。無限スクロール等では
   「前回の最後のidより後ろをN件」で辿る keyset(seek)ページングにするとOFFSETが不要になり、
   何ページ目でも速度が一定になります。good のコメントに一言残しています。
