## ❌ NGポイント (bad/ 配下)

1. **部分更新なのに、送られてこなかった項目まで `null` で上書きしてデータを消している（核心・API設計）**: この API は「変更したい項目だけ送る」部分更新（PATCH）のはず。ところが `member.setPhone(req.getPhone())` のように全項目を無条件でセットし直しているため、ユーザーがニックネームだけ変えて送ると、`req` の phone / email / birthday は `null` のまま渡ってきて、**既存の電話番号・メール・誕生日が丸ごと `null` で消える**。ユーザーからすれば「ニックネームを変えただけなのに電話番号が消えた」という深刻なデータ消失。部分更新では「値が入っている項目だけ」反映しなければならない。

2. **`findById(memberId).get()` で存在チェックをしていない（低〜中）**: 会員が存在しないと `NoSuchElementException` という中身の分からない例外で落ちる。`orElseThrow` で「会員が見つからない」と明示すべき。

3. **Entity をそのまま返している（情報漏洩・DTO 不在／副次）**: `Member` エンティティを直接返すと、内部管理項目やまだ公開すべきでないフィールドまでレスポンスに出てしまう恐れがある。公開してよい項目だけの応答用 DTO に詰め替えるべき。

4. **バリデーションが無い（低）**: メールアドレスの形式チェックや必須/桁数の検証が無く、不正な値でもそのまま保存される。

5. **更新系なのに `@Transactional` が無い（整合性）**: 取得〜更新〜保存を1つのトランザクションにまとめておらず、複数項目・複数テーブルに広がったときに部分的な更新が残りうる。

## ⭕️ 改善案 (good/ 配下)

1. **「値が入っている項目だけ」反映する**: 各フィールドについて `if (req.getXxx() != null) member.setXxx(...)` とし、`null`（＝今回は変更しない）の項目は既存値を残す。これで部分更新の意味を満たし、データ消失を防ぐ。（「明示的に null にしたい」要件がある場合は、`Optional` フィールドや「変更対象キー一覧」を持つ DTO 設計で「未指定」と「null にしたい」を区別する。）

2. **存在チェックは `orElseThrow`**: 会員が無ければ意味のある例外（`MemberNotFoundException` 等）で知らせる。

3. **Entity を直接返さず DTO に詰め替える**: 公開してよい項目だけの `MemberProfileResponse` を返す。

4. **変更がある項目だけバリデーションする**: メール形式などを確認してから保存する。

5. **更新系に `@Transactional` を付ける**: 取得〜保存を1つのまとまりにする。
