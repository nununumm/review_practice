## ❌ NGポイント (bad/ 配下)

1. **「数字かどうか」の判定に try-catch を使っている（例外を通常の制御フローに流用：最重要）**: `try { Integer.parseInt(s) } catch (NumberFormatException e) { ... }` で「数字でなければ既定値」を表現している。数字でない入力（例：空欄、"abc"）は**想定内のごく普通の入力**であって「異常」ではない。それなのに毎回わざわざ例外を投げて捕まえている。例外（＝プログラムの異常を知らせる仕組み）は、投げるときにスタックトレース（＝どこで起きたかの経路情報）を集めるため**生成コストが高い**。想定内のことで例外を投げると、遅いうえに「ここは異常が起きる場所なんだな」と読み手に誤解させる。想定内の分岐は `if` や事前チェックで普通に判定すべき。「try-catch は例外的なときの非常口であって、日常の分かれ道に使う道具ではない」と考えるとよい。

2. **一覧の終端検出・要素の存在判定に例外を使っている（例外でループ制御している）**: カテゴリ一覧の検索を `while (true) { categories.get(i) ... i++ }` で回し、**リストの範囲外まで行って IndexOutOfBounds(＝範囲外アクセス)例外が出たら打ち切る**、という作りになっている。「一覧を最後まで探した」というごく当たり前の正常な流れを、例外という非常口で表現してしまっている。これも NG1 と同じ「例外を制御フローに使うアンチパターン」で、遅いだけでなく、読んだ人が「なぜここで例外を握っているのか」を理解できない。素直に `for` で回す、あるいは `stream().filter().findFirst()` で「条件に合う最初の1件」を探すべき。

3. **例外を握りつぶして黙ってデフォルト値にすり替えている（失敗の原因が消える）**: 価格上限の `catch (NumberFormatException e) { maxPrice = 0; }` も、区分検索の `catch (Exception e) { matched = null; }` も、例外オブジェクト `e` を**一切ログに出さず捨てている**（＝握りつぶし）。本当は「なぜ変換できなかったのか／なぜ検索が失敗したのか」という手がかりが `e` に入っているのに、それを捨てて何事もなかったように既定値へ差し替えている。本番で「なぜかいつも0円上限になる」といった不具合が出ても、原因の痕跡がどこにも残らず、調査が極めて困難になる。

4. **`catch (Exception e)` で広く捕まえすぎて、本物のバグまで飲み込む**: 区分検索の catch が `Exception`（＝ほぼすべての例外の親）になっている。これだと、狙っている「範囲外」だけでなく、たとえば `categories` が null だったときの NullPointerException（＝本来直すべきプログラムのバグ）まで一緒に捕まえて `matched = null` にすり替えてしまう。バグが「区分が見つからなかっただけ」に化けて表に出てこなくなる。捕まえる例外は必要な種類だけに絞る（そもそも例外に頼らないのが本筋）。

5. **戻り値・既定値が曖昧で意味を取り違える（マジックナンバー / 0・nullの多義性）**: 価格上限が変換できないとき `0` を入れているが、これは「上限なし」のつもりなのか「上限0円（＝何も表示しない）」なのか、コードからは判別できない（＝0という数字に意味が二重になっている）。同様に区分が見つからないとき `null` を返すが、呼び出し側が null チェックを忘れると別の場所で NullPointerException を起こす。「無い」「制限なし」といった状態は、番兵となる名前付き定数や `Optional`（＝有る/無いを型で表す入れ物）で、意味をはっきり表すべき。

## ⭕️ 改善案 (good/ 配下)

1. **数字判定は事前チェックで行う**: `value.matches("-?\\d+")`（＝整数の形かを正規表現で確認）などで「変換できる形か」を静かに判定してから `Integer.parseInt` する。想定内の入力で例外を投げないので、速く・意図も明快。`parseIntOrDefault(値, 既定値)` の小メソッドに切り出して再利用する。

2. **存在検索は stream / Optional で表す**: `categories.stream().filter(c -> code.equals(c.getCode())).findFirst()` で「条件に合う最初の1件」を `Optional` として受け取る。見つからなければ空の Optional になるだけで、例外もループの手動打ち切りも要らない。

3. **例外は握りつぶさない**: そもそも想定内の分岐から例外を無くしたので握りつぶす場面が消える。もし本当に異常な例外を扱うなら、必ずログに残すか意味のある形で伝え直す。

4. **捕まえる例外は絞る（=そもそも減らす）**: `catch (Exception e)` のような広すぎる捕捉をやめ、正常系を if/Optional で表現することで、NullPointerException のような本物のバグは握りつぶさず表に出す。

5. **曖昧な既定値を名前付き定数・番兵にする**: 「上限なし」は `NO_PRICE_LIMIT = -1` のように名前を付けて意味を明示し、0の多義性を無くす。既定ページも `DEFAULT_PAGE = 1` と定数化する。

>
