## ❌ NGポイント (bad/ 配下)

1. **呼び出しのたびに `new ObjectMapper()` していて非効率（核心・パフォーマンス）**: `ObjectMapper` は生成時に内部で多くの初期化（設定の適用やシリアライザ/デシリアライザのキャッシュ構築）を行う、比較的「重い」オブジェクト。それを `toJson` / `fromJson` が呼ばれるたびに作り直しており、この `JsonConverter` はアプリ全体から高頻度で呼ばれるので、無駄な CPU 消費と GC（ガベージコレクション）負荷が積み重なる。`ObjectMapper` は**スレッドセーフで使い回し前提**の設計なので、アプリで1個作って共有するのが正しい。

2. **設定が各所でバラバラになり一貫性がない（設計）**: 毎回 new すると、日付フォーマットや「未知フィールドを無視するか（`FAIL_ON_UNKNOWN_PROPERTIES`）」などの設定を統一できない。ある場所では通る JSON が別の場所では落ちる、といった不整合の温床になる。設定は1か所に集約すべき。

3. **例外を握りつぶして `null` を返している（例外処理）**: `toJson` は `printStackTrace` して `null`、`fromJson` に至ってはログすら出さず黙って `null` を返す。呼び出し側は変換失敗に気づけず、返ってきた `null` を使った別の場所で NPE を起こす。原因も失われる。

4. **`static` ユーティリティ的で DI できず、テストで差し替えにくい（テスト容易性・低〜中）**: どこからでも `new JsonConverter()` して呼ぶ形だと、設定済みの ObjectMapper を注入したり、テスト用に振る舞いを差し替えたりしにくい。Spring の Bean にして注入できる形が望ましい。

## ⭕️ 改善案 (good/ 配下)

1. **`ObjectMapper` はアプリで1個だけ作って使い回す**: `JsonConverter` を Spring の `@Component`（アプリに1個だけの部品）にし、`ObjectMapper` をフィールドに1つ持って `final` にする。スレッドセーフなので共有して問題ない。

2. **設定を1か所に集約する**: コンストラクタで `FAIL_ON_UNKNOWN_PROPERTIES` などの方針をまとめて設定し、アプリ全体で一貫させる。

3. **例外を握りつぶさない**: `JsonProcessingException` を捕まえたら `null` を返さず、原因(e)を包んだ例外を投げて呼び出し側に失敗を伝える。

4. **注入しやすくする**: `ObjectMapper` を引数に取るコンストラクタも用意し、Spring 管理の共有 Bean を注入したりテストで差し替えたりできるようにする。

## 💬 レビューコメント例文

> 変換処理を1か所の共通ユーティリティにまとめる方針はとても良いですね。ただ1点、性能面で効いてくる直しがあります。`toJson` / `fromJson` の中で毎回 `new ObjectMapper()` していますよね。ObjectMapper は生成時に内部でいろいろ準備をする「重い」オブジェクトで、しかもこのクラスはアプリ中から高頻度で呼ばれるので、毎回作り直すのは無駄な CPU と GC 負荷になります。実は ObjectMapper はスレッドセーフで、1個作って使い回すのが公式の推奨なんです。

> なので、この `JsonConverter` を Spring の `@Component` にして、ObjectMapper をフィールドに1個だけ持たせて使い回しましょう。ついでに「未知フィールドを無視するか」などの設定もコンストラクタに集約すると、アプリ全体で挙動が揃って不整合が減ります。あと、変換に失敗したとき `null` を返しているのも直したいところ。呼ぶ側が失敗に気づけず、あとで別の場所で NPE になってしまうので、`JsonProcessingException` は原因を包んで投げ直すようにしておきましょう。
