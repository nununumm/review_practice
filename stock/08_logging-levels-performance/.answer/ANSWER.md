## ❌ NGポイント (bad/ 配下)

1. **ログレベルの誤用（大量ループの各件を info、重要な失敗を debug）**:
   数万件のループで1件ごとに `log.info("処理開始 ...")` `log.info("処理成功 ...")` を出している。
   本番のログが「1件ごとの当たり前の進捗」で埋め尽くされ、本当に見たい情報が探せなくなる（＝ログが多すぎて逆に何も分からない状態）。
   さらに逆に、`不正なデータのためスキップ` という**本当に気づきたい失敗**を `log.debug` で出している。
   debug は本番では普通オフなので、この重要イベントは**誰にも見えないまま消える**。レベルの使い方が上下逆さま。

2. **同じ例外の二重ログ（catch でログしてさらに throw、上でもまたログ）**:
   `process()` の中で `log.error("execute失敗 ...", e)` と出したうえで `throw new RuntimeException(..., e)` している。
   その例外を呼び出し元のループの catch がまた `log.error("項目処理でエラー ...", e)` で出す。
   結果、**まったく同じスタックトレース（＝エラーの発生経路の記録）が2回**ログに書かれる。
   さらに `NightlyBatchRunner` でも `log.error` があり、経路によっては三重にもなる。
   調査するとき「同じエラーが何回も出ている＝別々のエラーだ」と誤解し、件数も水増しされる。

3. **debug ログの重い文字列生成を無防備に毎回実行**:
   `log.debug("processing " + target.toBigString())` は、`+` の連結が**メソッド呼び出しより先に評価**される。
   つまり debug がオフの本番でも、全項目を連結する重い `toBigString()` が**毎件必ず実行される**。
   ログには何も出ないのに、CPU とメモリだけ消費する。数万件×毎回なので、バッチが目に見えて遅くなる。

4. **ロガーと System.out.println の混在**:
   開始・終了を `System.out.println` で出している。標準出力はログ基盤（ファイル出力・レベル制御・ローテーション＝古いログの自動整理）に乗らないため、
   出力先も時刻フォーマットもバラバラになり、本番では拾い漏れる。ログ管理の統一が崩れる。

5. **例外を握りつぶして処理続行（記録も集計もしない）**:
   ループの catch は `log.error` するだけで、失敗を数えも集めもせず次へ進む。
   バッチが「正常終了」したように見えても、実は何件失敗したのか、どのIDがダメだったのかが後から分からない。
   翌朝の突合で初めて事故が発覚する、という最悪の負債になる。

6. **文字列連結でログを組み立てている（{} プレースホルダ未使用）**:
   `"処理開始 id=" + target.getId() + " status=" + target.getStatus()` のように連結している。
   SLF4J では `log.info("処理開始 id={} status={}", id, status)` と書くのが作法。
   連結だと、そのレベルが無効でも文字列結合のコストが先に発生し、可読性も落ちる（プレースホルダなら出力しないときは結合もしない）。

## ⭕️ 改善案 (good/ 配下)

1. **レベルを役割で使い分ける**: 1件ごとの進捗は `trace`、詳細ダンプは `debug`、全体サマリ（開始/終了/成功・失敗件数）は `info`、
   スキップや個別失敗は `warn`、失敗が残ったことの総括は `error`。本番で見たいものが自然に浮かび上がる。
2. **例外は「ログか再スローのどちらか一方」に統一**: 「1件失敗しても全体は続ける」方針なら、失敗した場所で1回だけ記録して再スローしない。
   これで同じスタックトレースが二重に出ない。入口の Runner も、サービスが投げない設計にしたので再ログ不要。
3. **重い debug は `isDebugEnabled()` ガードで囲う**: `if (log.isDebugEnabled()) { log.debug("処理内容 {}", target.toBigString()); }`。
   debug がオフの本番では重い `toBigString()` が一切呼ばれない。
4. **{} プレースホルダを使う**: `log.info("... id={} status={}", id, status)`。無効レベルでは文字列結合も走らず、書きやすく読みやすい。
5. **System.out を排除**: すべて SLF4J のロガーに統一。出力先・レベル・フォーマットをログ基盤で一元管理できる。
6. **失敗は握りつぶさず集計して報告**: 失敗IDを `List` にため、最後に成功/スキップ/失敗の件数を `info` サマリで、失敗があれば `error` で1回出す。
   さらに件数とIDを詰めた `BatchResult` を戻り値で返し、呼び出し側が通知やリトライを判断できるようにする。

## 💬 レビューコメント例文

> バッチのログ、丁寧に進捗を出してくれていて意図はすごく良いと思います。そのうえで運用目線で3点だけ相談させてください。
> ① 1件ごとの `log.info` は数万件だと本番ログが進捗で埋まってしまうので、各件は `trace`/`debug` に落として、開始・終了・成功/失敗の件数サマリを `info` にしませんか。逆に「不正データでスキップ」は気づきたいイベントなので `warn` に上げたいです。
> ② `process()` で `log.error` してから throw し、呼び出し元でもまた `log.error` していて、同じスタックトレースが二重に出ています。「ログするか、再スローするか」はどちらか片方に寄せると調査が楽になります。今回は継続方針なので、失敗した場所で1回だけ記録する形が良さそうです。
> ③ `log.debug("processing " + target.toBigString())` は debug がオフの本番でも `toBigString()` が毎件走ってしまうので、`isDebugEnabled()` で囲うか `{}` プレースホルダに渡す形にしましょう。ついでにログは全部 `+` 連結ではなく `{}` に統一、`System.out` もロガーに寄せたいです。
> あと、失敗した件は数えて最後に「失敗N件（id一覧）」を出す＆戻り値で返すようにすると、翌朝の確認が一目で済みます。ここが一番の肝なので一緒に直しましょう。
