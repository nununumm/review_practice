## ❌ NGポイント (bad/ 配下)

1. **スレッドプールを解散（shutdown）していない → スレッドリーク**:
   `Executors.newCachedThreadPool()` で作ったプールは、使い終わったら `shutdown()`（＝もう仕事は来ないので作業員を解散させる合図）を呼ばないと、中の作業員スレッド（＝並行して動く作業員）が仕事を終えても居座り続けます。`sendToAll` を呼ぶたびに新しいプールが増え、居残り作業員がどんどん溜まっていきます。これを「スレッドリーク」と呼びます。作業員が消えないので JVM（アプリ本体）は「まだ仕事する人がいる」と判断してうまく終了できず、さらにスレッド1本ごとにメモリを消費するため、最後は OOM（＝メモリ不足でアプリが落ちること）に至ります。動作確認では1回しか呼ばないので気づきにくく、本番で何度も呼んで初めて牙をむく、たちの悪いバグです。

2. **メソッドの中で毎回 new している → プールにする意味がない**:
   スレッドプール（＝作業員を待機させて使い回す仕組み）の価値は「一度雇った作業員を待機させ、次の仕事でまた使い回す」ことでスレッド生成コストを節約する点にあります。ところが `sendToAll` の中で毎回 `newCachedThreadPool()` しているので、呼ばれるたびに作業員を新規に雇い直しており、使い回しの効果はゼロ。生成・破棄のコストがかさむうえ、（shutdown 漏れと相まって）スレッドが際限なく増えます。プールは本来アプリで1つ用意して共有すべき資源です。

3. **`newCachedThreadPool` / `newFixedThreadPool` の落とし穴（上限とキューが危険）**:
   `newCachedThreadPool()` は「タスクが来た分だけ作業員を作る」上限なしの設定です。数万人へ一斉送信すれば作業員が爆発的に増え、サーバのスレッド数上限に達して落ちます。かといって `newFixedThreadPool(n)` に替えても安心ではなく、こちらは作業員の数こそ固定ですが、順番待ちの行列（内部キュー）が無制限（`LinkedBlockingQueue`）なので、送りきれないタスクがメモリ上に無限に積み上がり、やはり OOM を招きます。本番用途では「作業員の上限」「行列の長さの上限」「あふれたときどうするか（拒否ポリシー）」を自分で決められる `ThreadPoolExecutor` / `ThreadPoolTaskExecutor` を使うべきです。

4. **`submit` の `Future` を無視 → 例外の握りつぶし**:
   `executor.submit(...)` はタスクの結果を受け取る `Future`（＝あとで結果を確認できる引換券）を返しますが、bad はこれを捨てています。すると、あるタスクの中でメール送信が例外で失敗しても、その例外は `Future` の中に閉じ込められたまま誰にも通知されません。結果「何件かは実は送れていない」のに、ログにも何も残らず、失敗に気づけません。

## ⭕️ 改善案 (good/ 配下)

1. **プールは共有 Bean にして DI で受け取る**:
   スレッドプールを `@Configuration` クラスで `ThreadPoolTaskExecutor` の Bean（＝アプリで1つだけ用意して共有する部品）として定義し、サービスはそれをコンストラクタで受け取ります（DI＝必要な部品を外から渡してもらう仕組み）。毎回 new せず、アプリ全体で1つを使い回します。

2. **ライフサイクル（後始末）を管理する**:
   Bean 化した `ThreadPoolTaskExecutor` は、アプリ終了時に Spring が自動で `shutdown` してくれるので、作業員の解散を自分で書かなくても漏れません。自前で `ExecutorService` を持つ場合は `@PreDestroy` で `shutdown()` ＋ `awaitTermination`（＝残った仕事の完了を待つ）を、1回きりの使い捨て用途なら try/finally で必ず `shutdown()` を呼びます。

3. **上限・有界キュー・拒否ポリシーを明示する**:
   `corePoolSize`（常駐の作業員数）、`maxPoolSize`（最大作業員数）、`queueCapacity`（順番待ち行列の上限）を有限に設定し、あふれたときは `CallerRunsPolicy`（＝手が空くまで呼び出し元自身に処理させ、新規受付を自然に抑える安全弁）を指定します。これでスレッド爆発もキュー無限増加も防げます。

4. **結果・例外を集約して失敗を可視化する**:
   `CompletableFuture` でタスクの結果を受け取り、`exceptionally` で失敗した宛先をログに残します。`allOf(...).join()` で全タスクの完了を待ってから戻ることで、呼び出し元は「送り終わった」ことと「どこが失敗したか」を把握できます。

## 💬 レビューコメント例文

> まず、一斉送信を1通ずつではなく並列で速くしようという発想、とても良いと思います。数万人規模なら直列送信は現実的でないので、方向性は正解です。
>
> そのうえで2点だけ直しましょう。1つ目は「後始末」です。今は `newCachedThreadPool()` をメソッドの中で毎回作っていて、しかも `shutdown()` を呼んでいません。スレッドプールは作業員を待機させて使い回す仕組みなので、解散させないと仕事が終わっても作業員が居座り続け、`sendToAll` を呼ぶたびに増えてしまいます（スレッドリーク）。結果、アプリが終了できなくなったりメモリを食いつぶしたりします。プールはアプリで1つの共有 Bean（`ThreadPoolTaskExecutor`）にして、後始末は Spring に任せるのがおすすめです。2つ目は「上限」です。`newCachedThreadPool` は作業員が無制限に増えるので、数万人送信でスレッドが爆発します。作業員数と順番待ちの行列に上限を設けて、あふれたら受付を抑える設定にしておきましょう。
>
> あわせて、送信タスクの失敗をログに残すようにすると「誰に届かなかったか」が追えて運用がぐっと楽になります。ここは経験を積むほど差が出るところなので、今回いっしょに直せるのは良い機会です。一緒に整えていきましょう。
