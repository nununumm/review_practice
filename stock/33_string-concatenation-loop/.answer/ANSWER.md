## ❌ NGポイント (bad/ 配下)

1. **ループ内の `+=` は毎回“全文の書き写し”になる（O(n²) の激遅コード）**:
   Java の `String` は**不変（＝いちど作ったら中身を書き換えられない）**です。だから `csv += 新しい行` を実行するたびに、
   「今までの全文」＋「新しい行」を**まるごとコピーした新品の文字列**が作られ、元の `csv` は捨てられます。
   たとえるなら、メモに1行足したいだけなのに**毎回まっさらな紙に全部を書き写し直している**ようなもの。
   1件目は1行ぶん、2件目は2行ぶん…と書き写す量がどんどん増え、n 件だと合計 1+2+…+n ≒ **n×n（O(n²)）**の作業量に膨らみます。
   数百件なら気づきませんが、要件にある**数万件**では処理量が桁違いになり、CPU を食いつぶして激遅になります。

2. **捨てられた大量の中間文字列が GC を圧迫する**:
   上のとおり `+=` のたびに古い文字列がゴミになります。n 件ぶんの巨大な“使い捨て文字列”が次々と生まれては捨てられ、
   **GC（＝使わなくなったメモリを自動で片付ける仕組み）**が頻繁に走ります。GC が動く間はアプリの処理が一瞬止まりがちで、
   バッチ全体の遅さ・カクつきの原因になります。速度だけでなくメモリの無駄遣いという意味でも損です。

3. **区切り文字・ヘッダの手組みで可読性が低く、エスケープも無い**:
   カンマや改行を手で1つずつ足していて、行の作り方があちこちに散らばっています。将来「列を1つ足す」ときに直し漏れが起きやすい形です。
   また顧客名にカンマが入ると列がずれてCSVが壊れます（本来はダブルクォートで囲むなどの**エスケープ**が必要）。今回の主役ではありませんが、
   「手組みは壊れやすい」という弱点として頭の隅に置いておきましょう。

## ⭕️ 改善案 (good/ 配下)

1. **`StringBuilder` で末尾に足していく**:
   `StringBuilder`（＝文字列を継ぎ足せる**書き換え可能な入れ物**）を1つ用意し、`append` で末尾に足すだけにします。
   同じ器を使い回すので全文コピーが起きず、処理量は件数に比例する **O(n)** に収まります。数万件でもスッと終わります。
   最後に `toString()` で1本の `String` に確定させて返します。

2. **別解：ストリーム＋`Collectors.joining` / `String.join`**:
   一覧を1件ずつ流して「1行の文字列」に変換し、`Collectors.joining("\n")` で改行を挟んで1本につなぐ書き方もあります。
   「1行をどう作るか」が1か所にまとまり、区切り文字の付け忘れも防げて読みやすくなります。`String.join` も同じ発想の道具です。

3. **（発展）CSVの中身は本来ライブラリに任せる**:
   カンマ入りの値のエスケープまできちんとやるなら、OpenCSV や comm('commons-csv) などの**CSV専用ライブラリ**に任せるのが安全です。
   今回は「連結の仕方」が主題なので `StringBuilder` を軸にしていますが、「手組みは壊れやすい」という感覚は持っておきましょう。

## 💬 レビューコメント例文

> `CsvReportBuilder`、ヘッダから明細まで素直に組み立てられていて、やりたいことがすぐ読めるのが良いですね。小さなデータではちゃんと動いています。

> 1点だけ、性能に効く大事なところを直しておきましょう。ループの中の `csv += ...` ですが、Java の `String` は「いちど作ったら中身を変えられない」ので、`+=` のたびに今までの全文をまるごとコピーした新しい文字列を作り直しているんです。件数が増えるほどコピー量が雪だるま式に増えて、数万件だと処理量がおよそ件数の二乗になり、急に激遅になります。捨てられた文字列がメモリ掃除（GC）も圧迫します。ここは `StringBuilder` を1つ用意して `append` で末尾に足していく形にすれば、コピーが起きず件数に比例する速さで済みます。

> 直し方はシンプルなので身構えなくて大丈夫。「ループの中で文字列を足すときは StringBuilder」は現場で何度も出てくる定番パターンなので、ここで覚えておくと今後ずっと効きますよ。余裕があれば `Collectors.joining` を使った書き方も見てみてください。
