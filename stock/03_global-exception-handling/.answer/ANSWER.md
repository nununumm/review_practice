## ❌ NGポイント (bad/ 配下)

1. **try-catch が全メソッドにコピペで散らばっている（横断的関心事の重複）**:
   `ProductController#getProduct`・`OrderController#getOrder`・`OrderController#createOrder`、
   すべてのメソッドが同じような try-catch を抱えている。「エラー処理」は本来どのAPIでも共通の"横串"の仕事（＝横断的関心事）なのに、
   各メソッドに手書きでコピペされている。エンドポイントが10個あれば10個に同じコードが増殖し、
   仕様変更（例：エラー形式を変える）のたびに全部を直して回る羽目になる。1か所直し忘れれば挙動がバラつく。

2. **例外の中身（メッセージ・スタックトレース）をそのままレスポンスに詰めて返す（情報漏洩）**:
   `body.put("error", e.getMessage())` や `e.toString()`、さらには `e.printStackTrace(new PrintWriter(sw))` で作ったスタックトレース全文を
   `body.put("trace", ...)` としてレスポンスbodyに入れて返している。
   これは「サーバの内部事情（クラス名・メソッド・DB構造・SQL・ファイルパスなど）」を外部にダダ漏れさせる行為。
   攻撃者に"攻めどころ"のヒントを与える立派なセキュリティ欠陥。加えて `e.printStackTrace()` は標準エラーに垂れ流すだけで、
   ログ基盤に乗らず後から検索・監視もできない。

3. **エラーなのに HTTP 200 OK を返す／ステータスがバラバラ**:
   `getProduct` はエラーでも `ResponseEntity.ok(body)`（＝200 OK）、`createOrder` も 200 OK、
   一方 `getOrder` は 500 を返している。同じ「見つからない」状況でも場所によって 200 だったり 500 だったり。
   フロントやAPI利用者は「HTTPステータスを見れば成功/失敗が分かる」ことを前提にしているのに、
   200なのに中身はエラー…では機械的に判定できず、リトライや画面表示の制御が壊れる。

4. **何でも `catch (Exception e)` で握って同じ扱い（例外の握りつぶし）**:
   「商品が見つからない(EntityNotFoundException)」も「入力が不正(IllegalArgumentException)」も「予期せぬ障害」も、
   全部ひとつの `catch (Exception e)` でまとめて捕まえ、同じレスポンスにしている。
   本当は「見つからない=404」「入力ミス=400」「サーバ障害=500」と区別すべきなのに、
   せっかく Service が独自例外(EntityNotFoundException)を投げても、その区別を潰してしまっている。

5. **`@ControllerAdvice` / `@ExceptionHandler` による集約が一切ない**:
   Spring には「例外処理を1か所に集める仕組み」があるのに使っていない。だから 1〜4 の問題がすべて発生している。
   仕組みを使えば、Controller は例外を投げっぱなしにして、受付係が一括で正しいステータス・形式に変換できる。

## ⭕️ 改善案 (good/ 配下)

1. **`@RestControllerAdvice` で例外処理を1か所に集約する**:
   `GlobalExceptionHandler` を作り、`@ExceptionHandler` で例外の種類ごとに処理を割り当てる。
   これで全 Controller から try-catch を"完全に"追放できる（横断的関心事を1枚にまとめた）。

2. **独自例外を「意味」で分け、正しいHTTPステータスへマッピングする**:
   `ResourceNotFoundException → 404`、`InvalidRequestException → 400`、`ConflictException → 409`、
   それ以外の想定外 → 500。Service は状況に応じて意味のある例外を投げ分けるだけでよい。

3. **統一エラーレスポンスDTO（`ErrorResponse`）を返す**:
   `timestamp / code / message` の決まった形で返す。内部詳細（スタックトレース・DB情報）は絶対に含めない。
   想定外エラー(500)のときは利用者に固定の一般メッセージだけを返し、原因調査に必要なスタックトレースは
   **ログ側にだけ** `log.error("...", e)` で残す（＝「詳しくはログへ、利用者へは最小限」の使い分け）。

4. **Controller を"例外を投げるだけ"の薄い形にする**:
   分岐や try-catch を書かず、正常系だけを記述。作成APIは 201 Created を返し、入力チェックは `@Valid` + リクエストDTOで入口に寄せる。

## 💬 レビューコメント例文

> エラー処理、各メソッドに丁寧に書いてくれてありがとう！ ここからもう一段良くできそうです。
> いま try-catch が全メソッドにコピペで入っていて、エンドポイントが増えるほど同じコードが増殖し、直し漏れの温床になりそうです。
> Spring には `@RestControllerAdvice` + `@ExceptionHandler` という「例外処理を1か所に集める仕組み」があるので、
> そこへ寄せて Controller からは try-catch を無くしませんか？ Controller は例外を投げっぱなしにするだけで済み、ぐっと読みやすくなります。
> あわせて2点だけ相談させてください。1つは、`e.getMessage()` やスタックトレースをそのままレスポンスに返している箇所です。
> 内部のクラス名やDB構造が外に漏れると攻撃のヒントになってしまうので、利用者には固定メッセージだけ返し、詳細はログ(`log.error`)に残す形にしましょう。
> もう1つは、エラーでも 200 OK が返っていたり、場所によって 500 だったりステータスがまちまちな点です。
> 「見つからない=404 / 入力ミス=400 / 想定外=500」と例外の種類ごとに揃えると、フロント側が成功・失敗を機械的に判定できて助かります。
> ここは設計の"型"を覚えれば一気に楽になる部分なので、一緒に整えていきましょう！
