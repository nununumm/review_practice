## ❌ NGポイント (bad/ 配下)

1. **外部から来た信頼できないバイト列を無検証でデシリアライズしている（＝リモートコード実行の温床）**: `new ObjectInputStream(...).readObject()` は、バイト列を Java オブジェクトに復元する処理（＝デシリアライズ：バイト列を元のオブジェクトに戻すこと）。ここに Cookie やリクエストパラメータという「攻撃者が中身を自由に差し替えられる外部入力」をそのまま流し込んでいる。Java ネイティブシリアライズは、復元の途中で相手のクラスの内部処理が勝手に動く仕組みになっており、攻撃者が世の中のライブラリを組み合わせた「細工したバイト列（＝ガジェットチェーン）」を送ると、復元しただけでサーバ上で任意のプログラムを実行させられてしまう（＝リモートコード実行＝RCE：外部から任意のコードを走らせる攻撃）。これは Java で最も有名な脆弱性パターンの1つで、「信頼できない入力を `ObjectInputStream` に渡さない」が鉄則。たとえるなら、差出人不明の小包を中身も確かめずに開けて、書いてある指示どおりに動いてしまうようなもの。

2. **`readObject()` の戻り値を無検査でキャストしている**: `(Cart) ois.readObject()` は、復元されたものが本当に `Cart` かを確かめずに「これは Cart だ」と決めつけて変換している（＝無検査キャスト）。攻撃者や不整合なデータで別の型が入ってくると、その瞬間に `ClassCastException`（＝型の取り違えによる実行時エラー）で落ちる。本来は `instanceof`（＝「これは Cart 型か？」を確かめる演算子）で型を確認してから扱うべき。

3. **ストリームを try-with-resources で閉じておらず、例外時にリークする**: `ByteArrayInputStream` と `ObjectInputStream` を開きっぱなしで、途中で例外が出ると `close()` されないまま処理を抜けてしまう（＝リソースリーク：使い終わった資源を解放し忘れること）。開いた資源は必ず閉じる必要があり、`try (...)` の形（＝try-with-resources：try のカッコ内で開いた資源を、正常時も例外時も自動で閉じる書き方）を使うのが定石。

4. **`catch (Exception e)` で握りつぶして null を返している**: すべての例外を1つの `catch` でまとめて捕まえ、中身を見ずに `return null` している（＝例外の握りつぶし）。`ClassNotFoundException`（クラスが見つからない）や本来気づくべき異常もすべて `null` に化けてしまい、「なぜ復元できなかったのか」という原因が完全に失われる。呼び出し側も `null` が返ってきた理由が分からず、デバッグのときにログに手がかりが1つも残らない。例外は種類ごとに意味のある形で扱い、原因（元の例外）を保持したまま投げ直すべき。

## ⭕️ 改善案 (good/ 配下)

1. **信頼できない入力は Java ネイティブシリアライズではなく JSON で復元する**: ブラウザから受け取る値は JSON 文字列にし、Jackson の `objectMapper.readValue(json, Cart.class)` で「復元先の型を Cart に限定して」戻す。JSON は「ただのデータ」であり、復元の途中で任意のコードが動くことはないので、RCE の入口を根本から塞げる。

2. **復元先の型を明示し、無検査キャストを無くす**: `readValue(json, Cart.class)` のように戻り値の型が最初から `Cart` に固定されるので、`(Cart)` の無検査キャストそのものが不要になる。ネイティブシリアライズを避けられない場合も `instanceof` で型を確認してから扱う。

3. **どうしても ObjectInputStream を使う場合は ObjectInputFilter でホワイトリスト＋try-with-resources**: `ObjectInputFilter`（＝復元してよいクラスの許可リスト）を設定し、許可した型以外は復元前に拒否する。ストリームは try-with-resources で確実に閉じる（good 版のコメント内に実装例あり）。

4. **例外は握りつぶさず、意味のある形で投げ直す**: 空入力や壊れた JSON は `IllegalArgumentException` に変換し、元の例外を原因（`cause`）として保持したまま投げる。こうすればログに根本原因まで残り、`null` に化けて手がかりが消えることもない。

## 💬 レビューコメント例文

> カートをゲストでも保持できるようにする発想、いいですね！ ただ1点、これはセキュリティ上どうしても直してほしい重要な箇所があります。いまカートの復元を `ObjectInputStream.readObject()` でやっていますが、ここに Cookie やパラメータという「外部から中身を自由に差し替えられる値」を渡しているのが危険なんです。Java のこの復元処理は、実は復元の途中で相手のクラスの処理が動く仕組みで、細工したバイト列を送られると「復元しただけでサーバ上で任意のプログラムが実行される」攻撃（リモートコード実行）につながります。Java で一番有名な脆弱性パターンのひとつで、ここは「信頼できない入力を readObject に渡さない」が鉄則です。
>
> 直し方としては、カート状態を JSON でやり取りして、Jackson の `readValue(json, Cart.class)` で「復元先を Cart に限定して」戻すのがおすすめです。JSON はただのデータなので、この攻撃の入口自体が無くなりますし、型が最初から Cart に決まるので、いまの `(Cart)` のキャストも要らなくなります。
>
> ついでにあと2つだけ。ストリームは `try (...)` の形で開くと、例外が出ても自動で閉じてくれてリークを防げます。それと `catch (Exception e)` で `null` を返している部分は、何が起きても原因が消えてしまうので、壊れたデータのときは意味のある例外に変えて投げておくと、後で障害を追うときに自分たちが助かります。セキュリティのところだけは最優先で、一緒に直しましょう！
