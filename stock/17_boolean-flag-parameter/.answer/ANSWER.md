## ❌ NGポイント (bad/ 配下)

1. **真偽値の引数（boolean parameter）が乱立していて、呼び出し側を見ても意味が読めない**: `send(user, message, true, false, true, false, false, true)` のように、true / false が何個も並んでいる。呼び出しコードだけを見ても「3番目の true は何？」「5番目の false は？」がまったく分からない（＝メソッド定義まで開かないと意味が取れない）。真偽値は「はい/いいえ」しか表せないので、引数が増えるほど並び順を間違えても気づけず、`useSms` と `usePush` を取り違えるようなバグが静かに混入する。名前付きの列挙型（＝決まった選択肢を持つ型）やオプションオブジェクトにすれば、`.via(MAIL, PUSH).mode(URGENT)` のように読むだけで意図が分かる。

2. **1つの `send` メソッドが複数の責務を抱え、フラグの if 分岐だらけになっている**: メール送信・SMS送信・プッシュ送信という本来別々の処理が、`if (useMail) {...} if (useSms) {...} if (usePush) {...}` として1メソッドに全部詰め込まれている。さらにその中で `isUrgent` / `isSilent` の分岐が入れ子になり、見通しが悪い。1つのメソッドが「あれもこれも」やっている（＝単一責任の原則に反する）ため、メールの仕様だけ直したいのにSMSやプッシュのコードまで読む羽目になり、修正時に無関係な箇所を壊すリスクが高い。手段ごとにクラスを分ける（＝Strategy）べき。

3. **矛盾する組合せ（緊急かつ静か）を型で防げていない**: `isUrgent`（緊急）と `isSilent`（通知音なし）を、それぞれ独立した boolean で受け取っている。そのため「緊急なのに音を鳴らさない」という意味の通らない組合せ（`isUrgent=true, isSilent=true`）を、コンパイルエラーにもならず普通に渡せてしまう。実際 bad のメール処理は `isSilent` を完全に無視しており、指定しても効かない（＝仕様が引数の型に表れていない）。「どちらか一方しか選べない」性質は、1つの列挙型（NORMAL / URGENT / SILENT）にまとめれば型として表現でき、矛盾する状態をそもそも作れなくなる。

4. **引数違いの同名メソッド（オーバーロード）が乱立し、組合せ爆発を起こしかけている**: `send(...)` が引数の数だけ何種類もあり、さらに `sendUrgent(...)` まで生えている。条件が1つ増えるたびに「この引数パターンも用意しないと」となり、メソッドの数が掛け算で膨らんでいく（＝組合せ爆発）。どのメソッドがどのデフォルト値を渡しているのかは中を読まないと分からず、`sendUrgent` が内部で `isSilent=true`（緊急なのに静か）を渡しているような、気づきにくい不整合の温床にもなる。

5. **手段や優先度を、意味の限られた型（boolean・文字列）で表している**: 送信手段を `useMail` / `useSms` / `usePush` の3つの boolean で、プッシュの優先度を `"high"` / `"normal"` という文字列（マジックストリング）で表している。boolean は選択肢を型で縛れず、文字列は `"hgih"` のようなタイプミスをしてもコンパイルは通ってしまう（＝実行して初めて壊れる）。列挙型 `NotificationChannel` / `DeliveryMode` にすれば、選べる値が型で限定され、打ち間違いはコンパイル時点で弾かれる。

## ⭕️ 改善案 (good/ 配下)

1. **手段・送り方を列挙型にする**: 送信手段は `NotificationChannel`（MAIL / SMS / PUSH）、送り方は `DeliveryMode`（NORMAL / URGENT / SILENT）という列挙型で表す。boolean や文字列と違い、選べる値が型で決まっているので、指定ミスがコンパイル時に分かる。

2. **矛盾する組合せを型で作れなくする**: 「緊急」と「静か」を別々の boolean にせず、`DeliveryMode` の1つの選択肢にまとめる。1つしか選べないので、「緊急かつ静か」という矛盾はそもそも構築不可能になる。

3. **引数はオプションオブジェクト＋ビルダーに集約する**: フラグの羅列をやめ、`NotificationRequest` 1つを渡す。`NotificationRequest.builder().to(user).message(...).via(MAIL, PUSH).mode(URGENT).trackRead().build()` のように、呼び出しコードが説明文のように読める（＝自己説明的なAPI）。オーバーロードの乱立も不要になる。

4. **手段ごとに処理を分割する（Strategy）**: `ChannelSender` という共通の窓口（インターフェース）を作り、`MailChannelSender` / `SmsChannelSender` / `PushChannelSender` に分ける。各クラスは1手段分の責務だけを持ち、`NotificationService` は「指定された手段へ振り分けるだけ」に徹する。新しい手段（例: LINE）が増えても、実装クラスを1つ足すだけで済む（＝拡張に強い）。

5. **入力の検証を1か所に寄せる**: 必須項目や「手段が空でないか」を `build()` の中で一度だけチェックし、おかしな状態のオブジェクトをそもそも作らせない。

## 💬 レビューコメント例文

> 通知まわり、メール・SMS・プッシュを1つの窓口でまとめて送れるようになっていて、機能としてはちゃんと揃っていますね！ そのうえで、これから条件が増えても崩れにくい形に一緒に整えたいです。
>
> まず一番気になったのが、呼び出し側の `send(user, message, true, false, true, false, false, true)` です。正直、この true / false の列だけ見ても何を指定しているのか読み解けなくて、`send` の定義まで開かないと意味が取れないんですよね。並び順を1つ間違えても気づけないのも怖いところです。ここは、手段を `NotificationChannel`（MAIL/SMS/PUSH）、送り方を `DeliveryMode`（NORMAL/URGENT/SILENT）という列挙型にして、`NotificationRequest.builder().to(user).message(...).via(MAIL, PUSH).mode(URGENT).build()` のように「読めば分かる」形にできると、ぐっと安全になります。
>
> それと、`isUrgent` と `isSilent` を別々の boolean で持っていると「緊急なのに静かに送る」という矛盾した指定ができてしまいます（実際いまメール側は isSilent を見ていないので、指定しても効かないんです）。この2つは「どちらか一方」なので、1つの列挙型にまとめてしまえば、矛盾する組合せがそもそも作れなくなります。
>
> 最後に、`send` の中でメール・SMS・プッシュを全部抱えていて分岐が深いので、手段ごとに小さなクラス（`ChannelSender`）へ切り出しませんか。そうするとメールの仕様変更でSMSのコードを読まずに済みますし、`sendUrgent` みたいなオーバーロードを増やさずに済みます。どれも「今は動くけど、機能追加のたびに効いてくる」タイプの整理なので、ここで土台を作っておきましょう！
