## ❌ NGポイント (bad/ 配下)

1. **`divide` に桁数・丸め方(`RoundingMode`)を指定しておらず、割り切れないと例外で落ちる（核心・気づきにくい）**: `total.divide(new BigDecimal(people))` は、`BigDecimal` のスケール（小数第何位まで）と丸め方を指定しない割り算。割り切れる場合は問題ないが、たとえば 1000円 ÷ 3人 のように**割り切れない瞬間に `ArithmeticException: Non-terminating decimal expansion`（無限小数で表しきれない）で落ちる**。割り勘は割り切れないのがむしろ普通なので、ごく当たり前の入力で本番が落ちる。`divide` は必ず「何桁まで・どう丸めるか」をセットで指定しなければならない。

2. **`new BigDecimal(double)` を使っており、生成時点で誤差が入る（金銭・正確性）**: `new BigDecimal(0.1)` は「0.1 ちょうど」ではなく `0.1000000000000000055511151231257827021181583404541015625` という誤差を含んだ値になる。`double` が 0.1 を正確に表せないためで、その不正確な値がそのまま BigDecimal に取り込まれる。**せっかく誤差を避けるために BigDecimal を使っているのに、生成方法のせいで誤差が入る**という本末転倒。文字列 `new BigDecimal("0.1")` か `BigDecimal.valueOf(0.1)` から作るのが正解。`taxIncluded` が引数を `double` で受けているのも、同じ理由で誤差の入口になる。

3. **人数の妥当性チェックが無い（低〜中）**: `people` が 0 だと（丸めを指定しても）ゼロ除算で `ArithmeticException`、負数だとマイナスの按分になる。割り算の前に `people >= 1` を確認すべき。

4. **税率 `0.1` のマジックナンバー（低）**: 何の値か分かりづらく、変更にも弱い。名前付き定数（できれば文字列から生成）にすべき。

5. **端数を誰が負担するかの方針が不明（設計）**: 割り勘は「切り上げ／切り捨て／四捨五入」で1人あたりが変わり、合計が総額と一致しないことがある。丸め方を明示することは、この方針を決めることでもある。

## ⭕️ 改善案 (good/ 配下)

1. **`divide` は桁数と `RoundingMode` を必ず指定する**: `total.divide(BigDecimal.valueOf(people), 0, RoundingMode.UP)` のように、円単位・丸め方を明示する。要件に応じて `HALF_UP`（四捨五入）や `FLOOR`（切り捨て）を選ぶ。

2. **`BigDecimal` は文字列 or `valueOf` から作る**: `new BigDecimal("0.10")` や `BigDecimal.valueOf(...)` を使い、`new BigDecimal(double)` は避ける。金額の入り口も `double` ではなく `BigDecimal` で受け取る。

3. **人数をガードする**: `if (people <= 0) throw ...` で不正な人数を弾く。

4. **税率を名前付き定数にする**: `TAX_RATE = new BigDecimal("0.10")` として意味を明示し、文字列から生成して誤差を防ぐ。

5. **丸め方針を明示して金額を整数円に整える**: `setScale(0, RoundingMode.HALF_UP)` などで最終的な円単位を確定させる。
