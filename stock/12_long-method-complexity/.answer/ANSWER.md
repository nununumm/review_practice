## ❌ NGポイント (bad/ 配下)

1. **1メソッドが長大で、深いネストの「アロー型」になっている（可読性・保守性）**: `validateAndGetError` は70〜90行あり、`if` の中に `if`、その中にまた `if`…と入れ子が10段以上えぐれている。コードの見た目が右へ右へと突き出て、真ん中がとがった矢印（アロー）のように見える形で、**アロー型アンチパターン**（＝ネストが深すぎて読めなくなる悪い書き方）と呼ばれる。人間の頭は「今どの条件の中にいるか」を数段しか覚えられないので、奥に行くほど「ここに来る条件は何だっけ？」が分からなくなり、修正時にバグを入れやすい。

2. **ガード節（早期return）が無く、正常系がネストの一番奥に埋もれている（可読性）**: 「おかしい入力を先に弾く」のではなく、「正しい場合だけどんどん奥に進む」書き方になっている。そのため「検証が全部通ったOKの状態」が、いちばん深い場所（`// ここまで全て通れば検証OK` のあたり）にひっそり埋もれている。読み手は正常系を確認するために全部の `if` を潜らないといけない。**ガード節（＝異常なら関数の入り口で即 return / throw して、以降は正常系だけを平らに書く手法）**を使えば、ネストはほぼ無くなり、上から順に読める。

3. **検証失敗を「例外」ではなく boolean／文字列メッセージで表し、`return false`（相当）を乱発している（設計・エラー設計）**: 失敗を戻り値の文字列（エラーメッセージ）で表現し、途中で `return "○○が不正です"` を連発している。この方式は、(a) 呼び出し側がその戻り値を**チェックし忘れてもコンパイラが警告してくれない**（＝バグに気づけない）、(b) 「成功」と「失敗」がどちらも文字列なので区別しづらい、(c) メッセージ文字列でしか原因を判別できず、プログラムから扱いにくい、という弱点がある。失敗は**専用の例外**（＝処理を中断し「ここがダメ」と型と一緒に伝える仕組み）で返すほうが、呼び出し側が握りつぶしにくく、原因も明確になる。

4. **「null かつ 空文字」チェックなど同種の処理が各項目でコピペ重複している（DRY違反）**: 顧客名・メール・電話・住所のそれぞれで `xxx != null && !xxx.trim().equals("")` をまるまる書き写している。**DRY原則（＝同じことを繰り返し書かない、Don't Repeat Yourself）**に反しており、たとえば「空白だけの入力も弾くよう仕様変更」となったとき、4か所すべてを直す必要がある（1か所直し忘れてバグ、が起きやすい）。共通処理は1つのメソッドにまとめるべき。

5. **文字数上限20・電話桁数などのマジックナンバーが直書きされている（可読性・保守性）**: `<= 20`、`length() == 10 || length() == 11`、`quantity <= 99` などの数字がコードに直に埋め込まれている。**マジックナンバー（＝意味の説明がない裸の数字）**は、「この20は何の20か」がコードだけでは分からず、同じ意味の数字が複数箇所に散ると変更漏れの原因になる。名前付き定数（`MAX_CUSTOMER_NAME_LENGTH` など）にすれば意味が読み取れ、変更も1か所で済む。

6. **検証メソッドの中に、検証以外の処理（クーポン在庫の減算・DB更新）が混ざっている（単一責任違反）**: `validateAndGetError` という名前なのに、中でクーポンの在庫を1減らし、利用回数を増やして `couponRepository.save(...)` や `orderRepository.incrementCouponUsage(...)` まで実行している。これは**単一責任の原則（＝1つのクラス／メソッドは1つの仕事だけを持つ、SRP）**に反する。副作用（データ書き換え）が混ざっていると、「入力チェックだけしたい」場面でも勝手にDBが更新されてしまい、危険で再利用もテストもしづらい。検証は「調べるだけ（副作用なし）」に保つのが鉄則。

## ⭕️ 改善案 (good/ 配下)

1. **ガード節で早期returnし、ネストを平らにする**: `if (request == null) throw ...` のように異常系を入り口で弾き、以降は正常系だけを段差なく並べる。矢印型のネストが消え、上から素直に読める。

2. **項目ごとの小さな private メソッドに分割する**: `validateCustomerName` / `validateEmail` / `validatePhone` … と1項目1メソッドに切り出す。`validate` 本体は「何を検証するか」の一覧になり、各メソッドは短くて追いやすい。

3. **失敗は意味のある例外で返す**: `OrderValidationException`（原因メッセージ付き）を投げる。呼び出し側が握りつぶしにくく、「成功＝例外なし／失敗＝例外あり」と型で明確に区別できる。（結果オブジェクトを返す方式でもよい。）

4. **「null または 空文字」チェックを共通メソッド `requireText` に集約する**: 同じ判定を1か所にまとめ、仕様変更もそこだけ直せばよいようにする（DRY）。

5. **マジックナンバーを名前付き定数にする**: `MAX_CUSTOMER_NAME_LENGTH = 20` などにして、数字の意味を名前で示し、変更箇所を一元化する。

6. **検証と副作用（DB更新）を分離する**: クーポンの在庫減算・利用回数更新は検証サービスから外し、`CouponService.consume(...)`（`@Transactional` 付き）に移す。検証は副作用ゼロで何度でも安全に呼べるようになり、消費処理は別々にテストできる。

> 補足：`bad` では、電話番号の数字判定で数字以外を見つけても `phoneIsNumber = false` にするだけでループを抜けず最後まで回している（早期に判定を打ち切れる場面で無駄がある）。`good` の `isAllDigits` は見つけた時点で `return false` して打ち切っている。
