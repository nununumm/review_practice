## ❌ NGポイント (bad/ 配下)

1. **拡張for文で回している最中に `remove` している（`ConcurrentModificationException`）**: `cleanupUnavailable()` は `for (CartItem item : cartItems)` で回しながら、その中で `cartItems.remove(item)` している。拡張for文（＝`for (要素 : リスト)` の書き方。裏でイテレータという「順番に取り出す係」が動いている）は、回している最中にリストの中身が変わると `ConcurrentModificationException`（＝反復中にコレクションを書き換えたときに投げられる例外）で即落ちする。本番で在庫切れ商品が1つでもあると、この処理は基本的に例外で止まる。

2. **インデックス付きforで削除すると要素を飛ばして消し残す（オフバイワン的バグ）**: `cleanupByIndex()` は `for (int i = 0; ...) ` で回しながら `cartItems.remove(i)` している。ある要素を消すと、その後ろの要素が1つ前へ「詰めて」きて番号がズレる。なのに `i` は次に進んでしまうため、詰めてきた要素を**素通り（スキップ）して消し残す**。たとえば販売終了が2つ隣り合っていると、2つ目が消えずに残る。「動いてるように見えるのに、たまに消え残る」というタチの悪いバグ。

3. **カートの中身を `@Service` のインスタンスフィールドで共有している（スレッド安全でない）**: `private List<CartItem> cartItems` をサービスのフィールドに持っている。`@Service`（＝Springが**1個だけ**作って全リクエストで使い回す部品）にデータを持たせると、Aさんのカートと Bさんのカートが**同じ入れ物を共有**してしまう。しかも `ArrayList` は非スレッドセーフ（＝複数のスレッドが同時に読み書きすると壊れる作り）なので、同時アクセスで中身が飛んだり、最悪データが壊れる。ユーザーごとに分かれているべきカートが混ざる、重大な設計ミス。

4. **getter でフィールドの List をそのまま返している（防御的コピーが無い）**: `getCartItems()` が内部の `cartItems` を**そのまま**返している。受け取った側が `list.add(...)` や `list.clear()` をすると、サービス内部の状態まで書き換わってしまう（＝カプセル化が破れる。外から内部をいじり放題）。返すときは複製や変更不可リストにして「見せるけど触らせない」のが鉄則。

5. **`null` を `add` してしまい、後段の集計で `NullPointerException`**: `addItemByName()` は名前で商品を探すが、見つからないと `found` が `null` のまま `cartItems.add(found)` してしまう。リストに `null` が混じると、あとで合計を出す `item.getQuantity()` の所で `NullPointerException`（＝中身が無いのに使おうとして落ちる）になる。しかも落ちる場所が「追加した時」ではなく「後で集計した時」なので、原因の特定がとても難しい。

## ⭕️ 改善案 (good/ 配下)

1. **削除は `removeIf`（または `Iterator.remove`）で安全に**: `working.removeIf(item -> 条件)` にすると、反復中の削除を内部で正しく処理してくれるので `ConcurrentModificationException` も消し残しも起きない。「消したい条件」を1行で書けて意図も明確。

2. **共有可変フィールドをやめてローカル変数／引数にする**: カートの中身をフィールドで持たず、メソッドの**引数**で受け取り**戻り値**で返す「状態を持たない（ステートレスな）」設計に変える。`@Service` は使い回されても各リクエストが自分のデータだけを扱うので、混線もスレッド事故も起きない。（どうしてもリクエストをまたいで保持したいなら、DBやセッション、`@Scope("request")` などリクエストごとの器を使う。）

3. **返すときは `List.copyOf` / 変更不可リストで防御する**: 戻り値を `List.copyOf(working)` にすると、呼び出し側が `add/remove` しても例外になり内部を壊せない。また作業前に `new ArrayList<>(cart)` で複製（＝防御的コピー）してから触ることで、渡された元のリストも書き換えない。

4. **`null` を弾く**: 追加時は `Objects.requireNonNull(item, ...)` でその場で分かりやすく例外にし、原因を早く特定できるようにする。集計側でも `removeIf` で null を除去し、念のため `item != null` を確認してから足すことで、後段の `NullPointerException` を根本から断つ。

## 💬 レビューコメント例文

> カート整理のロジック、やりたいことは伝わりました！ ただ、このままだと本番で落ちるポイントがいくつかあるので一緒に直しましょう。
>
> まず削除の書き方です。拡張for文で回しながら `list.remove()` を呼ぶと `ConcurrentModificationException`（回してる最中にリストを触ると出る例外）で止まっちゃうんです。index版のほうも、1つ消すと後ろが前に詰めてくるのに `i` が進むので、隣り合った対象を消し残すクセがあります。ここは両方 `removeIf(...)` に置き換えると、条件も1行で書けて事故も起きなくなりますよ。
>
> それから設計で一番大事な点を。カートの中身を `@Service` のフィールドで持っているんですが、`@Service` はアプリ全体で1個を使い回す部品なので、これだと全ユーザーのカートが同じ入れ物を共有してしまいます（`ArrayList` は複数スレッド同時アクセスにも弱いです）。カートはメソッドの引数で受け取って戻り値で返す形にして、サービス自身は状態を持たないようにしましょう。
>
> 最後に細かいけど効くやつを2つ。`getCartItems()` が内部リストをそのまま返しているので、呼び出し側から中身をいじれてしまいます。`List.copyOf(...)` で「見せるけど触らせない」形にしておくと安心です。あと名前検索で見つからなかったときに `null` を add していて、これが後の集計で NPE の火種になります。見つからなければ追加しない、追加値は `Objects.requireNonNull` で弾く、にしておきましょう。どれも「動いてるように見えて本番で効いてくる」タイプなので、ここで潰しておきたいです！
