## ❌ NGポイント (bad/ 配下)

1. **デメテルの法則違反（トレインレック＝列車事故）**: `order.getCustomer().getAddress().getZipCode()` のように、ドット（.）でメソッド呼び出しを数珠つなぎにしています。デメテルの法則（＝「直接の知り合いとだけ話す」「相手の内部を辿らない」という設計の指針。別名：最小知識の原則）に反します。たとえるなら、友達に用事を頼むのに「友達の財布の中の、そのまたカードの暗証番号」まで自分の手で掘りに行くようなもの。`order` の「直接の友達」は Customer までですが、その先の Address まで手を突っ込んで内部を掘っています。連結した貨車のように呼び出しが連なる様子から「トレインレック（列車事故）」とも呼ばれます。

2. **強すぎる結合（＝依存の強さ）**: 呼び出し側であるこの Service が、Order → Customer → Address という「他人の家の間取り」を丸ごと知ってしまっています。結合（＝クラス同士の依存の強さ。強いほど片方の変更が他方を壊す）が強い状態です。将来 Address の持ち方を変えたり、住所の階層を1段増やしたりすると、この Service まで芋づる式に修正が必要になります（変更に弱い）。

3. **NullPointerException（NPE）の地雷原**: 連鎖の途中（customer が null、address が未登録で null など）で、どこか1つでも null だと即 NPE で落ちます。しかも `getCustomer().getAddress().getZipCode()` のどのドットで落ちたのかがスタックトレースから分かりにくく、原因調査に時間がかかります。

4. **テストしづらい**: この1メソッドを試すだけなのに、Order・Customer・Address の入れ子になったモック（＝テスト用の偽物オブジェクト）を全部組み立てないと動きません。準備が重く、テストを書く気が失せてしまいます。

## ⭕️ 改善案 (good/ 配下)

1. **Tell, Don't Ask（聞くな、命じよ）で"持っている側"に窓口を作る**: 「相手の中身を聞き出して自分で処理する」のではなく、「相手に"やって"と頼む」形にします。ラベルに必要な情報は Order が（Customer/Address 経由で）持っているので、`order.getShippingLabelInfo()` のような「必要な情報をまとめて返す窓口メソッド」を Order 側に用意します。呼び出し側は直接の友達である order とだけ話し、その先の構造を知らずに済みます。

2. **内部構造を隠して結合を弱める**: Customer / Address を辿る責務を Order 自身に移すことで、Service は Order の内部構造を知らなくなります。将来 Address の作りが変わっても、直すのは Order の中だけ。Service は無傷です（変更に強い）。

3. **null 安全は"持っている側"で保証する**: null チェックや `Optional`（＝「値があるかもしれない箱」）での安全な組み立ては、内部構造を知っている Order 側でまとめて面倒を見ます。呼び出し側に null 地雷が漏れてきません。

4. **小さな値オブジェクトにまとめる**: ラベルに載せる項目だけを持つ `ShippingLabelInfo` のような小さな入れ物を返せば、テストもその窓口メソッド1つを差し替えるだけで済み、入れ子モックが不要になります。

## 💬 レビューコメント例文

> 配送ラベルに必要な項目（郵便番号・都道府県・宛名）を集めて1つの文字列に組み立てる、という処理の流れ自体はとても明快で読みやすいです。やりたいことがすっと頭に入ってきました。

> 1点だけ設計の相談を。今 `order.getCustomer().getAddress().getZipCode()` のようにドットで数珠つなぎに辿っていますが、これは「デメテルの法則（＝"直接の知り合いとだけ話す"、相手の内部までは掘らない、という指針）」の観点だと少し遠くまで手を伸ばしている状態なんです。Service が Order → Customer → Address の内部構造を全部知ってしまうので、将来 Address の持ち方を変えたときにここまで一緒に壊れてしまうのと、途中が null だと NPE で落ちてどこが原因か追いにくいのが気になります。そこで「Tell, Don't Ask（相手の中身を聞かず、欲しいものを相手に頼む）」の形にして、Order 側に `getShippingLabelInfo()` のような窓口メソッドを用意し、Service は `order` にだけ「ラベル情報ちょうだい」と頼む形にしてみませんか。null の面倒も持っている Order 側で見られるので、堅牢さもテストのしやすさも上がります。
