## ❌ NGポイント (bad/ 配下)

1. **サービスに `@Transactional` が無く、LAZY な明細をトランザクションの外で触っている（LazyInitializationExceptionの温床）**: 明細 `lines` は `fetch = FetchType.LAZY`（＝遅延ロード：必要になった瞬間に初めてDBへ取りに行く設定）になっている。ところが `findOrders()` にも呼び出し側にも `@Transactional`（＝DBとのやり取りをひとまとまりにし、その間だけDBセッションを開いておく印）が無い。JPAでは、DBセッション（＝DBとの接続の会話）が開いている間しか遅延ロードできない。`findOrders()` を抜けた時点でセッションは閉じるので、その後コントローラで `order.getLines()` を呼ぶと「もう会話が終わってるのに続きを取りに来た」状態になり `LazyInitializationException` で落ちる。たとえるなら、店員に「あとで在庫を確認します」と言っておきながら、店を閉めてシャッターを下ろした後に在庫を聞きに戻るようなもの。よくある「動いてるように見える」ケースは OSIV（Open Session In View＝リクエストの間ずっとセッションを開けっ放しにする既定機能）に頼っている状態で、これは事故を先送りしているだけの危うい作り。境界（どこまでがトランザクションか）をサービスで明示すべき。

2. **コントローラのループ内で毎回 `getLines()` を呼び、N+1問題を起こしている**: `findAll()` でまず注文を取り（SQL 1回）、そのあとループの中で注文1件ごとに `getLines()` を呼ぶと、明細を取るSQLがそのたびに1回ずつ飛ぶ。注文が100件あれば「1（注文一覧）＋100（各明細）＝101回」のSQLが発行される。これが N+1問題（＝1回で済むはずが、件数Nの分だけSQLが増殖する定番の性能事故）。件数が増えるほどDBへの往復が雪だるま式に増え、一覧がどんどん遅くなる。明細は「まとめて1回で取る」べき。

3. **`findAll()` で全件取得している（ページングが無い）**: 注文をページ分割せず全部読み込んでいる。N+1と重なると被害が倍増し、注文が数万件になった瞬間、SQLの回数もメモリも一気に膨れて固まる。一覧は必ず `Pageable`（＝1ページ分だけ切り出す仕組み）を受け取るべき。

4. **Entity（Order／LAZYプロキシ入り）を直接レスポンスに返している**: コントローラが `List<Order>` をそのまま返している。Order は LAZY な `lines` を抱えたままなので、JSON化（＝レスポンスを文字列に変換する処理）の途中で遅延ロードが走り、やはり LazyInitializationException で落ちたり、意図しない明細まで芋づるで出力されたりする。外に返す形は、必要な項目だけを詰めた DTO（＝Data Transfer Object：受け渡し用の入れ物）に切り離すべき。

5. **コントローラが集計ロジック（合計点数の計算）を持ってしまっている**: 本来サービス（業務ロジックの置き場）でやるべき合計計算を、コントローラ（受け口）が抱えている。役割がにじむと、テストしづらく再利用もしづらい。集計はトランザクション内のサービスに寄せるべき。

## ⭕️ 改善案 (good/ 配下)

1. **サービスメソッドに `@Transactional(readOnly = true)` を付ける**: 明細（LAZY）を触る処理を、セッションが開いているトランザクションの中に閉じ込める。読み取りだけなので `readOnly = true` にして最適化を効かせる。トランザクション内で DTO へ詰めきってから返すので、外で遅延ロードして落ちることがない。

2. **`JOIN FETCH`（または `@EntityGraph`）で注文と明細を1回のSQLでまとめて取る**: `@Query("select distinct o from Order o left join fetch o.lines")` のように書けば、注文と明細を1発のSQLで結合取得でき、N+1が消える。`distinct` は明細の数だけ注文行が重複するのを1件にまとめるための指定。

3. **`Pageable` を受け取りページングする**: `Page<Order>` で1ページ分だけ取得し、`Page<OrderSummary>` として返す。件数が増えても破綻しない。

4. **応答用の DTO（`OrderSummary`）に詰め替えて返す**: Entity ではなく、`id / customerName / totalQuantity` だけを持つ DTO に変換して返す。LAZYプロキシを外に出さないので JSON化で落ちることもない。

5. **集計はサービス（トランザクション内）で行う**: 合計点数の計算をサービスに寄せ、コントローラは「受け取って返すだけ」にする。役割がきれいに分かれ、テストもしやすい。

## 💬 レビューコメント例文

> 注文と明細をたどって合計を出す流れ、やりたいことはしっかり形になっていますね。ここは JPA の遅延ロードとトランザクションが絡む、みんなが一度はハマるポイントなので、一緒に整理しましょう。
>
> まず一番大事なのが、明細（lines）が LAZY なのに、それを触っているのがトランザクションの外（コントローラ）になっている点です。JPAは「DBとの会話（セッション）が開いている間」しか遅延ロードできないので、サービスを抜けたあとに `getLines()` を呼ぶと `LazyInitializationException` で落ちます。いまたまたま動いて見えるとしたら OSIV に助けられているだけで、これは事故を先送りしている状態なんです。対策はシンプルで、明細を触る処理をサービスの `@Transactional(readOnly = true)` の中に入れて、そこで DTO に詰めきってから返すこと。境界をサービスで区切るのがセオリーです。
>
> もう1つ、ループの中で注文ごとに `getLines()` を呼んでいるので、注文が100件だと明細取得のSQLが100回飛びます（いわゆる N+1問題）。ここは `JOIN FETCH` で注文と明細を1回のSQLでまとめて取るようにすると一気に速くなります。ついでに一覧なので `Pageable` でページングを入れて、返すのは Order エンティティ直返しではなく `OrderSummary` みたいな DTO にしておくと、情報漏れもシリアライズ時の事故も防げます。どれも「一覧APIあるある」なので、ここで型を覚えておくと今後ずっと効きますよ。
