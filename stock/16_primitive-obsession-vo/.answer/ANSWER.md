## ❌ NGポイント (bad/ 配下)

1. **プリミティブ執着（＝意味のある値を全部 String / int の素の型で持ち回している）**: メール・郵便番号・電話番号がすべて `String`、金額が `int`。型が「ただの文字列」「ただの整数」でしかないので、「これはメールアドレスだ」「これは円だ」という意味がコードのどこにも表れない。結果として、正しい形式かどうかの検証（＝チェック）を**値を使う各所で毎回自前でやる**しかなくなり、後述のとおりコピペと抜け漏れの温床になる。「意味のある値なのに専用の型を作らず素の型で済ませてしまう」この状態を「プリミティブ執着」と呼ぶ。

2. **意味の違う同じ型の引数が並んでいて、取り違えてもコンパイルエラーにならない**: `register(String email, String phone, String postalCode)` は3つとも `String`。呼び出し側が `register(phone, email, postalCode)` のように順番を間違えて渡しても、型が全部同じなのでコンパイラ（＝実行前にコードをチェックする仕組み）は何も文句を言わず、**そのまま通ってしまう**。間違いに気づくのは本番で変なデータが登録された後、という最悪のパターンになる。型で取り違えを防げていないのが問題。

3. **金額を int の「円」で持ち回り、税込計算で単位・丸め・桁あふれの事故が起きる**: `estimateShipping(int itemPrice, int shippingFee)` は金額を `int` で扱い、`subtotal * 110 / 100` で税込を計算している。`int` は約21億までしか表せないので、金額が大きいと掛け算の途中で**桁あふれ（＝扱える範囲を超えて値が壊れること。オーバーフロー）**が起き、いきなりマイナスの金額になったりする。さらに `/ 100` の整数割り算は端数を勝手に切り捨てるが、その「丸め方」が型に表れず意図が読めない。金額は本来 `BigDecimal`（＝桁数と丸め方を正確に扱える数値型）で計算すべきで、それが不在。

4. **同じ検証が複数メソッドにコピペされている**: メール形式チェック（`@` と `.` を含むか）が `register` と `changeEmail` に、郵便番号の桁チェックが `register` と `changePostalCode` に、それぞれ**丸ごとコピペ**されている。しかも税込計算 `subtotal * 110 / 100` も `estimateShipping` と `isExpensiveShipping` で重複。コピペは「片方だけ直して片方を直し忘れる」事故（＝仕様がズレる）を招くうえ、新しくメールを受け取る箇所が増えるたびに検証を書き足す羽目になり、いつか必ず**書き忘れ（＝検証の抜け漏れ）**が出る。

## ⭕️ 改善案 (good/ 配下)

1. **値オブジェクト（＝意味のある値を専用の小さな型にしたもの）を作る**: `EmailAddress` / `PostalCode` / `PhoneNumber` / `Money` を用意する。`String` や `int` の代わりにこれらの型で持ち回すことで、「この値が何者か」が型そのものに表れる。

2. **検証を生成時の1箇所に集約する**: 各値オブジェクトのコンストラクタ（＝作る入口）で形式チェックを行い、通らなければ例外を投げる。こうすると「その型のオブジェクトが存在する＝検証済み」が保証され、`register` や `changeEmail` からコピペ検証がすべて消える。検証の抜け漏れも起きない。

3. **不変（＝一度作ったら中身を変えられない。イミュータブル）にする**: フィールドを `final` にし、`final class` にする。値が途中で書き換わらないので、安心して引数や戻り値で持ち回せる。`equals` / `hashCode` を「値が同じなら同じ」で実装する。

4. **引数を専用型にして取り違えをコンパイルで防ぐ**: `register(EmailAddress, PhoneNumber, PostalCode)` にすれば、メールの位置に電話番号を渡した瞬間にコンパイルエラーになる。**実行前に**間違いを潰せる。

5. **金額は Money に BigDecimal を内包させる**: `Money` は内部に `BigDecimal` を持ち、`add`（足し算）・`withTax`（税込化）・`isGreaterThanOrEqual`（しきい値比較）を提供する。単位（円）と丸め方（切り捨て等）が Money の中に隠れるので、呼び出し側は掛け算・丸めのミスや桁あふれを気にしなくてよくなる。

6. **重複ロジックを一本化する**: 見積もり計算を `estimateShipping` に集約し、`isExpensiveShipping` はそれを呼ぶだけにする。会員検索も `findByEmail` にまとめる。税率やしきい値は名前付き定数にしてマジックナンバーを避ける。
