## ❌ NGポイント (bad/ 配下)

1. **金額を `int` で計算しており、桁あふれ（オーバーフロー）で合計が壊れる（核心・気づきにくい）**: `int` は約21億（`2,147,483,647`）までしか表せない。`total += line.getUnitPrice() * line.getQuantity()` で、たとえば単価30,000円 × 数量100,000個 = 30億のような明細が来ると、この上限を超えた瞬間に**例外も出さず静かにマイナスの値へ化ける**。しかも `unitPrice * quantity` の掛け算自体も int 同士なので、1行の中ですでにあふれることもある。テストデータ（少額・少量）では通ってしまい、本番の大口取引で「合計金額がマイナス」という形で初めて発覚する、最もたちの悪いバグ。

2. **`averagePerItem` で総数量が 0 のときゼロ除算になる（中）**: `total / count` の `count` は明細の数量合計。空リストや数量0の明細だけのとき `count == 0` となり、`ArithmeticException: / by zero` で落ちる。事前チェックが無い。

3. **そもそも金額を `int`（整数型のプリミティブ）で持つ設計が不適切（型設計）**: 金額は `long` でも桁あふれの懸念が残り、消費税や割引で小数・端数が絡むと誤差も出る。金額は本来 `BigDecimal`（正確な十進計算ができる型）や専用の金額型（Money 値オブジェクト）で扱うべき。プリミティブへの執着が根っこにある。

4. **`lines` の null / 要素 null を考慮していない（低）**: `lines` が null だと拡張 for で即 NPE。呼び出し規約が不明瞭。

## ⭕️ 改善案 (good/ 配下)

1. **金額を `BigDecimal` で扱う**: 掛け算・足し算を `multiply` / `add` で行えば桁あふれの心配がなく、税や割引の小数も正確に扱える。`calculateTotal` / `averagePerItem` の戻り値も `BigDecimal` にする。

2. **ゼロ除算を事前に弾く**: 割り算の前に `count == 0` を確認し、`IllegalArgumentException` で「なぜ計算できないか」を明示する。

3. **`BigDecimal.divide` は丸めを明示する**: 金額の割り算では「小数第何位まで・どう丸めるか（`RoundingMode`）」を必ず指定する（指定しないと割り切れないとき例外になる）。ここでは円単位・四捨五入にした。

4. **入力を防御する**: `Objects.requireNonNull(lines, ...)` で null を早期に弾き、意図しない NPE を意味のある例外に変える。

## 💬 レビューコメント例文

> ロジックの見通しは良くて読みやすいです。ただ、この計算には本番の大口注文で表面化する怖いバグが潜んでいます。金額を `int` で足し込んでいますよね。`int` は約21億までしか表せなくて、それを超えると**例外も出さずマイナスの値に化ける**んです。単価3万円 × 数量10万個みたいな明細が1行あるだけで、その掛け算の時点であふれます。テストの少額データでは通ってしまうので、気づいたときには「なぜか請求額がマイナス」になっている、という一番デバッグしづらいパターンになりがちです。

> 対策として、金額は `BigDecimal` で扱いましょう。`multiply` / `add` を使えば桁あふれの心配がなくなりますし、この先で消費税や割引の端数が絡んでも誤差なく計算できます。あわせて `averagePerItem` は、総数量が0だと `total / count` がゼロ除算で落ちるので、割る前に `count == 0` をチェックして意味のある例外にしておきましょう。BigDecimal の割り算は丸め方（小数第何位・四捨五入か）を明示しないと割り切れないときに例外になるので、そこも一緒に決めておくと安心です。
