## ❌ NGポイント (bad/ 配下)

1. **手続き的な `if` 検証が散らばり、しかも重複・抜け漏れがある**:
   `RegisterService.register()` は氏名・メール・年齢・パスワードを1つずつ `if` で
   チェックしている。さらに `validateForAdmin()` でも似たような検証を「もう一度手で」
   書いていて、しかも中身がズレている（admin 側にはメール形式チェックとパスワード
   チェックが無い、など）。検証ルールが複数の場所にコピーされると、片方だけ直して
   もう片方を直し忘れる、という事故が必ず起きる（＝ルールの二重管理）。入力チェックは
   「1か所に宣言的に書いて全員がそれを使う」のが鉄則。

2. **メール検証の正規表現が ReDoS 脆弱（＝細工した入力でCPUを食いつぶす）**:
   `"^([a-zA-Z0-9]+)*@example\\.com$"` の `([a-zA-Z0-9]+)*` は、量指定子（`+`）の
   かたまりをさらに `*` で包んだ「ネストした繰り返し」になっている。この形は、
   マッチに失敗する入力（例：`"aaaaaaaaaaaaaaaaaaaaaaaaaaaa!"` のように最後だけ
   条件を外した文字列）を渡すと、正規表現エンジンが膨大な組み合わせを総当たりで試す
   「破滅的バックトラッキング」に陥る。文字を1文字足すだけで処理時間が倍々に伸び、
   1リクエストでCPUが100%に張り付いてサーバー全体が固まる（＝典型的なDoS＝サービス
   妨害攻撃の入口）。メール検証は自作の正規表現ではなく、実績のあるライブラリに任せる。

3. **検証ロジックと業務ロジックが同じメソッドに混在していてテストしづらい**:
   `register()` は「入力チェック」と「会員を作って保存する」を1つのメソッドで
   やっている。そのため「保存処理だけをテストしたい」のに、毎回すべての検証を通る
   ダミー入力を用意しないと1行も先に進めない。役割が混ざっていると、テストも修正も
   影響範囲が読めなくなる（＝関心の分離ができていない）。

4. **エラーの通知方法がバラバラ（例外 / false / null が混在）**:
   氏名・メール・年齢は `throw`（例外）、パスワード不足は `return null`、
   `validateForAdmin` は `return false`。呼び出す側は「このメソッドは失敗をどう
   知らせてくるのか？」を毎回覚えていないと正しく扱えない。特に `null` を返されると、
   呼び出し側が `null` チェックを忘れて、あとで別の場所で NullPointerException（＝
   null を触って落ちる例外）になる。しかも「なぜ失敗したのか（どの項目がダメか）」が
   `false`/`null` からは分からない。通知方法は1つに統一すべき。

5. **境界値チェックの漏れ・不整合**:
   `register()` には年齢の「上限」チェックが無い（999歳でも登録できる）が、
   `validateForAdmin()` には `0〜150` の範囲チェックがある——同じ「会員登録」なのに
   ルールが食い違っている。氏名も `register` は「50文字まで」を見るが admin 側は
   長さを見ない。空文字判定も `trim().isEmpty()`（空白のみもNG）と `isEmpty()`
   （空白のみはOK）で不揃い。パスワードの上限も無く、極端に長い文字列を弾けない。
   「どこで何の境界を守るか」がバラバラだと、入口によって通る・通らないが変わる。

## ⭕️ 改善案 (good/ 配下)

1. **入力ルールは DTO に制約アノテーションで「宣言的に」書く**:
   `RegisterRequest` の各フィールドに `@NotBlank`（必須）、`@Size`（文字数）、
   `@Email`（メール形式）、`@Min` / `@Max`（数値の範囲）を付ける。ルールが
   フィールドの真上に一覧で並ぶので抜け漏れに気づきやすく、検証コードを手書きしないので
   重複も起きない。

2. **危険な自前正規表現をやめて `@Email` に任せる**:
   メール検証は `@Email` に置き換える。ライブラリ側は ReDoS を起こさない安全な実装
   なので、細工した入力でCPUが張り付く心配がない。「車輪の再発明（＝既にある仕組みを
   自作し直すこと）」をしないのが安全でもある。

3. **境界（Controller）で `@Valid`＋`@RestControllerAdvice` によりまとめて検証**:
   Controller の引数に `@Valid` を付けるだけで、リクエストが入ってきた時点で
   DTO のルールが自動チェックされる。ルール違反は `MethodArgumentNotValidException`
   として投げられ、`GlobalExceptionHandler`（`@RestControllerAdvice`）が受け止めて
   400（入力エラー）＋「どの項目がなぜダメか」に変換する。これでエラー通知も
   例外に一本化できる（NG4の解消）。

4. **業務ロジックから検証を追い出す**:
   `RegisterService.register()` からは `if` の検証をすべて撤去し、「会員を作って保存する」
   だけにする。検証は境界で済んでいる前提なので、サービスは短く読みやすく、テストも
   「保存処理」だけに集中できる（NG3の解消）。管理画面用の重複メソッドも不要になる
   （同じ DTO＋同じアノテーションを使い回せる）。

5. **境界値を DTO の1か所に集約して不整合をなくす**:
   年齢は `@Min(18)`＋`@Max(150)`、氏名は `@Size(max = 50)`、パスワードは
   `@Size(min = 8, max = 100)` のように上限・下限を明示。入口が管理画面でも
   フォームでも同じ DTO を通せば、ルールは常に一致する。
