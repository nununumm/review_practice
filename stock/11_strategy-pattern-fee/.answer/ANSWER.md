## ❌ NGポイント (bad/ 配下)

1. **決済手段を巨大な if-else で分岐している（拡張のたびに本体を改造：OCP違反）**: `if (method == "CREDIT_CARD") ... else if ...` と、決済手段の数だけ分岐がぶら下がっている。新しい決済手段（例：後払い、ポイント払い）が増えるたびに、この `calculateFee` メソッドを開いて分岐を追加・改造しなければならない。これは「機能追加のたびに既存の動いているコードをいじる」という状態で、変更するたびに他の手段まで壊す危険がある。プロの世界では「拡張には開いていて、修正には閉じているべき（＝OCP：オープン・クローズドの原則）」とされ、この状態はそれに反している。決済手段ごとの違いは、その手段自身に閉じ込める（＝Strategyパターン＝やり方ごとに部品を差し替える設計）のが定石。

2. **手数料率・上限・最低手数料をマジックナンバーで各分岐に直書きしている**: `0.036`、`5000`、`50`、`60`、`30` といった数字が、意味の説明もなくコードの中に散らばっている（＝マジックナンバー：それ単体では何の数字か分からない即値）。「5000 が何の上限なのか」「50 が最低手数料なのか手数料率なのか」がコードを読んだだけでは判別しづらく、料率改定のときにどこを直せばよいか探し回るハメになる。名前付きの定数や、ルールをまとめた入れ物（値オブジェクト）に持たせて意味を与えるべき。

3. **金額を double で計算していて丸め誤差が出る（お金の計算に double を使っている）**: 戻り値も引数も `double`。`double`（＝コンピュータ内部では2進の小数）は `0.1` すら正確に表せず、掛け算を重ねると `539.9999...` のようなズレが生じる。お金の計算でこれをやると、1円ずれる・端数処理が思った通りにならない、という事故につながる。お金は必ず `BigDecimal`（＝10進で誤差なく計算できる型）＋ `RoundingMode`（＝丸め方を自分で指定）で扱うのが鉄則。

4. **`else` / `default` が無く、未知の決済手段だと手数料0のまま黙って素通りする（バグ）**: どの `if` にも当てはまらない手段（例：スペルミスや新手段）が渡ると、`fee` は初期値の `0` のまま `return` される。エラーにもならず「手数料0円」として通ってしまうため、取りこぼしても誰も気づけない。「想定外の入力は黙って通さず、はっきり例外で知らせる」べき典型例。

5. **「上限キャップ」「最低手数料」の同じロジックが複数分岐にコピペされている（重複）**: `if (fee > 5000) fee = 5000;` や `if (fee < 50) fee = 50;` といった上限・最低の処理が、各手段の分岐に何度も貼り付けられている。同じロジックが散らばると、仕様変更（例：上限を4000円に）のときに全箇所を漏れなく直す必要があり、1つ直し忘れるとそこだけ古い挙動が残るバグになる。共通の処理は1箇所にまとめる（＝DRY：繰り返さない）べき。

6. **決済手段名を `==` で比較していて、文字列比較として壊れている＋表記ゆれに弱い**: `method == "CREDIT_CARD"` は文字列の**中身**ではなく**同じオブジェクトか**を比べている（＝参照比較）。渡され方によっては中身が同じでも `false` になり、分岐が一致せず全部素通り（NG4の0円バグ）に直結する。文字列の中身を比べるなら `equals` を使うのが基本。さらに、そもそも文字列で手段を受け渡すと `"credit_card"` や前後の空白などの表記ゆれにも弱い。手段は型（enum）で表し、そもそも不正な値が入り込めないようにするのが本筋。

## ⭕️ 改善案 (good/ 配下)

1. **決済手段を enum にして、手数料ルールを手段自身に持たせる**: `PaymentMethod`（enum）を作り、各手段に「率・上限・最低」をまとめた `FeeRule` を1つ持たせる。新しい手段は enum を1行足すだけで増やせ、計算サービス本体の分岐は一切いじらなくてよい（OCP を満たす）。

2. **手数料率・上限・最低を FeeRule（値オブジェクト）に集約し、マジックナンバーに意味を与える**: 数字を裸で散らさず、`new FeeRule(率, 上限, 最低)` の形で「これは率」「これは上限」と役割をはっきりさせる。料率改定のときも enum の定義を見れば全手段の数字が一覧でき、直す場所が明確。

3. **お金は BigDecimal ＋ RoundingMode で計算する**: 金額・手数料をすべて `BigDecimal` で扱い、最後に `setScale(0, RoundingMode.HALF_UP)`（＝円未満を四捨五入）で丸める。丸め方を明示するので誤差も端数のブレも起きない。

4. **未知の手段は黙って通さず例外を投げる**: enum で受け取れば存在しない手段はそもそも入れられない。文字列入口を用意する場合も、対応する手段が無ければ「未対応の決済手段です」と意味のある例外を投げ、0円素通りを防ぐ。

5. **上限・最低の共通ロジックを FeeRule の1メソッドに1本化する**: 「率をかける → 上限で頭打ち（min）→ 最低で底上げ（max）→ 丸める」という流れを `applyTo` 1箇所だけに書く。各手段はこれを共有するので、仕様変更の修正も1箇所で済む（DRY）。

6. **手段は enum で型として扱い、文字列比較（== / equals）そのものを無くす**: `PaymentMethod` を引数に取れば `==` 比較の入る余地がない。文字列で受ける入口では `trim().toUpperCase()` で表記ゆれをそろえてから `valueOf` で安全に変換する。
