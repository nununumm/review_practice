## ❌ NGポイント (bad/ 配下)

1. **`Collectors.toMap` に重複キーの扱いを指定しておらず、重複コードがあると落ちる（核心・本番で初めて発覚）**: `toMap(Product::getCode, p -> p)` の2引数版は、**同じキーが2回以上現れると `IllegalStateException: Duplicate key` を投げる**。商品リストは外部取込データで内容が保証されていないため、同一コードの商品が混ざった瞬間に索引作成ごと落ちる。テストのきれいなデータでは通ってしまい、本番データで突然エラーになる典型。重複時にどうするか（先勝ち・後勝ち・エラー）を必ず明示すべき。

2. **索引作成時と検索時でキーの作り方が食い違い、「登録したのに見つからない」（正確性のバグ）**: `indexByCode` は `getCode()` をそのままキーにしているのに、`findByCode` は `code.toUpperCase()` と大文字化して引いている。元コードが小文字や混在だとキーが一致せず、存在する商品でも `null` が返る。キーの正規化は「作るとき」と「引くとき」で必ず揃えなければならない。

3. **検索のたびに全件を `Map` 化していて非効率（パフォーマンス）**: `findByCode` が毎回 `indexByCode(products)` を呼んで全商品から Map を作り直している。1件引くために毎回 O(n) の索引構築が走り、索引にした意味がない。索引は1度作って使い回すべき。

4. **`code` の `toUpperCase()` が `Locale` 未指定＋ null 非考慮（国際化・堅牢性／低〜中）**: `toUpperCase()` は Locale を指定しないと実行環境のロケール依存になり、トルコ語環境などで `i` の大文字化が変わってキーがずれる有名な罠がある。さらに `code` が null だと `NPE`。

## ⭕️ 改善案 (good/ 配下)

1. **`toMap` の3引数版で重複キーの扱いを明示する**: `toMap(key, value, (existing, replacement) -> replacement)` のようにマージ関数を渡し、「重複したら後勝ち／先勝ち」を意図として書く。これで重複データでも落ちず、挙動が明確になる。

2. **キーの正規化を1か所に集約し、作成時・検索時で必ず同じ関数を通す**: `normalize(code)`（大文字化）を用意し、索引作成と検索の両方でこれを使う。キーの作り方が揃うので不一致バグが消える。

3. **索引は1度だけ作って保持する**: コンストラクタで索引を作りフィールドに持つ。検索は既存の Map を引くだけで O(1)。

4. **`toUpperCase(Locale.ROOT)` と null チェック**: Locale を固定して環境非依存にし、null は早期に弾く。

## 💬 レビューコメント例文

> Stream の `toMap` で索引を作る発想は良いですし、コードもコンパクトですね。ただ、外部取込データが相手だと本番で初めて落ちる罠があるので直しましょう。`toMap(getCode, p -> p)` の2引数版は、同じ商品コードが2回出てきた瞬間に `Duplicate key` で例外になるんです。きれいなテストデータだと気づけないので、`toMap(キー, 値, (a, b) -> b)` のように「重複したらどうするか（後勝ちなど）」を必ず書いておきましょう。

> もう1つ、地味だけど痛いバグがあります。索引を作るときは `getCode()` をそのままキーにしているのに、`findByCode` では `toUpperCase()` して引いていますよね。これだとキーが一致せず、存在する商品でも見つからなくなります。キーの正規化（大文字化するなら）は「作るとき」と「引くとき」で必ず同じ関数を通すのが鉄則です。正規化メソッドを1個作って両方から呼ぶと安全ですし、そのとき `toUpperCase(Locale.ROOT)` にしておくとロケール依存の事故も防げます。あと `findByCode` が毎回全件を Map 化しているので、索引はコンストラクタで1回作って使い回すようにしましょう。
