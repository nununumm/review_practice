## ❌ NGポイント (bad/ 配下)

1. **文字列の一致を `==` で比べている（最重要）**: `couponCode == "SUMMER2026"` のように、文字列の中身を比べたいのに `==` を使っている。`==` は「参照（＝オブジェクトが置いてある場所）が同じか」を比べる演算子で、「書いてある文字の中身が同じか」は比べない。たとえるなら、同じ内容の紙が2枚あるとき、`==` は「これは物理的に同じ1枚の紙ですか？」と聞いていて、`equals` は「書いてある内容は同じですか？」と聞いている。中身を判定したいなら `equals` を使わなければならない。

2. **「開発では動いて見えるのに本番でだけ壊れる」潜伏バグになる**: `"SUMMER2026"` のように直接書いた文字列（リテラル）同士だと、Java は「文字列プール（＝同じ内容のリテラルを1つにまとめて使い回す仕組み）」で同じ実体を指すため、`==` でもたまたま `true` になる。だから開発中のテストでは通ってしまう。ところが本番では、クーポンコードは画面やAPI・DBから受け取った**別インスタンス**（`new String(...)` や文字列結合で作られたものと同じ）なので、中身が `"SUMMER2026"` でも `==` は `false`。結果、割引が一切効かない。コンパイルも通り、開発では気づけない、非常にたちの悪いバグ。

3. **null のときの安全性を考えていない**: `couponCode` が `null` で送られてくる可能性がある。`equals` に直すときに `couponCode.equals("SUMMER2026")` と書くと、`couponCode` が `null` のときに `NullPointerException`（＝null に対して操作してしまう例外）で落ちる。定数を左に置いて `"SUMMER2026".equals(couponCode)` と書けば、`null` でも単に `false` が返り安全。

4. **大文字小文字・表記ゆれを考慮していない**: 画面やAPIから来る値は `"gold"` や `"Gold"` のように揺れることがある。ランクやコードの仕様によっては、`equalsIgnoreCase`（大文字小文字を区別しない比較）や、事前の正規化（`trim` や大文字化）を検討する余地がある。

## ⭕️ 改善案 (good/ 配下)

1. **文字列の中身の比較は必ず `equals`、しかも定数を左に置く**: `"SUMMER2026".equals(couponCode)` と書く。こうすれば中身で正しく判定でき、かつ `couponCode` が `null` でも `NullPointerException` にならず `false` が返るので null 安全になる。

2. **取りうる値が決まっているものは enum 化も検討**: 会員ランク（GOLD/SILVER…）のように候補が有限のものは、`String` ではなく enum（列挙型）にすると、タイプミスがコンパイル時に弾かれ、`==` で安全に比較できるようになる。今回は文字列判定の学びが主眼なので equals で統一したが、設計上は enum 化が一段上の解。

3. **必要に応じて `equalsIgnoreCase` や正規化を**: 入力の表記ゆれが想定されるなら、大文字小文字を無視する比較や、受け取り時点での正規化を入れる。
