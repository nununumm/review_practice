## ❌ NGポイント (bad/ 配下)

1. **コレクションで null を返している（`findByCategory`）**: 0件のとき `return null;` としている。これが一番の地雷。呼び出し側が「一覧をループで回す」つもりで受け取ると、`for (Product p : list)` の時点で list が null なら即 NullPointerException（＝null の中身を触ろうとして落ちる例外）で画面が真っ白になる。だから呼び出し側は毎回 `if (list != null)` という防御コードを書かされ、1箇所でも忘れれば本番で落ちる。`Effective Java`（Javaの定番指南書）の項目「null ではなく、空の配列やコレクションを返せ」がまさにこれ。「無い」は "null" ではなく "空っぽの箱"（＝空リスト）で表すのが鉄則。

2. **単体オブジェクトの「見つからない」を null で表している（`findByCode`）**: 「該当なし」を返り値の型（`Product`）で全く表現できていない。受け取る側は、そのメソッドが null を返しうるのかどうかをシグネチャ（＝メソッドの見た目）から読み取れず、ドキュメントか実装を読むまで分からない。結果、null チェックを忘れて NPE になる。「無いかもしれない」という事実は、型で正直に示すべき（＝Optional）。

3. **null の意味が多義（あいまい）**: 返ってきた null が「条件に合う商品が無かった（正常系）」なのか「DB接続エラー等で取得できなかった（異常系）」なのか、呼び出し側からは区別できない。本来まったく扱いが違う2つの状況が、同じ null に押し込められている。「正常に0件」は空リスト／Optional.empty で、「異常」は例外で、と表現手段を分けるべき。

4. **stream や拡張for に直接渡せず、防御コードが散らばる**: null を返しうるせいで、呼び出し側は `list.stream()...` の前に必ず null 判定を挟む必要があり、その `if` があちこちにコピペで増殖する（＝防御コードの散らばり）。空リストを返す設計なら、0件でも「0回まわるだけ」なので、呼び出し側はチェック無しでそのまま流せてコードがすっきりする。

## ⭕️ 改善案 (good/ 配下)

1. **一覧は「常に空でない List」を返す（null 禁止）**: 0件なら `Collections.emptyList()`（＝要素0個の変更できないリスト。実体を使い回すので生成コストゼロ）や `List.of()` を返す。リポジトリが万一 null を返してきても、サービス層で空リストへ寄せて外に null を漏らさない。呼び出し側は null チェック不要で、そのまま拡張for や stream に渡せる。

2. **単体は `Optional<Product>` を返す**: `Optional`（＝「有るかもしれない／無いかもしれない」を型で表す入れ物）で返すと、「無いこともある」がメソッドの見た目に正直に出る。呼び出し側は `orElseThrow`（無ければ例外）、`orElse`（無ければ既定値）、`map`（有るときだけ変換）と、目的に応じて明示的に書ける。`Optional.ofNullable(product)` を使えば null → empty の変換も一行。

3. **「正常に無い」と「異常」を分ける**: 「0件・未検出」は空リスト／Optional.empty という正常系の表現に、「取得失敗」は例外に、と役割を分ける。これで返り値の意味が一つに定まり、読み手が迷わない。

4. **結果として防御コードが消える**: 呼び出し側の散らばった null チェックが不要になり、ロジックの本筋だけが残る。堅牢性（＝落ちにくさ）と可読性が同時に上がる。

## 💬 レビューコメント例文

> `ProductQueryService`、業務ロジックの分け方はきれいで、リポジトリに委譲できているのも良いですね。ここからさらに"落ちにくいコード"にするための提案です。

> `findByCategory` が0件のとき null を返しているのですが、これを呼ぶ側が一覧をループで回すと、0件のたびに NullPointerException で落ちる可能性があります。`Effective Java` でも「null ではなく空コレクションを返す」が推奨されていて、ここは 0件なら `Collections.emptyList()` を返すようにすると、呼び出し側は null チェック無しでそのまま回せるようになります。同じく `findByCode` の"見つからない → null"は、`Optional<Product>` で返すと「無いこともある」がメソッドの型に表れて、呼ぶ側が `orElseThrow` などで安全に扱えます。

> どちらも「無い、を null 以外でどう表すか」という同じテーマの話です。ここを直すと、あちこちに書かれがちな防御的な null チェックがまとめて要らなくなるので、コード全体が一段すっきりします。直し方で迷ったら一緒に見ますね。
