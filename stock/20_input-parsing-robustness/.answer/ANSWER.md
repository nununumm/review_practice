## ❌ NGポイント (bad/ 配下)

1. **`Integer.parseInt` を無防備に呼んで 500 エラーになる（例外処理・堅牢性）**: `page` と `size` は `Integer.parseInt(params.get("page"))` をそのまま呼んでいる。画面から `"abc"` や空文字、`null` が来た瞬間に `NumberFormatException`（＝数値に変換できないときに出る例外）が飛び、そのまま画面に伝わると `500 Internal Server Error`（＝サーバー側が想定外で落ちた、というエラー）になる。利用者から見ると「サーバーが壊れた」ようにしか見えず、「入力のどこが悪いのか」がまったく分からない。入力の不備は本来 `400 Bad Request`（＝あなたのリクエストが不正、という400番台のエラー）で「どの項目がダメか」を伝えるべき。

2. **例外を握りつぶして黙って既定値に倒している（可観測性・UX）**: `minPrice` は `catch (Exception e) { minPrice = 0; }` としていて、変換に失敗しても何も言わず 0 にしてしまう。しかも `catch (Exception e)` は例外を何でも一網打尽にする書き方で、想定外のバグまで飲み込んでしまう。利用者は「1000円以上で検索したはずなのに全部出てくる」理由が分からず、開発者もログに何も残らないので原因追跡ができない。「該当なし」なら正常だが、「変換に失敗した」は利用者に伝えるべき異常。

3. **値の範囲チェック（clamp）が無い（セキュリティ・性能／DoS）**: `size` に `1000000` が来てもそのまま受け入れてしまう。検索が一度に大量の行を取得してメモリを圧迫し、これを連打されるとサービス停止（＝DoS：故意に高負荷をかけてサービスを止める攻撃）の入口になる。`page` が負数、`minPrice` が負数でも素通りで、`offset = page * size` が負になって不正なSQLにもなりうる。**上限・下限で範囲に丸める（clamp）** のが必須。

4. **`sort` を検証せず ORDER BY 句に文字列連結している（セキュリティ／SQLインジェクション）**: `"ORDER BY " + sort` と、画面から来た文字列をそのまま SQL の並び順に埋め込んでいる。ここに `price; DROP TABLE products; --` のような文字列を入れられると、意図しないSQLが実行されてしまう（＝SQLインジェクション：入力に不正なSQLを紛れ込ませてDBを操作する攻撃）。`toSql` の `keyword` も同様に `LIKE '%...%'` へ直接連結していて危険。**並び順は許可リスト（ホワイトリスト＝あらかじめ決めた安全な値だけ通す仕組み）で検証**し、値そのものはプレースホルダ（`?`）でバインドすべき。

5. **前処理（trim・空文字・null・全角数字）を考慮していない（堅牢性）**: `keyword` は `params.get("keyword")` をそのまま入れており、前後の空白（`"  シャツ  "`）や空文字、`null` の区別をしていない。数値も、画面で全角（`"１２３"`）を打たれると `parseInt` が失敗する。入力の「表記ゆれ」を正規化（trim・全角→半角変換・空→既定値）してから使うべき。

6. **桁あふれ（オーバーフロー）を考慮していない（堅牢性）**: `Integer.parseInt("99999999999")` のように `int` の範囲（約21億まで）を超える数字が来ると、これも `NumberFormatException` になる。1 と同じく無防備なので 500 に化ける。数値の範囲まで意識して、失敗は 400 に翻訳する必要がある（`Integer.parseInt` はオーバーフローも例外で弾いてくれるので、そこを catch すればまとめて扱える）。

## ⭕️ 改善案 (good/ 配下)

1. **変換を共通メソッド `parseInt(raw, fieldName, default)` に集約**: null・空文字は「省略」とみなして既定値を返し、変換失敗（不正文字・桁あふれ）は `ResponseStatusException(BAD_REQUEST, "...")` に翻訳して「どの項目がなぜダメか」を伝える。500 を 400 に変え、握りつぶしをやめる。

2. **すべての数値を clamp（範囲に丸める）**: `page` は下限0、`size` は `MIN_SIZE=1`〜`MAX_SIZE=100`、`minPrice` は下限0。上限を設けることで大量取得（DoS）を物理的に不可能にする。上限・下限・既定値はすべて名前付き定数にして「なぜこの値か」を明確にする。

3. **`sort` は許可リストで検証**: `Map<String,String> ALLOWED_SORTS` に「画面の値→安全なORDER BY句」を定義し、`getOrDefault` で載っている値だけ採用、未知の値は既定の並び順にフォールバック。画面の文字列がSQLに直接流れ込まないので、SQLインジェクションの入口を塞げる。`keyword` も本番では `?` でバインドする前提にする。

4. **前処理を正規化**: `Normalizer.normalize(..., NFKC)` で全角数字を半角に、`trim()` で前後空白を除去、`keyword` の空文字は `null`（絞り込みなし）に統一。長すぎる `keyword` は 400 で弾く。

5. **既定値を「明示的に」扱う**: 「省略された（null/空）→既定値」と「不正な値が来た→400」をはっきり分ける。黙って0に倒す曖昧な挙動をなくす。
