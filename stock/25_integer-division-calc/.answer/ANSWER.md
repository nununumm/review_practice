## ❌ NGポイント (bad/ 配下)

1. **達成率を整数同士で割っていて小数が消える（＝整数除算）＋掛ける順序も悪い**: `(int)(actual / target) * 100` は、`actual / target` を先に計算する。両方とも `long`（整数）なので、この割り算は**小数点以下を全部切り捨てる**（＝整数除算：整数同士の割り算では商の小数部が捨てられる、というJavaの仕様）。たとえば達成金額 6,000 円・目標 9,000 円なら本当は約 66.7% だが、`6000 / 9000` は 0.666... の小数部が捨てられて `0`。それに 100 を掛けても `0` で、達成率が**常に 0%**になってしまう。目標未達のあいだずっと「達成率0%」と表示され続けるバグ。対策は「割り算の前に 100 を掛ける」か「小数（`double` か `BigDecimal`）で割る」こと。順序と型の両方が原因。

2. **割引の按分で割り切れない余り（端数）が消え、配った合計が元の額と一致しない**: `perItem = total / count` を全員に同じだけ配っているが、これも整数除算なので余りが捨てられる。たとえば 100 円を 3 商品に配ると `100 / 3 = 33` 円ずつ。しかし 33 × 3 = 99 円にしかならず、**1 円が行方不明**になる（配った合計 ≠ 元の割引額）。お金の按分では「余った端数を誰かに寄せて、配った合計を元の額にぴったり合わせる」のが必須。ここでは端数がそのまま消えていて、会計が合わなくなる。

3. **`target` が 0 のときの 0除算（ArithmeticException）を防いでいない**: `achievementRate` は `actual / target` をいきなり計算しているので、`target` に 0 が渡ると「0で割った」として `ArithmeticException`（＝算術エラー。整数を0で割ると発生して処理が落ちる）で例外が飛ぶ。同様に `distributeDiscount` も `count` が 0 だとここで落ちる。0 になり得る入力は割り算の前にガード（先に弾く）すべき。

4. **金額を int/long のまま扱い、率も int で返している（精度の設計が無い）**: 戻り値の達成率が `int` なので、たとえ計算を直しても 66.7% のような小数を表現できず 66% や 67% に丸まる。お金や率の計算は「どこまでの精度で・どう丸めるか」を設計する必要があり、正確さが要るなら `BigDecimal`（＝10進で誤差なく計算でき、丸め方を自分で指定できる型）を使うのが定石。`double` でつなぐと今度は 0.1 すら正確に表せず誤差が出る。

5. **入力（負数・null 相当）の検証が無い**: `actual` に負数、`count` に 0 以下などの不正値が来ても素通りする。負の達成率や、空の按分結果など、意味の通らない値が後工程に流れてしまう。境界値（0・負数）は入口で検証して、意味のある例外で弾くべき。

## ⭕️ 改善案 (good/ 配下)

1. **達成率は割る順序を正し、小数を保てる型で計算する**: `actual × 100 ÷ target` の順にして、`BigDecimal` で `divide(target, 1, RoundingMode.HALF_UP)` のように「小数第1位まで・四捨五入」と桁数と丸め方を明示する。これで目標未達でも 66.7% のように正しく出る。

2. **按分は余り（端数）を配り切って合計を一致させる**: `base = total / count` と `remainder = total % count`（余り）を出し、先頭の `remainder` 件に 1 円ずつ足す。こうすると配った合計が必ず `total` に一致する（100 円 → 34, 33, 33）。

3. **0除算を先にガードする**: `target <= 0` や `count <= 0` を割り算の前にチェックし、意味のある例外を投げて落ちる前に弾く。

4. **率は `BigDecimal` で精度と丸めを設計する**: 戻り値を `BigDecimal` にし、必要な小数桁と `RoundingMode`（丸め方）を明示する。int で切り捨てられて情報が消えるのを防ぐ。

5. **入力の境界チェックを入口で行う**: 負数や 0 以下を `IllegalArgumentException` で弾き、意味の通らない値が後工程に流れないようにする。
