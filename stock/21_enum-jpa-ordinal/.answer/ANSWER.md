## ❌ NGポイント (bad/ 配下)

1. **enum を `@Enumerated(EnumType.ORDINAL)` で保存している（データ破壊の時限爆弾）**: `@Enumerated` に `EnumType.ORDINAL` を指定すると、enum は「名前」ではなく「並び順の番号」でDBに保存される。つまり `NEW→0`、`PAID→1`、`SHIPPED→2`、`CANCELED→3` という数字だけがDBに入る（＝ORDINAL：enum を宣言した順番の番号）。ここで恐ろしいのは、あとから enum の途中に新しい状態を差し込んだ瞬間、番号の意味が全部ずれることだ。たとえば `NEW, PAID, RETURNED, SHIPPED, CANCELED` と `RETURNED` を3番目に入れると、これまで「2＝SHIPPED」だったDB上の全注文が、コード上は「2＝RETURNED」に化ける。出荷済みの注文が一斉に「返品」扱いになる、という取り返しのつかない事故になる。しかもエラーは一切出ず、静かにデータが壊れる。お金や状態を持つ enum は必ず `EnumType.STRING`（＝"NEW" という名前で保存）にすべき。ちなみに `@Enumerated` を書かない場合のデフォルトも ORDINAL なので、「書き忘れ」も同じ地雷になる。

2. **状態遷移のチェックが無く、あり得ない遷移が素通りする**: `updateStatus` は渡された文字列をそのまま `setStatus` しているだけで、「今の状態から、その状態へ進んでよいか」を一切見ていない。そのため、すでに `CANCELED`（キャンセル済み）の注文を `SHIPPED`（出荷済み）に上書きする、といった業務上あり得ない遷移がそのまま通ってしまう。状態を持つ業務では「進んでよい道順（＝ステートマシン：状態と、その間で許される移動を定めた仕組み）」を必ず持ち、外れた遷移は弾くべき。

3. **Entity（Order）をそのままAPIレスポンスで返している**: `updateStatus` も `list` も、DBのテーブルに対応する `Order` エンティティを直接返している。これには2つの被害がある。1つは、`shippingAddress`（住所）のような外に出したくない内部項目まで丸ごと露出すること。もう1つは、Entity は将来カラムが増えると勝手にAPIの応答も変わってしまい、画面側と仕様が噛み合わなくなること。外に返す形は、専用の DTO（＝Data Transfer Object：受け渡し用の入れ物）に必要な項目だけ詰め替えて切り離すべき。

4. **`findAll()` で全件取得している（ページングが無い）**: `list()` はテーブルの注文を無条件に全部メモリに読み込む。注文が10件のうちは動くが、数万件になった瞬間、DBもアプリもレスポンスも膨れ上がって固まる（＝一覧APIの定番事故）。一覧は必ず `Pageable`（＝1ページ分だけ切り出す仕組み）を受け取り、少しずつ返すべき。

5. **`Optional.get()` で存在チェックをしていない**: `orderRepository.findById(id).get()` は、注文が見つからないと `NoSuchElementException` という分かりにくい例外で落ちる。`get()`（＝中身があると信じて箱を無理やり開ける）ではなく、`orElseThrow` で「注文が見つかりません」と意味のある形で知らせるべき。

## ⭕️ 改善案 (good/ 配下)

1. **`@Enumerated(EnumType.STRING)` で名前保存にする**: enum を並び順の番号ではなく `"NEW"` などの名前でDBに保存する。こうすれば、あとから状態を途中に追加・並べ替えても既存データの意味がずれない。

2. **遷移ルールを `OrderStatus` 自身に持たせ、`canTransitionTo` で弾く**: 各状態に「次に進んでよい状態の集合」を持たせ、`order.changeStatusTo(...)` の中で許可された遷移かを確認する。`CANCELED → SHIPPED` のような不正遷移は例外で弾かれる。ルールが enum に集約されるので、状態が増えても1か所を見れば全体像が分かる。

3. **応答用の DTO（`OrderResponse`）に詰め替えて返す**: 住所などの内部項目を出さず、必要な `id / customerName / status` だけを返す。Entity の変更がそのままAPIに漏れることもなくなる。

4. **`Pageable` を受け取りページングする**: `findAll(pageable)` で1ページ分だけ取得し、`Page<OrderResponse>` として返す。件数が増えても破綻しない。

5. **`orElseThrow` で存在チェックする**: `findById(id).orElseThrow(...)` にして、見つからないときは意味のあるメッセージで例外を投げる。

## 💬 レビューコメント例文

> 状態を enum で扱っていて、遷移の処理もちゃんとサービスにまとまっていますね。動くものとしては良いスタートです。そのうえで、これは本番で効いてくるので必ず直したい、という点が1つあります。
>
> 一番大事なのは `status` の保存方法です。いま `@Enumerated(EnumType.ORDINAL)` になっていて、これだと enum が「NEW=0, PAID=1…」という並び順の番号でDBに保存されます。今後「返品受付」みたいな状態を途中に足したくなったとき、番号の意味が全部ずれて、出荷済みの注文が一斉に別状態に化けてしまうんです。しかもエラーが出ずに静かにデータが壊れるのが怖いところ。ここは `EnumType.STRING` にして名前で保存するようにしておけば、あとから状態を足しても安全です。これはもう「好み」ではなく事故防止のルールとして、状態系の enum では STRING 固定にしましょう。
>
> あと2つ、余裕があれば一緒に。1つは、いまキャンセル済みの注文でも出荷済みに上書きできてしまうので、「進んでよい状態か」のチェックを OrderStatus 側に持たせると業務ルールが崩れません。もう1つは、一覧が `findAll()` の全件取得になっている点で、注文が増えると固まるので `Pageable` でページングを入れておきたいです。ついでに、外向けの応答は Order エンティティ直返しだと住所まで漏れるので、DTO に詰め替えると安心ですよ。
