## ❌ NGポイント (bad/ 配下)

1. **論理演算子の優先順位ミスで「GOLDなら金額に関係なく常に適用」になっている（最重要バグ）**: `if (rank == GOLD || rank == SILVER && amount >= 5000)` と書いているが、Java では `&&`（＝かつ）は `||`（＝または）より先に評価される（＝演算子の優先順位。掛け算を足し算より先に計算するのと同じ）。そのためこの式は、書いた本人の頭の中では「(GOLD または SILVER) かつ 5000円以上」のつもりでも、実際には `GOLD || (SILVER && amount >= 5000)` と解釈される。結果、**GOLD会員は金額が0円でも常に true**、SILVERだけが5000円以上を求められる、という意図と違う挙動になる。金額チェックをすり抜けてクーポンが使えてしまう、売上に直結する事故。意図した優先順位は必ず括弧 `( )` で明示すべき。

2. **キャンペーン期間の境界がずれている（オフバイワン＝1個ずれ）**: `today.isAfter(campaignStart)` は「開始日**より後**」なので、**開始日当日は含まれない**（本来は当日から使えてほしい）。さらに `!today.isAfter(campaignEnd.plusDays(1))` は「終了日の翌日まではOK」という意味になり、**終了日の翌日まで1日多く**クーポンが通ってしまう。`< / <=`、`isBefore / isAfter` の取り違えは「1個だけずれる」形で紛れ込みやすく（＝オフバイワン）、テストで境界日をまたいで確認しないと気づけない。「開始日を含む／含まない」「終了日を含む／含まない」を仕様と突き合わせて書くべき。

3. **否定の掛け違い（ド・モルガンの法則の誤り）で、退会済み会員を弾けていない**: 「ログイン済み**かつ**有効な会員だけ許可」＝「そうでなければ弾く」を、`if (!member.isLoggedIn() && !member.isActive())` と書いている。これは「ログインしておらず、**かつ** 退会もしている」＝**両方が false のときだけ**弾く、という意味になってしまう。本当は「ログインだけしていて退会済み」の人も弾きたいのに、この人は素通りする。`!(A && B)`（＝AとBが両方真、を否定）は、ばらすと `!A || !B`（＝どちらか一方でも偽）になる（＝ド・モルガンの法則。「両方そろってはいない」＝「どちらかが欠けている」）。`&&` と `||` を取り違えているのがバグの正体。

4. **`== true` という冗長な比較で、かえって読みにくくバグを隠している**: `member.isCouponEnabled() == true` は、真偽値（boolean）をわざわざ `== true` と比べていて意味がない（`isCouponEnabled()` 自体がすでに true/false）。書くなら `member.isCouponEnabled()` だけでよい。冗長なだけでなく、うっかり `= true`（代入）と書くと常に true になる古典的バグの温床にもなる。真偽値は素直にそのまま条件に使う。

5. **`member` が null のとき NullPointerException で落ちる（未ログイン・未指定の考慮漏れ）**: メソッド冒頭でいきなり `member.getRank()` を呼んでおり、`member` が null で渡されると即 NullPointerException（＝中身が無いものを触ろうとして落ちる例外）になる。判定処理は「怪しい入力」ほど渡ってきやすい入口なので、null は黙って落とさず、はっきり異常として弾く（または明示的に false を返す）べき。

6. **条件が一つの巨大なネスト（入れ子）に詰め込まれていて読めない／直しにくい**: ランク・金額・期間・ログイン・上限が `if` の入れ子で積み上がっており、「どの条件が何のためにあるのか」が読み解きにくい。読みにくさは NG1〜3 のような**判定ミスを隠す温床**そのもの。条件を意味のある名前の真偽値や小さなメソッド（`isRankEligible()` など）に分解すれば、名前を読むだけで意図が分かり、優先順位・境界・否定のミスも一目で見つけられるようになる。

## ⭕️ 改善案 (good/ 配下)

1. **意図した優先順位を括弧で明示する**: `(rank == GOLD || rank == SILVER) && amount >= MIN_AMOUNT` のように、「ランク条件」を括弧でまとめてから金額条件と `&&` でつなぐ。頭の中の意図とコードの解釈を一致させる。

2. **境界を仕様どおりに書く（当日を含むなら isBefore/isAfter の否定形を使う）**: 「開始日以上 かつ 終了日以下（両端を含む）」を `!today.isBefore(start) && !today.isAfter(end)` で表現する。`plusDays(1)` のような小細工で境界をずらさない。

3. **否定は肯定形で素直に書く**: 「ログイン済み かつ 有効」を `member.isLoggedIn() && member.isActive()` とそのまま肯定形で書き、最後に `&&` でつなぐ。`!(A && B)` を無理にばらして書かないことで、ド・モルガンの取り違えを起こさない。

4. **真偽値はそのまま使い、`== true` を消す**: `member.isCouponEnabled()` とだけ書く。冗長さと `= true` 誤記のリスクを同時に無くす。

5. **null は入口で弾く**: 先頭で `if (member == null) throw new IllegalArgumentException(...)` として、意味のある形で異常を知らせる。

6. **条件を名前付きの真偽値・小さなメソッドに分解し、早期returnで読みやすく**: `isRankEligible()` / `isWithinCampaign()` / `isLoggedInAndActive()` に分ける。最終行は `return rankEligible && withinCampaign && loginOk && withinLimit;` と全体像がひと目で読める形にする。

>
> 一番大きいのが `rank == GOLD || rank == SILVER && amount >= 5000` の行です。Java は `&&` を `||` より先に計算するので、これは意図と違って `GOLD || (SILVER && 5000以上)` と読まれます。つまり **GOLD会員は金額0円でもクーポンが通ってしまう**んです。ここは `(GOLD || SILVER) && 5000以上` と括弧で意図をはっきりさせましょう。「かっこを省略しても動くから」ではなく、「読む人（未来の自分含む）が誤解しないように」括弧を付ける、と考えるといいです。

> あと2つ、境界と否定も見てほしいです。キャンペーン期間の判定が `isAfter(開始日)` になっていて開始日当日が使えず、逆に `終了日+1日` まで通ってしまっています（1日ずれ）。「当日を含むか」を仕様と突き合わせて、`!isBefore(開始)` と `!isAfter(終了)` に直しましょう。それと退会チェックの `!loggedIn && !active` は、「両方だめな人だけ弾く」意味になっていて、ログイン中の退会済みユーザーが素通りします。ここは素直に「ログイン済み かつ 有効」を肯定形で書くのが安全です。
