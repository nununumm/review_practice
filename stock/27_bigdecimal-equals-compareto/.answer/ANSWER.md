## ❌ NGポイント (bad/ 配下)

1. **`new BigDecimal(0.1)` と double を引数に取るコンストラクタで生成している（誤差が入る）**: `BigDecimal` は「誤差なく計算するための型」なのに、その材料に `double`（＝コンピュータ内部では2進の小数）を渡してしまっている。`double` の `0.1` は内部的には `0.1` ちょうどではなく `0.1000000000000000055511151231257827021181583404541015625` という近い値になっており、`new BigDecimal(0.1)` はこの誤差を含んだ値をそっくり取り込む。つまり「せっかく BigDecimal を使ったのに最初から誤差入り」という本末転倒な状態。割引率をこれで作ると、掛け算のたびにこの余計な桁が付いて回る。正しくは `new BigDecimal("0.1")`（＝文字列で渡すと書いたとおり正確に 0.1 になる）か、`BigDecimal.valueOf(0.1)`（＝内部で文字列表現に直してくれる）を使う。

2. **金額の一致判定を `paid.equals(billed)` で行っている（スケール違いで誤判定）**: `BigDecimal` の `equals` は「値が同じか」だけでなく「スケール（＝小数第何位まで持っているか）」まで一致しないと `true` にならない、という特殊な性質を持つ。たとえば `100`（スケール0）と `100.00`（スケール2）は、数としてはまったく同じ「百」なのに、`equals` では小数の桁数が違うため `false` になる。DBや外部から来た金額はスケールがまちまちなので、正しく満額を支払っているのに「不一致（未払い）」と誤判定してしまう事故につながる。値の等価・大小は `compareTo(...) == 0`（＝数の大小だけを比べ、`0` なら等しい）で判定するのが正解。たとえるなら、`equals` は「1000円ちょうど」と「1000円00銭」を"表記が違うから別物"と言い張るようなもの。

3. **`divide(...)` に scale と RoundingMode を指定しておらず、割り切れないと例外で落ちる**: `billed.divide(new BigDecimal(times))` のように桁数も丸め方も指定しない `divide` は、`1 ÷ 3 = 0.3333...` のように「割り切れず無限に続く小数」になる計算のとき、「有限の桁で正確に表せない」として `ArithmeticException`（＝無限小数エラー）を投げて落ちる。分割回数によっては本番でいきなり例外が飛ぶ時限爆弾。除算では必ず `divide(相手, scale, RoundingMode.HALF_UP)` のように「小数何桁まで」「どう丸めるか」を指定する。

4. **割引率などがマジックナンバー気味で、null / 負数 / 0除算のチェックが無い**: 割引率 `0.1` の意味づけはあるものの、丸めの桁数などは裸の状態で、`paid` / `billed` が `null` でも `signum` チェックが無く NullPointerException になりうる。また `calculateInstallment` は `times` が `0` でも素通りするため 0除算で落ちる。金額計算は境界（null・負数・0）を最初に弾いておくべき。

## ⭕️ 改善案 (good/ 配下)

1. **生成は `new BigDecimal("0.1")`（文字列）か `BigDecimal.valueOf(...)` にする**: 材料に double を通さないことで、誤差が入り込む余地を最初から無くす。定数 `DISCOUNT_RATE` は `new BigDecimal("0.1")` で定義する。

2. **一致・大小の判定は `compareTo(...) == 0` に統一する**: `equals` のスケール依存を避け、`paid.compareTo(billed) == 0` で「数として等しいか」を判定する。これで `100` と `100.00` を正しく同額と扱える。

3. **除算は `divide(相手, scale, RoundingMode.HALF_UP)` で桁数と丸め方を明示する**: 割り切れない計算でも例外で落ちず、指定桁で四捨五入した安全な結果を返せる。丸めの桁数（円なので 0）は定数 `MONEY_SCALE` にして意味を持たせる。

4. **null・負数・0除算を先頭でチェックし、丸め桁を定数化する**: 各メソッドの入口で `null` と負数、分割回数 `<= 0` を弾き、意味のある例外を投げる。金額の丸めは `setScale(MONEY_SCALE, RoundingMode.HALF_UP)` で端数のブレも無くす。

>
> まず割引率の `new BigDecimal(0.1)`。せっかく誤差の出ない型なのに、材料に `double` の `0.1` を渡すと、`0.1` は内部だと `0.1000...0055` みたいな近い値なので、その誤差ごと取り込んでしまうんです。ここは `new BigDecimal("0.1")` と文字列で渡すと、書いたとおり正確な 0.1 になります。
>
> 次が一番怖いところで、支払額の一致判定に `equals` を使っている点です。BigDecimal の `equals` は「値」だけじゃなく「小数の桁数（スケール）」まで一致しないと true にならない仕様で、`100` と `100.00` は同じ金額なのに false になります。つまり満額払っているお客さんを「未払い」と誤判定しかねない。金額の一致は `paid.compareTo(billed) == 0` に変えましょう。compareTo は数の大小だけを見るので、桁数が違っても正しく等しいと判定できます。

> 最後に `divide` ですが、桁数と丸め方を指定しないと、分割回数によっては 1÷3 みたいに割り切れず、その場で例外が飛んで落ちます。`divide(相手, 0, RoundingMode.HALF_UP)` のように「何桁で・どう丸めるか」を必ず添えてください。どれもテストで金額を `100.00` にした瞬間に露見するタイプなので、ここを直せばぐっと堅くなりますよ！
