# 第38問：外部連携処理の例外設計 — 解答

> この問題のテーマは「**例外そのものの設計**」です。第31問（`@ControllerAdvice` でエラー処理を集約する）とは別で、ここでは「原因の連鎖・独自例外の階層・握りつぶし・チェック例外の扱い」に絞っています。

## ❌ NGポイント (bad/ 配下)

1. **原因（cause）を捨てて新しい例外を投げている**: `pay()` の
   `catch (Exception e) { throw new RuntimeException("決済に失敗しました"); }` が最大の問題です。
   元の例外 `e` を渡していないので、**本当にどこで何が起きたか（＝スタックトレース）が丸ごと消えます**。
   本番で「決済に失敗しました」というログだけが残り、通信エラーなのか残高不足なのかバグなのか、
   調査のしようがなくなります。例外は「事件の目撃者」で、cause はその「証言」。証言を捨ててはいけません。

2. **例外を握りつぶして黙って null を返している**: `tryPayAndGetTransactionId()` は失敗すると
   `return null` します。呼び出し側は「決済が成功して取引IDが取れなかった」のか「そもそも失敗した」のか
   区別できません。**失敗が成功のフリをして通り抜けてしまう**（＝後続で NullPointerException になったり、
   最悪お金が動いていないのに注文が確定したりする）、いちばん怖いパターンです。

3. **`catch (Exception e)` / `throws Exception` で区別せず一括処理**: 通信エラー・パースエラー・残高不足という
   「性質がまったく違う失敗」を全部 `Exception` ひとまとめで捕まえています。`isPaymentApproved` の
   `throws Exception` も同じで、**呼び出し側は「何が起きうるか」がまったく分からず**、想定外のバグ例外
   （NullPointerException 等）まで一緒に飲み込んでしまいます。

4. **独自例外の階層が無く、リトライ可否を区別できない**: 失敗はすべて `RuntimeException` に潰されるので、
   呼び出し側は「もう一度やれば直る一時的エラー（通信断）」なのか「何度やっても無駄なエラー（残高不足）」なのかを
   判断できません。結果、残高不足なのに延々リトライする、といった無駄・事故につながります。

5. **二重処理 & finally の return で握りつぶし**: `isPaymentApproved()` は
   `log.severe(...)` してから `throw e` しています（＝**同じ例外をログしてさらに投げる二重処理**。上位でも
   ログされて二重に記録される）。さらに致命的なのが `finally { return approved; }` で、
   **finally の中で return すると、try/catch でせっかく投げた例外が捨てられて握りつぶされます**。
   通信エラーで throw したはずが、finally の return が勝って `false` が返り、例外が消えます。

## ⭕️ 改善案 (good/ 配下)

1. **原因を必ず連鎖させる**: `new PaymentSystemException("...", e)` のように、翻訳後の例外に元の例外 `e` を
   cause として渡す。これでスタックトレースがつながり、「表向きは決済失敗、原因はタイムアウト」まで追えます。

2. **独自例外を階層で設計する**: `PaymentException`（親）の下に
   `PaymentSystemException`（システム系＝リトライ可能）と `PaymentDeclinedException`（業務系＝リトライ不可）を用意。
   `isRetryable()` という型の目印で、呼び出し側は「リトライすべきか」を型を見るだけで判断できます。
   チェック例外（`throws` 必須）ではなく `RuntimeException` ベースにして、境界でまとめて扱う方針にしています。

3. **生の例外を「翻訳」して区別する**: `catch (Exception)` の一括りをやめ、`GatewayDeclinedException` /
   `IOException` / `GatewayParseException` を**別々に catch** して、それぞれ適切な独自例外に翻訳。
   想定外の例外はわざと素通りさせ、バグに早く気づけるようにします。

4. **握りつぶさない**: `null` や `false` でごまかさず、失敗は必ず例外で上に伝える。`payAndGetTransactionId()` は
   成功時のみ取引IDを返し、失敗時は `pay()` の例外がそのまま伝播します。

5. **ログは境界で一度だけ / finally で return しない**: サービス層ではログを出さずに投げるだけにし、
   最終的なログは上位（Controller や `@ControllerAdvice`）で一度だけ記録。`finally` は後片付け専用にして、
   絶対に `return`（や `throw`）を書かない。

## 💬 レビューコメント例文

> 決済サービスの例外まわり、いくつか一緒に見直したいです。まず `pay()` の
> `catch (Exception e) { throw new RuntimeException("決済に失敗しました"); }` は、元の `e` を渡していないので
> 原因のスタックトレースが消えてしまいます。障害調査のときに効いてくるので `new PaymentSystemException("...", e)` の形で
> 原因を必ず連鎖させましょう。あと `tryPayAndGetTransactionId` が失敗時に `null` を返すのと、
> `isPaymentApproved` の `finally { return approved; }` は、どちらも例外がこっそり握りつぶされて
> 「失敗が成功のフリをする」状態になっています。ここはお金が絡む処理なので、失敗はちゃんと例外で上まで伝えたいです。
> ついでに、通信エラー（リトライすれば直るかも）と残高不足（何度やっても無駄）は性質が違うので、
> 独自例外を「システム系／業務系」で型分けして、呼び出し側がリトライ可否を判断できるようにしておくと安心です。
