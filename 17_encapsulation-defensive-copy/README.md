# 第17問：買い物カゴの中身を保持するクラス

**📅 出題日**: 2026年8月3日

## 📋 レビュー課題

ECサイトの「買い物カゴ（`ShoppingCart`）」を表すクラスと、それを組み立てる `CartService` です。

`ShoppingCart` は、
- カゴに入っている商品名の一覧（`items`）
- カゴを作成した日時（`createdAt`）

を持ち、`CartService` は、
- 商品リストから新しいカゴを作る（`createCart`）
- カゴに商品を1つ追加する（`addItem`）
- カゴの中身の件数を返す（`itemCount`）

という、カートまわりでよくある処理をまとめています。

対象: `bad/ShoppingCart.java` / `bad/CartService.java`

一見ふつうに動きそうに見えますが、**このクラスを受け取った人（呼び出し元）が、`ShoppingCart` の“知らないところ”でカゴの中身を勝手に書き換えられてしまう**書き方になっています。たとえば、あるカゴを作ったあとに、元の商品リストを別の処理で使い回すと、作ったはずのカゴの中身まで一緒に変わってしまう——そんな“気づきにくい事故”が起きます。

「どこが問題か、どう直すべきか」をテックリード目線でレビューしてみてください。

---

## ❌ NGポイント (bad/ 配下)

1. **入口：外から渡されたリストをそのまま保持（共有参照／別名の罠）**: コンストラクタで `this.items = items;` と、受け取った `List` の“参照”をそのまま持っている。呼び出し元が持っている元リストと **「同じ1個のリストを指しているだけ」** なので、あとで元リストを `add`/`clear` すると、作ったはずのカゴの中身まで一緒に変わる。テストでは気づきにくく、本番で「なぜかカゴに知らない商品が…」となる典型事故。

2. **出口：getter が内部リストの“原本”をそのまま返す**: `getItems()` が `return items;` で内部リストの参照を渡している。受け取った側が `cart.getItems().clear()` や `.add(...)` でカゴの中身を**外から破壊できる**。フィールドを `private` にしても、getter が原本を漏らしていれば `private` の意味は無効化される（＝カプセル化の“出口の穴”）。

3. **変更：全開放の setter（`setItems` / `setCreatedAt`）**: 何でも受け付ける setter を公開しているため、`null` や不正な値（過去・未来の日時など）も入れ放題。特に `createdAt`（作成日時）は**一度決めたら変わらないはずの値**なのに、後からいくらでも書き換えられてしまう。

4. **可変な日時型 `Date` を保持・返却**: `Date` は `setTime(...)` などで後から中身を書き換えられる**可変オブジェクト**。仮に getter でそのまま返すと、受け取った側が日時を改ざんできる。日時は不変型（`Instant` / `LocalDateTime` 等）で持つのが定石。

5. **`CartService` が getter 経由で内部を変更**: `addItem` が `cart.getItems().add(item)` と、getter で取り出したリストを直接いじっている。これは 2 の“出口の穴”を使ってカプセル化を迂回している症状で、「本来カート自身が持つべき『追加』の責務が外に漏れている」状態。

## ⭕️ 改善案 (good/ 配下)

1. **入口を塞ぐ：リストはカート自身が内部で生成**: コンストラクタで外の `List` を受け取らず `this.items = new ArrayList<>();` とカート専用の入れ物を作る。外のリストと縁が切れるので共有参照の事故が起きない。（もし既存データからカートを作る必要がある場合は、`this.items = new ArrayList<>(src);` と**防御的コピー**＝“写しを持つ”で入口を守る。）

2. **出口を塞ぐ：読み取り専用ビューを返す**: `getItems()` は `Collections.unmodifiableList(items)` を返す。中身を見る・ループで回すのはOKだが、`add`/`clear` しようとすると例外で弾かれる。原本を“ガラスケース越し”に見せるイメージ。

3. **変更は「意図のある窓口」に限定**: 全開放の setter を廃止し、`addItem(String)`（追加）や `markUsed()`（使用を記録）といった**操作の意味が伝わるメソッド**だけを公開。「変更は許すが、やり方はクラスが決める」形にする。

4. **変えない値は `final` + 不変型**: `createdAt` は `final Instant` にして、作成後は誰も書き換えられないようにする。`lastUsedAt`（最終使用日時）は変わってよい値なので `final` にはしないが、更新は `markUsed()` 経由だけに絞る。

5. **`markUsed()` が値を外から受け取らない**: `setLastUsedAt(値)` だと `null`・過去・未来など**おかしな値を入れられてしまう**。`markUsed()` は常に「今の時刻」を入れるので、正しさをクラス自身が保証できる（＝ルールが1箇所に集約される）。

> 補足：作成日時に `Instant.now()` を直接使っているため、厳密な単体テスト容易性の観点では `Clock` を注入する余地がある（第8・12問のテーマ）。本問の主眼はカプセル化なので、そこは踏み込まず不変性の徹底に絞っている。

## 💬 レビューコメント例文

> カート周り、機能自体はちゃんと動いていて良いと思います 🙆 ひとつ設計の相談をさせてください。今 `ShoppingCart` が外から渡された `List` をそのまま保持していて、さらに `getItems()` でも内部リストをそのまま返しているので、呼び出し元が知らないうちにカゴの中身を書き換えられてしまう状態です（元リストへの `add` や `cart.getItems().clear()` が素通りします）。
>
> リストはカート内部で持つようにして、外へ返すときは `Collections.unmodifiableList` で読み取り専用にすると安全です。商品追加は `cart.addItem(...)` のような窓口に寄せると、変更の入口を1本化できます。あわせて、作成日時は変わらない値なので `final` + `Instant`、最終使用日時は `setter` ではなく `markUsed()` のような「操作の意味が伝わるメソッド」で更新すると、変な日時が入る余地もなくせます。`private` にするだけだと getter から漏れてしまうのがポイントなので、次のリファクタで一緒に“入口・出口・変更のしかた”を整えてみましょう 💪
