# 第10問：抽選キャンペーンの応募受付サービス（同時アクセス）

**📅 出題日**: 2026年7月19日

## 📋 レビュー課題

抽選キャンペーンの応募を受け付ける Spring Boot のサービスです。
`apply(userId)` を呼ぶと、そのユーザーの応募を記録します。
**1ユーザーにつき1回だけ**応募できるように、応募済みかどうかをチェックしています。

ローカルで1人ずつ順番に叩くと、2回目はちゃんと「すでに応募済みです」と弾かれ、
合計応募数もきれいに増えていって、一見きちんと動いています。

対象: `bad/CampaignApplicationService.java`

このサービスは人気キャンペーンの一部で、**開始と同時に大量の応募が同時に押し寄せる**場面で使われます。
「どこが問題か・どう直すべきか」をレビューしてみてください。
今回は特に **「同時アクセスに耐えられるか（並行処理・スレッド安全性）」** の観点で見てみましょう。

---

## ❌ NGポイント (bad/ 配下)

1. **Check-Then-Act の競合状態（レースコンディション）**:
   `containsKey`（応募済み？を確認）と `put`（記録する）が別々の動作になっているため、その“すきま”に別スレッドが割り込める。
   同じユーザーの2リクエストがほぼ同時に来ると、両方が「まだ応募していない」と判定を通過し、**同じ人が2回応募できてしまう**。「確認してから実行する」パターンは並行処理では危険。

2. **共有フィールドがスレッドセーフでない**:
   `@Service` はアプリ全体で1個だけ作られ、全リクエスト（全スレッド）が同じインスタンスを使い回す。
   その中の `HashMap`（`appliedUsers`）を複数スレッドが同時に書き込むと内部構造が壊れうる（`HashMap` は並行書き込み非対応）。
   `totalApplications = totalApplications + 1` も「読む→+1→書く」の3ステップで、追い越しにより**カウントが実際より少なくズレる**。

3. **状態をメモリに持っているので消える・分裂する**:
   `appliedUsers` はメモリ上の箱なので、**サーバー再起動で応募済みの記録が消える**。
   さらに本番でサーバーを複数台に増やすと箱が**台ごとに分裂**し、A号機とB号機で同じ人が1回ずつ通ってしまう。

4. **“本当に守りたいルール”を守る場所が間違っている**:
   「1ユーザー1回だけ」も「合計応募数」も、データの最終的な置き場所である**DBで守る/数えるべき**。
   メモリの門番（`appliedUsers`）は、DBの受付係（`campaignRepository`）と役割がかぶった冗長な存在。

## ⭕️ 改善案 (good/ 配下)

1. **DBのユニーク制約を“門番”にする**:
   `applications` テーブルの `user_id` 列にユニーク制約（同じ値を2つ入れさせないルール）をかける。
   これは分解できない1動作でDB自身が保証するので、2件同時に保存が走っても2件目を必ず弾く。

2. **「確認してから保存」→「保存を試みて、弾かれたら気づく」へ発想を逆転**:
   事前チェックをやめ、まず `save()` を試みる。ユニーク制約違反（`DataIntegrityViolationException`）を
   catch して「すでに応募済みです」に変換する。すきまが生まれないので競合状態が原理的に起きない。

3. **サービスから状態（フィールド）を排除**:
   `appliedUsers` と `totalApplications` を削除。合計は `campaignRepository.count()` でDBに数えさせる。
   共有される可変フィールドが無くなり、どのスレッドが同時に呼んでも安全（ステートレス＝状態を持たない）。

4. **DI はコンストラクタ注入に**:
   `@Autowired` フィールド注入をやめ、`final` + コンストラクタで受け取る（差し替え不可・必須を保証）。

## 💬 レビューコメント例文

> apply() のロジック、ローカルだと綺麗に動いていて良いと思います！ひとつ、本番の「開始と同時にドッと来る」状況を想定して相談させてください。
> 今は「応募済みか確認 → 記録」の2ステップになっていて、その“すきま”に同じユーザーの別リクエストが割り込むと、両方すり抜けて二重応募が通ってしまう可能性があります（Check-Then-Act の競合状態というやつです）。
> あと `@Service` は1インスタンスを全リクエストで共有するので、中の `HashMap` やカウンタを同時に触ると壊れたり数がズレたりします。加えて、メモリ保持だと再起動で消える・複数台で分裂する、という弱点もあります。
> ここは思い切って、`user_id` にDBのユニーク制約をかけて、「保存を試みて弾かれたら“応募済み”と返す」形に寄せませんか？ そうすると `appliedUsers` ごと消せてコードもぐっと減りますし、正しさをDBが保証してくれるので安心です。合計数も `count()` に任せればズレません。一緒に直してみましょう！
