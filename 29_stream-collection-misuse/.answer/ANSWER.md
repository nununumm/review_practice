## ❌ NGポイント (bad/ 配下)

1. **Stream の `forEach` で外部リストに add している（副作用でのStream誤用）**: `highValueOrders`（外側で用意した `ArrayList`）に `orders.forEach(... add(order) ...)` で詰め込んでいる。Stream（＝データを流れ作業で処理する仕組み）は本来「入力を変換して新しい結果を作る」道具で、外側の入れ物をいじる（＝副作用）ために使うものではない。この書き方は普通の `for` 文より読みにくいだけで、Stream の利点（並列化・簡潔さ）を一切活かせていない。`filter().collect()` で書けば「条件に合うものを集める」という意図がそのまま1行で表せる。

2. **商品マスタを明細ごとに線形探索していて O(n²)（最重要・性能）**: 合計計算とカテゴリ集計の両方で、明細1件ごとに `for (Product p : products)` と商品リストを毎回まるごと走査している。明細が m 件・商品が n 件なら m×n 回の比較になり（＝O(n²)、二乗で膨らむ計算量）、注文が増えると急激に遅くなる。しかも同じ探索を2箇所で繰り返している。商品マスタを最初に一度だけ `Map<Long, Product>`（ID→商品の対応表）にしておけば、各検索は `map.get(id)` の一発（ほぼ一定時間）で済む。

3. **結果が0件のとき `null` を返している**: 高額注文が無いと `return null`。呼び出し側が `summary.getHighValueOrders()` などを触った瞬間に `NullPointerException`（＝中身が無いのに使おうとして落ちる）になる。「該当なし」は異常ではなく正常な結果なので、**空のリスト**を返すのが鉄則。呼び出し側は `for` で回しても0回で素通りでき、null チェックが要らなくなる。

4. **`Optional.get()` を存在チェックなしで多用している**: `first.get().getName()` のように、中身があるか確かめずにいきなり取り出している。`Optional`（＝「有るかもしれない箱」）は、空のときに `get()` すると `NoSuchElementException` で落ちる。さらに手前の `items.get(0)` も、明細リストが空だと `IndexOutOfBoundsException` になる。「無いかもしれない」を表す型なのに、無い場合の処理を書いていないのが問題。

5. **Stream の外の可変変数 `total` に `forEach` で足し込んでいる**: `long total = 0;` を用意して `forEach` の中で `total += ...`。これは「累積を外の変数に貯める」古い書き方で、並列化ができず（複数スレッドで同時に足すと壊れる）、読み手も「最終的にいくつになるのか」を追いかけないと分からない。`mapToLong(...).sum()` を使えば「各明細を金額に変換して合計する」と一目で分かり、安全。

6. **カテゴリ別集計を手製 `HashMap` の `containsKey`→`get`→`put` で組み立てている**: 「キーが有れば足す、無ければ新規」を自前で書いている。動くが冗長で、キー計算・取得・書き戻しを手作業でやっているぶんバグの温床。`Collectors.groupingBy` + `summingLong` を使えば「カテゴリごとにまとめて金額を合計」が宣言的に1文で書け、意図が明確になる（`getOrDefault` や `merge` でも短くできるが、集計そのものは `groupingBy` が本命）。

> 補足：2・4 は「商品マスタに無い productId が来たら？」というデータ不整合の考慮漏れにも繋がっている（bad では `found` が null のまま `found.getPrice()` を呼んで NPE になりうる）。good では検索を1箇所に集約し、無ければ意味のある例外を投げるようにしている。

## ⭕️ 改善案 (good/ 配下)

1. **商品マスタを先に Map 化して O(n) に**: `products.stream().collect(Collectors.toMap(Product::getId, Function.identity()))` で「ID→商品」の対応表を一度だけ作る。以降の検索はすべて `map.get(id)`。二重ループが消え、性能が明細件数に比例するだけ（O(n)）になる。

2. **合計は `mapToLong().sum()`**: `items.stream().mapToLong(item -> 単価×数量).sum()`。外部変数への足し込みをやめ、式が意図をそのまま表す。

3. **カテゴリ別は `groupingBy` + `summingLong`**: `Collectors.groupingBy(カテゴリ, Collectors.summingLong(金額))` の1文に置換。手製 HashMap の分岐が不要。

4. **抽出は `filter().collect(toList())`**: 「条件に合う注文だけ集める」を素直に表現。該当なしでも空リストが返り、`null` を返さない。

5. **`Optional` は `map`＋`orElse` で安全に**: 代表商品名は `items.stream().findFirst().map(...).orElse("")` とし、明細が空でも `get(0)` や `Optional.get()` で落ちないようにする。

6. **検索の一元化＋意味のある例外**: 商品検索を `productOf(...)` に集約し、見つからなければ `null` を返さず `IllegalStateException` を投げて、データ不整合を黙って握りつぶさない。

7. **マジックナンバーを定数に**: しきい値 `10000` を `HIGH_VALUE_THRESHOLD` という名前付き定数にし、意図と変更箇所を明確にする。

>
> 一番効いてくるのが商品マスタの引き方です。いま明細1件ごとに `products` を頭から全部探していて、明細×商品の掛け算の回数になってしまうんです（注文が増えるとジワジワ重くなるやつ）。最初に一度だけ `Map<Long, Product>`（ID→商品の対応表）を作っておいて、あとは `map.get(id)` で引くようにすると、検索が一発になって速度も安定します。同じ探索を合計とカテゴリ集計で2回書いている重複も、これで1本にまとめられます。
>
> あと Stream の使い方を少しだけ。合計は外の `total` に `forEach` で足すより `mapToLong(...).sum()`、高額注文の抽出は外の `ArrayList` に add するより `filter().collect(toList())` にすると、「何をしたいか」がそのまま式になって読みやすくなります。カテゴリ別も `groupingBy` + `summingLong` で1文にできますよ。
